# Durable recovery scenario fixtures

These are behavioral test vectors for a future Rust Durable implementation, not a crate, serialized storage snapshots, or an executable test suite. The reference is upstream pi at commit [`827383a15262905f82e418483825a49dbb1adbf5`](https://github.com/earendil-works/pi/tree/827383a15262905f82e418483825a49dbb1adbf5/packages/durable). A harness should translate the symbolic actions to its public API and observe persistent records and a fake external service. Names and IDs in the fixtures are logical labels, not required wire formats.

## How to use

Each scenario is independent: start with an empty durable store and fake service unless `setup` says otherwise. Run `steps` in order. A step has one `action`, an optional `boundary`, and optional `expect` assertions immediately after that action. `expect_final` is checked after all steps. Strings in expectations state observable requirements, not literal error messages. Arrays are ordered only when they explicitly describe a sequence; compare sets otherwise. IDs like `T`, `C1`, and `R` are stable harness aliases, not concrete storage IDs. Counts cover the entire scenario, including prior processes. `reopen` opens the same committed store with the same definitions and fake external service, but does not schedule work until `resume` unless a step explicitly waits. Tests must not simulate process death with graceful close.

The test adapter implements the following fault controls: `crash` kills the host at the named barrier and discards volatile state; for `before_commit` it must ensure the named write did **not** reach durable storage, while `after_commit` means its atomic storage transaction completed. An in-flight write whose outcome is unknown must be tested in both branches: recovery may see either complete old or complete new state, never a partial transaction. An external effect is outside the store and survives host death. Use a controlled storage implementation/barriers and a fake clock; never depend on sleeps or probabilistic timing. Install task definitions before opening except in the missing-definition scenario. `run_to` advances execution only to the named barrier, and `observe` must not enable scheduling. The fixture's task programs are specified below; fake task execution must be gated at each boundary.

## Test programs and observations

* **Transfer** starts at `prepare`, commits `apply` with key `transfer-T` and memo `requested=7`, invokes fake service `apply(key, 7)`, then atomically commits terminal `completed` with `receipt=70` and entry `receipt:70`. The fake service records every call but applies a key only once. Memo writes are durable first-writer-wins, not a transaction with the external service.
* **Atomic task** commits checkpoint `next`, entry `E`, document value `1`, and child `C` in one transaction. The adapter reads all four after reopening. No child code runs during observation.
* **Abort task** records each run/abort handler invocation. Its run stays gated. Its abort handler commits terminal `aborted`. `abort_mark` is the durable mark, before signaling/joining the run.
* **Sleeper** commits sleeping with checkpoint `deliver` and deadline `100`; the deliver phase records one invocation and completes. Clock starts at `0`.
* **Waiter** waits with policy `allSettled` for children `C1` and `C2`; on resumption it reads their terminal outcomes and completes. Both children are owned by the waiter. Their completion is controlled independently.
* **Tool call** records each `execute` invocation, returns a durable result when released, and has a replay policy. Its intent must already be committed before the crash barrier. For the policy-change case, reopen with the changed registration. The fake effect is not assumed idempotent.
* **Submission** admits input into one conversation with a client request ID. The adapter compares returned submission identities and counts admitted records and input entries, without requiring a generated answer.

A crash after a service call but before a receipt commit can cause another service call. A first-written memo can provide a stable service key, but does not make a separate service call atomic: recording a "done" memo before an effect can lose the effect on crash; recording it after can duplicate it. Exactly-once effect in the transfer case depends on the fake service's key deduplication, not on Durable alone.

## Sources and scope

The `sources` fields point to the pinned upstream paths and named tests or sections. Primary references are [task semantics](https://github.com/earendil-works/pi/blob/827383a15262905f82e418483825a49dbb1adbf5/packages/durable/docs/spec.md#5-tasks), [submission admission](https://github.com/earendil-works/pi/blob/827383a15262905f82e418483825a49dbb1adbf5/packages/durable/docs/spec.md#6-submissions-and-inbox), [task recovery tests](https://github.com/earendil-works/pi/blob/827383a15262905f82e418483825a49dbb1adbf5/packages/durable/test/harness-tasks-recovery.test.ts), and [tool recovery](https://github.com/earendil-works/pi/blob/827383a15262905f82e418483825a49dbb1adbf5/packages/durable/docs/suspendable/spec.md). The vectors describe selected upstream behavior, not complete compatibility; no Rust runner exists yet. In particular, a clean close stops and joins invocations and writes pending records without charging a crash restart; a crash leaves a running record for recovery to count. The restart-limit vector below applies to extension tasks, not necessarily built-in generation or tool tasks, which have their own outcomes.
