# Durable の機能優先順位と残りタスク

初回統合の [PR #723](https://github.com/quantum-box/pi-rs/pull/723) に続き、途中出力の基礎を [PR #730](https://github.com/quantum-box/pi-rs/pull/730)、子ツール・文書・履歴・テキストCLIの拡張を [PR #731](https://github.com/quantum-box/pi-rs/pull/731)、テキストRPCを [PR #732](https://github.com/quantum-box/pi-rs/pull/732) で `main` に取り込んだ。この一覧は、利用時の影響と機能間の依存関係で順序をつけたもの。

## 実装の優先順位

| 順位 | 領域 | 作業と完了条件 |
| --- | --- | --- |
| 1 | チェックポイント対応ツールの途中出力 | 今回の実装で、テキストの追記、会話と個別タスクのライブ表示、出力を省略した成功時のテキスト・詳細の引き継ぎに対応。ツールごとに保持するバイト数・行数と先頭／末尾を指定できる。会話に属する親と子の確定済み途中出力も履歴ストリームで読める。成功時は、選択済みの終了フックにも途中診断を引き継ぎ、フック後の結果に保存する。フックなしの会話ルートでも途中診断を確定結果に保存する。 |
| 2 | 子ツール・サブエージェント | 会話内の親は、実行中に登録済みのチェックポイント対応の子を開始し、期限付きで結果を待てる。リプレイ不可の親が中断された場合、その実行中に起動した未完了の子は自動で再開しない。子の再接続は明示したキーによる。リプレイ不可の子が中断された場合は照合が必要になり、自動再実行を行わない。フックを選択していない親は、リプレイ可能な汎用タスクツールも呼び出せる。通常の非同期ツールも、リプレイ方針を明示して子として登録できる。途中出力のテキストと詳細を保存し、確定結果はツールの返り値を使う。通常ツールからも、登録済みの子を順序付きで呼び出せる。リプレイ可能な親は、前景サブエージェントを起動して、その応答を待てる。再起動後は同じ会話と入力を使う。UI・拡張状態との連携は後続。 |
| 3 | セッション操作 | 会話のトランザクション内で JSON または Rust の型で編集できる文書ドラフトとフォーク時の文書方針を編集し、エントリや通知とまとめて保存できる。上流と同じく、履歴へのエントリ追加を基本とする。定義付きの会話文書は、スキーマ版とフォーク方針を固定し、移行・終了・再作成を同じトランザクション内で扱える。残りは上流のエントリツリー、タスク文書の定義、保存方式と操作の組み合わせの拡張。 |
| 4 | 履歴・フォーク | 履歴は保存したカーソルから再開でき、会話の状態、アプリケーション履歴、モデル・ツールの途中出力を同じカーソルで確定順に読み出せる。フォーク先で追加した表示エントリと、作成時の由来を検証できる継承エントリを位置指定に使える。残りは未対応の位置指定と、文書操作を含めた監視。 |
| 5 | 既存CLI・TUI・RPCとの統合 | 独立した実験用 CLI で OpenAI Responses のテキスト会話を開始・再開できる。JSON モードで確定済みの途中出力を表示する。既存 CLI からは `--durable` で起動できる。テキスト RPC では入力、ストリーミング、中止、状態とメッセージの取得に対応。実行中に追加入力を永続キューに登録でき、キューの一括取り消しと配信モード設定にも対応。OpenAI Responses では画像付き入力を保存し、再開後の履歴にも画像を返せる。既存 TUI、待機中のキュー投入と他の RPC コマンドは後続。 |
| 6 | 履歴の回収 | 終了したツールの作業用途中出力は、タスク指定またはスケジューラーの保存期間設定で回収できる。自動回収は終了状態を確認してから保存期間を数え、確認結果は再起動後も保持する。別のオプトイン設定で、終了タスクの公開済みチェックポイント途中出力も本文を回収できる。通番と確定順、結果、フォークの参照は保たれる。生成中のモデル途中出力も、専用設定を有効にすると終了後に本文を回収できる。既存のインライン形式のモデル途中出力も、別の設定で同じカーソルを保って回収できる。通常ツールとチェックポイント対応ツールのインライン途中出力にも保存期間を適用できる。履歴・フォーク本体の参照関係を考慮した期限付き回収は後続。 |

途中出力の API と現在の制限は[キャンセル設計書](durable-conversation-cancel-design.md)を参照。その他の詳細は[上流互換性の一覧](pi-durable-parity.md)と[Durable の設計](pi-durable-design.md)を参照。

## 実験用テキスト CLI

`OPENAI_API_KEY` を環境に設定してから、SQLite ファイル、Responses の送信先、モデルを指定する。 `pi-rs-durable` を `pi-rs` と同じディレクトリにインストールしている場合は、下の `cargo run … --` を `pi-rs --durable` に置き換えられる。

```sh
cargo run -p pi-rs-durable --features text-cli --bin pi-rs-durable -- \
  --db durable.sqlite --endpoint https://api.openai.com/v1/responses \
  --model MODEL --json '最初のメッセージ'
```

続けるには、同じデータベースと送信先を指定し、`--model MODEL` を最初に表示された `--conversation UUID` に置き換える。同じ入力を再送する場合は同じ `--request-id` を使う。`--json` は会話 ID、保存済みのテキスト進捗、確定結果を1行ずつ出力する。

テキスト RPC は `--json` とコマンド末尾のメッセージを `--rpc` に置き換えて起動する。標準入力から1行ごとに `prompt`、`abort`、`get_state`、`get_messages` を受け取る。HTTPS または数値ループバックの HTTP で OpenAI Responses に接続する場合は、`prompt`、`steer`、`follow_up` の `images` に `type: "image"`、`mimeType`、base64 の `data` を持つ画像を追加できる。画像は送信するモデル向けに調整した状態で保存する。実行中は `steer`、`follow_up`、または `streamingBehavior` 付きの `prompt` で追加入力を積む。`clear_queue` は未処理の入力をまとめて取り消し、種別ごとのテキストを返す。確定した途中出力は `message_update` イベントで返す。生成を再試行した場合は別のアシスタントメッセージを開始し、失敗時はその試行で保存した途中出力を返す。`abort` は実行中のターンが終了してから応答する。残っているキューは次の入力が来るまで保存する。

## 運用・検証

SDK の `Scheduler::start_published_checkpointable_progress_retention` は、以後の公開済みチェックポイント途中出力を別レコードに保存する形式をデータベースに記録する。同じ終了タスクと本文を指定期間観測した後に本文を回収し、履歴には期限切れの記録を残す。形式の有効化後は対応するバイナリを使用する。再起動後にスケジューラーの回収処理を再設定すると、保存済みの期限判定を引き継ぐ。

SDK の `Scheduler::start_published_generation_retention` は、以後の生成中のモデル途中出力を期限付きの本文として別レコードに保存する。完了または中止のチェックポイントを観測してから保存期間を数え、再起動後も期限判定を引き継げる。期限切れ後も元の履歴カーソルとコミット位置で対象リクエストの期限切れを読める。生成の終了状態、最終応答、既存のインライン履歴、フォークの証拠は維持する。有効化後は対象形式を読めるバイナリを使用する。

SDK の `Scheduler::start_inline_generation_retention` は、既存形式で保存された生成中のモデル途中出力にも保存期間を適用する。各リクエストの終了確認から期間を数え、古い本文を期限切れの記録に置き換える。元の通番、コミット順、最終応答、フォークの証拠を維持する。この回収を有効にしたDBには、期限切れの形式に対応する読み手が必要になる。

SDK の `Scheduler::start_inline_tool_progress_retention` は、通常ツールの試行が完了・中止した記録、またはチェックポイント対応タスクの終了記録を確認してから、インライン途中出力に保存期間を適用する。統合履歴と試行単位の監視履歴の両方を回収し、回収後も元の位置でツールや試行の識別子を読める。最後の途中出力を含む終了チェックポイント、ツールの結果、フォーク参照は維持する。

### 実験機能の既定化判断

`experimental-graph-scope` と `experimental-graph-revision` は明示的に有効化する。合成負荷では、4,096ルートで無関係な書き込みの p95 が約45 ms、8,192ルートでは40回すべてで走査上限に達した。測定条件と現在の上限は[キャンセル設計書](durable-conversation-cancel-design.md)を参照。

- 実運用を代表するDBのコピーで、旧版から v4 への移行、再オープン、バックアップ復元を検証する。旧バイナリでの書き込み拒否と、復元時にバックアップ後の書き込みが失われる範囲も確認する。
- 代表的なグラフ規模と更新頻度で、書き込み遅延、走査上限への到達率、手動照合が必要になった件数を測る。許容値を決め、超過時の運用手順を残す。
- **完了条件**　移行・復元の手順と測定結果から、既定化するか、明示有効化を継続するかを判断し、根拠を設計書に記録する。
