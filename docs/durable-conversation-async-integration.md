# Conversation-owned checkpointable async tools: integration design

Status: an explicit replay-safe, unhooked conversation-owned checkpointable Tool path is enabled. Unsafe checkpointable tools, selected extensions, task-owned conversations and cancellation APIs for external jobs are unsupported and fail closed. Generic conversation TaskTools continue to use the existing path.

## Reference and current boundary

Compared with upstream pi durable at `9cd49d2c00ac446f774b878d25923bdb3739dadd`, especially `packages/durable/src/harness/tool.ts`: its ToolTask owns before-tool hooks, prepared arguments, execution intent, park/wake, cancellation and after-tool hooks. A parked task keeps its prepared arguments, checkpoint and replay policy; wake starts a new intent with the wake value. Recovery of an interrupted invocation requires both saved and current replay policy to be safe. A park is not a terminal outcome and does not run after-tool hooks. An abort of a parked or woken tool can invoke the upstream tool cancellation API.

Foundation `faf92f0c591bff77d5b520faf86e75b4aedc8086` has a separate conversation `TaskPending` admission and standalone checkpointable driver. It also has extension identity selection, attempt/owner fences and child admission machinery, but the standalone admission and installation guards explicitly reject conversation attachment. The private executor handoff binds an ordinary `ToolRunning` attempt, not a `TaskPending` task tree. Neither existing primitive grants permission to execute a conversation-owned async tree.

A separate `register_conversation_replay_safe_durable_tool_with_selected_hooks` registration records the ordered stable extension selection as part of the Tool definition and requires separate host attestations for the Tool and hooks. On driver attachment, a persisted pending task requires the current conversation selection to resolve to that same identity. This is registration groundwork only: both top-level and nested conversation dispatch with that selection are rejected. Hook execution, memo fencing, and hook-phase kill/reopen are not yet connected or tested.

An explicit `register_conversation_replay_safe_durable_tool` registration now constructs one unhooked, replay-safe candidate and its driver registration before opening the Harness. Attachment checks both directions against the conversation tool list, including the exact handler allocation and current spec. A fresh paired registration may be reconstructed after reopen; changed persisted task identities still reject. The Harness admits the root directly; invoking the adapter as an ordinary Tool remains rejected. The root admission atomically records an immutable binding to the conversation, tool attempt, task, definition and raw arguments. Intent and task settlement check the binding, active lease, owner chain, abort fences and conversation version. Keyed child admission is staged with the parent park or completion commit. Unsafe and hook-enabled registrations are not offered by this API.

This change strengthens the existing TaskPending boundary: scheduler attachment checks that the persisted conversation arguments equal the task's immutable input; result and abort cleanup additionally verify that input and the persisted task definition match the conversation's adapter identity. The normal-result and abort-cleanup conversation commits also check the exact task version that supplied the outcome. A competing task update causes a bounded retry after rereading the conversation, adapter identity and task; any changed task value is rejected instead of reusing a stale result. This is not an execution authorization token, an async park/child settlement fence, or a substitute for trusted storage.

## Implementation and remaining work

Steps 1–3 are partially implemented for the explicitly registered unhooked path; the remaining items specify broader parity work.

1. Add an explicit host registration for conversation async execution. Bind the exact adapter/tool version and replay attestation, permitted child definitions, and the ordered `StableExtensionSelection` (including hook identities and phase policies) to the TaskPending admission, in the same checked commit as the root task. Require an independently resolved current registration, not merely a matching stored string. Missing or old selection evidence must block this new path and request reconciliation; never backfill it from today's registry. Existing generic TaskTools retain their current format and behavior.
2. Introduce a versioned conversation task-tree binding distinct from `ToolAttempt` handoff: conversation and operation ID, root task and immutable raw input, selected tool/adapter and hook identities, each child ownership edge, task generation and active lease. Every dependent intent, memo, admission, park, outcome and settlement transaction must include checks for the conversation version, all relevant owner/abort and attempt generations, and the registration binding. Hold the conversation worker/poll fence before the task gate; do not await or dispatch under a synchronous lock. A stale or uncertain commit retires the capability; reread and reconcile instead of blindly retrying an external effect.
3. Start with one explicitly replay-safe root and replay-safe children and no selected hooks. Prepare and validate once; persist prepared arguments and a digest in the same checked intent that authorizes dispatch. Atomic park includes its durable checkpoint, child admission, wait definition and owner/attempt fences; retire the lease and release the worker only after commit. Wake binds a fresh attempt and verifies the previous committed park, prepared arguments, identity and actual wait result. Nested admission needs exactly-once keys and checked parent lineage, including ancestor abort. Unproven legacy records fail closed.
4. Next admit only explicitly replay-safe before/after hooks with a pinned ordered selection. Before-hook memo and final arguments must be committed before tool intent. After-hook work starts only after a durable raw outcome receipt and uses its own checkpoint/memo and attempt fencing. Park must retain proof without running after hooks. Hook authorization never implies the tool is replay-safe; phase-specific replay and cleanup policies remain separate. Hook failure and interrupted after work must preserve the raw receipt.
5. Add unsafe tools only after independently durable receipts and park proposals, including identifiers from pending/unknown results, are bound to the originating attempt and survive abort/settlement races. A proven committed park can resume with its saved arguments; an interrupted unparked unsafe invocation requires reconciliation. Fence parent success on unresolved unsafe descendants, including Any-wait losers. An actual cancellation API and durable cancellation results require separate design; local token cancellation is not equivalent to upstream external-job cancellation.

All and Any must preserve child identity and results through reopen; Any cannot silently discard still-running unsafe children. Parent/ancestor abort, graph changes between scan and commit, foreign or substituted registrations, changed hook ordering, uncommitted park proposals and two concurrent workers must fail closed. Durable proof must bind both checkpoint and arguments to a prior committed attempt, not merely compare two mutable copies.

## Required validation before enabling dispatch

Use the real conversation Harness and driver with network-isolated tests: public root admission, two nested parks and result propagation, All/Any, prepare exactly once across wake, before/after ordering and durable memo replay. Kill/reopen at intent, raw receipt and park commit boundaries; exercise abort and cancellation in each phase, sibling waits, graph/evidence races and unknown outcomes. Test missing/foreign identity, changed extension registrations or ordering, stale generations, conflicting writers and old-format upgrades. Require checked atomic commits and explicit reconciliation wherever evidence is insufficient. The current tests exercise two park levels, retained children, abort and kill/reopen; hook dispatch, external-job cancellation, and the remaining race and upgrade cases above are not implemented.
