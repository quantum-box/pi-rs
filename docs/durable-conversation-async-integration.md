# Conversation-owned checkpointable async tools: integration design

Status: explicitly registered replay-safe conversation-owned checkpointable Tools support either no hook or an ordered selection of identified replay-safe hooks. Unhooked unsafe checkpointable conversation task trees are supported through a separate explicit opt-in. Selected replay-safe hooks are also available for unsafe Tools through a separate explicit registration. Task-owned conversations and cancellation APIs for external jobs are unsupported and fail closed. Generic conversation TaskTools continue to use the existing path.

## Reference and current boundary

Compared with upstream pi durable at `9cd49d2c00ac446f774b878d25923bdb3739dadd`, especially `packages/durable/src/harness/tool.ts`: its ToolTask owns before-tool hooks, prepared arguments, execution intent, park/wake, cancellation and after-tool hooks. A parked task keeps its prepared arguments, checkpoint and replay policy; wake starts a new intent with the wake value. Recovery of an interrupted invocation requires both saved and current replay policy to be safe. A park is not a terminal outcome and does not run after-tool hooks. An abort of a parked or woken tool can invoke the upstream tool cancellation API.

Foundation `faf92f0c591bff77d5b520faf86e75b4aedc8086` has a separate conversation `TaskPending` admission and standalone checkpointable driver. It also has extension identity selection, attempt/owner fences and child admission machinery, but the standalone admission and installation guards explicitly reject conversation attachment. The private executor handoff binds an ordinary `ToolRunning` attempt, not a `TaskPending` task tree. Neither existing primitive grants permission to execute a conversation-owned async tree.

`register_conversation_replay_safe_durable_tool_with_selected_hooks` binds an ordered, identified hook selection into the Tool identity and requires separate host attestations for Tool and hook replay safety. The Harness must use the same live extension registration as the registration snapshot; reopen reconstructs both together. Selection changes, abort, task ancestry, attempts and memo writes are fenced at their checked commits. Before-hook rewritten arguments are checkpointed before Tool intent; Tool outcome is checkpointed before after hooks. Selected children must use the same selection. The after result reaches the parent as a rich result, and a root's after result is published directly without rerunning conversation hooks. Root publication preserves bounded ordered blocks, error status, details, structured output, attachments and diagnostics, including host-generated failures after before Block or argument validation. Malformed, non-object and oversized selected-hook input creates a fenced host failure and runs the after hook without invoking the Tool or before hook. Configured output schemas are checked on publication. Invalid structured outcomes suppress the automatic text projection, including in legacy results, while preserving unrelated hook-written content. Providers without status metadata receive a generic error marker. Because the stored result has no diagnostic-origin proof, derived failure and gate diagnostics remain in host metadata but are conservatively withheld from model text; explicit hook diagnostics with the same codes are also withheld. Multiple or non-text blocks require a durable tool-block provider adapter; without one, generation fails closed rather than dropping content. A before hook may sleep until an absolute Unix-millisecond deadline: the task persists its wait, wakes automatically, and reruns the entire before chain with the same task memo and selection checks. A committed non-abort wait resets the consecutive restart count even when its checkpoint is unchanged; invalid or conflicted waits do not. This does not authorize replay of an interrupted unsafe effect. An invalid deadline-only wait runs after hooks with invalid_park. Signal-based hook sleeps use task-scoped typed keys, with fenced wait registration, consumption, wake and signal reads. Consumed or expired keys cannot be reused; hooks inspect values or expiry with Context::read_signal. Registry publication and reopen wake gate sleeps for reevaluation; ready signals and deadlines take precedence. The saved selection is checked before hooks or Tool dispatch, and a mismatch fails closed. The hook memo and unconsumed signals survive a registry wake. Other unsupported channels remain fail closed. Existing disabled selected-hook records lacking the new selection identity are not migrated and require reconciliation.

`register_conversation_unsafe_durable_tool` separately registers an unhooked non-replayable Tool and its allowed task children. Each task and attempt uses the conversation/root binding, ownership and abort checks for intent and settlement. Joined unsafe results and Park proposals are saved independently of settlement; a checked committed park permits wake with its original prepared arguments, while interruption during execution leaves reconciliation evidence and never authorizes replay. An unsafe root result is published only with a matching attempt receipt and an evidence-prefix fence, or with atomically committed first-attempt no-dispatch evidence for preparation or schema rejection. The latter is not an external Tool receipt. Pending/Unknown results and local abort require reconciliation; external cancellation and hooks without replay-safe authorization remain unsupported. The host can read retained receipts and Park proposals but must reconcile external effects itself.

`register_conversation_unsafe_durable_tool_with_selected_hooks` separately binds the unsafe Tool, the ordered identified hook selection and each child registration. Before and after phases may replay only with their phase evidence; Tool execution itself never becomes replay-safe. A versioned rich after-final record binds the final content to the raw unsafe receipt, after checkpoint and finishing attempt. It is checked and fenced before a child or the conversation can consume it. Interruption during Tool execution and Pending/Unknown results require reconciliation; the raw receipt remains available. Abort fences hook memo and final publication. Before Block, preparation/schema errors and malformed raw input may run after hooks when a no-dispatch proof is committed with the before checkpoint or root admission. It binds owner, task definition, input digest, checkpoint and before attempt; the same transaction checks that the unsafe evidence prefix is empty. After execution, recovery, child reads and conversation publication recheck that proof and fence the entire prefix. Unsafe initial before-hook execution and each memo access also fence an empty evidence prefix. If the after hook fails after a proved host rejection, an owning parent receives the known failure as AfterIncomplete; it is evidence and not a finalized result. A validated version-3 final marker distinguishes a later failure from an incomplete hook. Any prior intent or conflicting evidence requires reconciliation. This assumes the store and direct writers preserve append-only unsafe execution evidence; deleting earlier intent records defeats that proof. External cancel and unsafe hook side effects are not provided; hooks require explicit replay-safe authorization.

An explicit `register_conversation_replay_safe_durable_tool` registration now constructs one unhooked, replay-safe candidate and its driver registration before opening the Harness. Attachment checks both directions against the conversation tool list, including the exact handler allocation and current spec. A fresh paired registration may be reconstructed after reopen; changed persisted task identities still reject. The Harness admits the root directly; invoking the adapter as an ordinary Tool remains rejected. The root admission atomically records an immutable binding to the conversation, tool attempt, task, definition and raw arguments. Intent and task settlement check the binding, active lease, owner chain, abort fences and conversation version. Keyed child admission is staged with the parent park or completion commit. Unsafe and hook-enabled registrations are not offered by this API.

For an unhooked conversation Tool, whether replay-safe or unsafe, a first-attempt preparation error or invalid prepared value becomes a bounded known Tool failure only when the current intent is the sole recorded intent for the task, the restart count is zero, and an intent-prefix fence commits with the result. Any prior intent or interrupted/recovered attempt preserves uncertainty instead. Intent records are retained by the runtime; stores and direct writers must preserve that append-only evidence. Selected-hook execution is available only through the separate explicit replay-safe registration above.

This change strengthens the existing TaskPending boundary: scheduler attachment checks that the persisted conversation arguments equal the task's immutable input; result and abort cleanup additionally verify that input and the persisted task definition match the conversation's adapter identity. The normal-result and abort-cleanup conversation commits also check the exact task version that supplied the outcome. A competing task update causes a bounded retry after rereading the conversation, adapter identity and task; any changed task value is rejected instead of reusing a stale result. This is not an execution authorization token, an async park/child settlement fence, or a substitute for trusted storage.

## Implementation and remaining work

Steps 1–3 are partially implemented for the explicitly registered unhooked path; the remaining items specify broader parity work.

1. Add an explicit host registration for conversation async execution. Bind the exact adapter/tool version and replay attestation, permitted child definitions, and the ordered `StableExtensionSelection` (including hook identities and phase policies) to the TaskPending admission, in the same checked commit as the root task. Require an independently resolved current registration, not merely a matching stored string. Missing or old selection evidence must block this new path and request reconciliation; never backfill it from today's registry. Existing generic TaskTools retain their current format and behavior.
2. Introduce a versioned conversation task-tree binding distinct from `ToolAttempt` handoff: conversation and operation ID, root task and immutable raw input, selected tool/adapter and hook identities, each child ownership edge, task generation and active lease. Every dependent intent, memo, admission, park, outcome and settlement transaction must include checks for the conversation version, all relevant owner/abort and attempt generations, and the registration binding. Hold the conversation worker/poll fence before the task gate; do not await or dispatch under a synchronous lock. A stale or uncertain commit retires the capability; reread and reconcile instead of blindly retrying an external effect.
3. Start with one explicitly replay-safe root and replay-safe children and no selected hooks. Prepare and validate once; persist prepared arguments and a digest in the same checked intent that authorizes dispatch. Atomic park includes its durable checkpoint, child admission, wait definition and owner/attempt fences; retire the lease and release the worker only after commit. Wake binds a fresh attempt and verifies the previous committed park, prepared arguments, identity and actual wait result. Nested admission needs exactly-once keys and checked parent lineage, including ancestor abort. Unproven legacy records fail closed.
4. Next admit only explicitly replay-safe before/after hooks with a pinned ordered selection. Before-hook memo and final arguments must be committed before tool intent. After-hook work starts only after a durable raw outcome receipt and uses its own checkpoint/memo and attempt fencing. Park must retain proof without running after hooks. Hook authorization never implies the tool is replay-safe; phase-specific replay and cleanup policies remain separate. Hook failure and interrupted after work must preserve the raw receipt.
5. Extend the unhooked unsafe path to selected hooks and external cancellation only after independently durable receipts and park proposals, including identifiers from pending/unknown results, are bound to the originating attempt and survive abort/settlement races. A proven committed park can resume with its saved arguments; an interrupted unparked unsafe invocation requires reconciliation. Fence parent success on unresolved unsafe descendants, including Any-wait losers. An actual cancellation API and durable cancellation results require separate design; local token cancellation is not equivalent to upstream external-job cancellation.

All and Any must preserve child identity and results through reopen; Any cannot silently discard still-running unsafe children. Parent/ancestor abort, graph changes between scan and commit, foreign or substituted registrations, changed hook ordering, uncommitted park proposals and two concurrent workers must fail closed. Durable proof must bind both checkpoint and arguments to a prior committed attempt, not merely compare two mutable copies.

## Required validation before enabling dispatch

Use the real conversation Harness and driver with network-isolated tests: public root admission, two nested parks and result propagation, All/Any, prepare exactly once across wake, before/after ordering and durable memo replay. Kill/reopen at intent, raw receipt and park commit boundaries; exercise abort and cancellation in each phase, sibling waits, graph/evidence races and unknown outcomes. Test missing/foreign identity, changed extension registrations or ordering, stale generations, conflicting writers and old-format upgrades. Require checked atomic commits and explicit reconciliation wherever evidence is insufficient. The current tests exercise selected before/after hooks, two park levels, retained children, abort, selection and memo fences, and kill/reopen. External-job cancellation, multiple selected hooks and the remaining race and upgrade cases above are not implemented.

The test `restart_after_waits_for_owned_child_abort_cleanup` gates its fast sibling until the grandchild has entered execution; this stabilizes its cleanup-order scenario. It does not establish liveness when Any wakes before the slow child admits its descendant.

## Synchronous task settlement under contention

A synchronous `Scheduler::tick` retains the completed invocation, its exclusive
lease and any prepared candidate when a checked settlement cannot start because
another SQLite writer holds the lock. It returns `Error::Busy`; the host must
call `tick` again after contention or a relevant ownership change. Each retry
rechecks the task, attempt, abort and ownership/evidence fences before committing.
Other synchronous ticks cannot reserve independent work while that lease remains
pending; the concurrent driver is available when independent progress is needed.
The retained outcome is in memory: after process loss, existing durable evidence
and unsafe interruption reconciliation still govern recovery.

A caller using `settle_invocation` directly owns any `Pending` or
`PendingPrepared` result and must use `try_resume_pending` (and, when required,
checked cleanup) rather than rerunning the handler. `take_serial_pending` can
transfer an outcome retained by `tick`. It does not make an indeterminate commit
safe to retry: storage errors after a transaction starts remain fail-closed and
require reconciliation, including when an unsafe Tool may have external effects.
A pending synchronous outcome is transferred to the concurrent driver when the
scheduler is handed to it. An indeterminate retained outcome stops that driver
and remains available for reconciliation instead of being retried.

## Owned conversation cleanup concurrency

The concurrent task driver schedules marked owned conversations independently;
it does not impose the synchronous cleanup tick's eight-worker limit. This
keeps an unrelated graph runnable while another cleanup callback is stalled,
consistent with upstream's per-task scheduling and bottom-up abort ordering.
The synchronous cleanup tick has eight slots and releases them as individual
workers finish; one graph finishing does not imply that every other timeout has
already been collected.

pi-rs bounds abort-time usage reporting at 120 seconds. If that callback times
out after the durable cleanup marker was written, the marker and abort state
remain for explicit reconciliation before another attempt. This timeout and
marker protocol are pi-rs safety behavior; they do not establish that an
external callback had no effects.
