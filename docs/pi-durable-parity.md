**Task-backed multi-level waits:** A model-issued `TaskTool` can own a keyed
`TaskTool::start_child` task whose handler starts another, independently owned

child. Admission and the parent checkpoint/wait commit atomically; each wake
reports ended direct children and keyed calls can reconnect to the same child.
`WaitFor::Tasks` waits for all named children and `TasksAny` wakes on any.
The latter does not abort the remaining children: if a parent wakes while another child
is admitting a descendant, conflicting graph observations are retried for a
replay-safe child; an unsafe child remains subject to outcome reconciliation.
This is a synchronous registered-task-handler API: nested children run task handlers,
not the ordinary asynchronous `Tool` invocation or its nested tool-hook pipeline.
It is separate from `KeyedHost` multi-level nested calls and does not establish
parity with upstream `executeTool(..., { wait: false })` or its tool API.

Conversation-owned checkpointable asynchronous tools support explicitly registered replay-safe task trees and an ordered selection of identified replay-safe before/after hooks, with checked intent, ownership, memo and park settlement. Before-hook sleeps support deadlines and task-scoped typed signals, survive restart and rerun the whole hook chain with durable memo. Registry publications and reopen wake gate sleeps for reevaluation; the saved selection remains fenced and a mismatch blocks dispatch. Selected root after results retain bounded ordered content blocks, error status, details, structured output, attachments and diagnostics in the conversation. A provider that accepts durable tool blocks is required for multiple or non-text blocks; otherwise generation fails closed. Schema-invalid structured results suppress automatic text projection while preserving unrelated hook-written content. Providers without status metadata receive a generic error marker. A committed non-abort wait resets the consecutive restart count even when its checkpoint is unchanged; invalid or conflicted waits do not. This does not authorize replay of an interrupted unsafe effect. Normal conversation after hooks are not repeated. The separate `register_conversation_unsafe_durable_tool` opt-in supports unhooked conversation-owned unsafe checkpointable task trees, including mixed safe/unsafe children. A committed park and its proof authorize wake; interruption during execution remains uncertain and is not replayed. Joined outcomes, pending references and park proposals remain available as reconciliation evidence even if abort wins. Conversation success requires the final unsafe receipt and fences its evidence; abort remains blocked for reconciliation when effects may be unknown. A separate selected-hook registration supports explicitly replay-safe hooks with unsafe Tools and preserves a checked rich after result. Host-generated pre-dispatch errors, including before Block, preparation/schema errors and malformed input, run after hooks only when a transaction proves the task's unsafe evidence prefix was empty and binds the error checkpoint. Earlier or conflicting execution evidence requires reconciliation; the host must preserve append-only intent records. External-job cancellation remains unsupported. The existing TaskPending boundary now checks the admitted input and task definition on attachment and outcome reading; see the [integration design](durable-conversation-async-integration.md) for the additional authorization, fencing and recovery work required before enabling dispatch.

**Foreground task ancestry:** Task reservation and wake checks follow task ownership across foreground conversation edges. Interrupted or incompatible running ancestors, failure, and abort fence descendant execution; background edges remain independent. Successfully completed task anchors, including their task-owner chain, remain traversable for work later admitted in an owned conversation; failed and cancelled anchors block it. Invalid foreground ownership chains fail closed. A background task forms a boundary before its owning conversation’s abort mark; its foreground descendants remain runnable unless the task itself is aborted. Held TaskTool failures mark and drain foreground-owned work, including generic tasks in owned conversations, before the failure becomes terminal.
**Run failure increment:** Runs ending without an answer persist their running submission IDs, a classified reason and optional detail in `Conversation.run_failure`. Model errors, abort, reset, turn limit, nothing to answer, and model restart limit are classified at their settlement sites; submission status reason strings remain unchanged. A later run clears the failure. A reset or `afterFailedRun::Continue` replacement run retains it, including across reopen. When no reset, independent summary, or unplaced write is pending, the replacement starts atomically in the failure commit. Otherwise selection remains deferred until the ordered work is placed; in that gap a new continue is rejected as busy, but the selected input is still withdrawable and abort and late steering can differ from upstream. Existing persisted records from before classification retain their original reason string and have no detail. Upstream task IDs, `first` lineage, other failure sources, and exact upstream interruption phase wording remain unsupported.

**Nested pending identity gap:** Existing pending nested jobs persist a tool name, replay policy and opaque reference, but no implementation or tenant identity. A host must restore the original child configuration and tenant before polling; a same-named tool pointed at a different backend can otherwise associate the wrong remote result with the recorded operation. Reconciliation is required when that identity cannot be established.

**Queued input abort policy:** `AdmissionOptions::on_abort` defaults to `Withdraw`; `OnAbort::Keep` preserves a queued input through conversation aborts and ownership cascades, including recovery. Explicit submission withdrawal still removes it, and failed runs use `AfterFailedRun` independently. A later input or ordered write resumes placement. Abort marks record which inputs they retained, so cleanup and conflict retries distinguish them from later admissions after reopening; a repeated abort establishes a new boundary. An abort already in progress in a store written before this boundary was recorded cannot distinguish its retained inputs from later admissions and may resume them during cleanup. The Rust runtime stores the policy on its persisted submission rather than an upstream inbox item. See [upstream change e67aa1a4e](https://github.com/earendil-works/pi/commit/e67aa1a4e5faa33d4a3144f31a16fcda68ffc0db).

Runnable work and abort cleanup still hold the owner. Background ownership edges remain boundaries.

**Nested pending identity boundary:** Identity-bound nested jobs validate a host-declared implementation and tenant identity before polling and unsafe resume. Legacy unbound replay-safe jobs remain pollable for compatibility; their host must restore the original child configuration and tenant because those records cannot establish that identity. Unsafe legacy proofs without a parent identity require reconciliation. Identity declarations and updates are host responsibilities.

**Task driver concurrency:** The attached generic task driver reserves work through a coordinator and runs up to four ordinary synchronous handlers concurrently, with one additional reserved worker for a direct generic child of a live TaskTool when those slots are full. Unrelated work cannot use the reserved worker. A blocking generic child can occupy it, and the fixed bound does not guarantee progress for arbitrary recursively blocking handlers; handlers must be cooperative. It fences dependent task admission and settlement against published failure outcomes, and drains foreground ownership before finalizing task outcomes. Hook-created children retain their completed hook result while a related outcome settles. Unrelated work can progress while a handler is blocked, subject to the fixed worker bounds. Synchronous handlers must still return for their own cleanup and shutdown; the worker limit and host-facing `TaskPublicationBusy` retry differ from upstream. See [task driver](../crates/durable/src/task_driver.rs) and [process recovery tests](../crates/durable/tests/process_recovery.rs).

**Uncertain ownership recovery:** A failed owner with a damaged ownership graph remains parked on attachment; interrupted descendants whose ancestry cannot be ruled out remain unrecovered. Completed in-flight descendant outcomes retain their leases and are revalidated after repair, before their effects can settle. Shutdown returns such outcomes for explicit reconciliation rather than waiting indefinitely for graph repair. Independent work can continue when its separation from published outcomes is provable. If a damaged edge prevents that proof, scheduling remains conservative until the edge is repaired; opaque damage can affect more than one graph.

**Completing outcome checkpoint:** A generic task that succeeds or fails while ordinary owned work is live retains its outcome and remains live until a later scheduler tick observes the foreground ownership graph drained. A held failure initiates a durable abort cascade before the task scheduler dispatches another child; independently scheduled conversations can continue until the cascade commits. Its outcome survives restart, including an OS kill after the hold commit; [process tests](../crates/durable/tests/process_recovery.rs) cover success and failure. The success transaction includes staged keyed children and document writes; an active owned conversation or work started later in it also holds the task, even without generic child tasks. A graph-wide put fence protects the hold and finalization against concurrent admissions, and reopening does not require the held parent's definition. This fence tracks supported store puts; delete-only and raw SQLite writes are outside it, and ownership edges must remain immutable. Abort marks the held record without changing its outcome; the harness abort path cascades through owned conversations, while standalone task drivers require an attached conversation runtime for foreground-conversation aborts. Direct new children of a completing task are rejected. Background tasks and background conversation edges remain boundaries. Explicitly acquired task documents are retained at hold and retired in the terminal task transaction, including abort and failure. Exact document-key ownership metadata in a separate SQLite table is checked by the store for raw and checked writes; unregistered addresses and arbitrary byte keys retain their existing behavior. Task candidates and explicit legacy migration use the same persisted task schema as `TaskStore`, rejecting malformed records atomically. Only affected owners are validated, so corruption does not block unrelated commits; mutations involving a corrupt owner fail closed and preexisting corruption is not automatically repaired. Experimental byte-key ownership records require explicit migration with all old writers stopped. A task-document pull watch delivers a retirement with its last value and ends after the terminal commit, including after cursor resume. This is a partial API, not upstream token or listener parity; ownership metadata is permanent, acquiring an existing unowned document is rejected, and the implementation scans ownership metadata during commits. Generic low-level task creation still has legacy behavior for already-terminal or abort-marked owners outside the new completing check. Failure settlement retries bounded conflicts caused by concurrent graph puts; persistent contention or a changed parent version is still surfaced. Unlike upstream, cascade and finalization occur on later driven ticks rather than after every commit. See [upstream structured concurrency](https://github.com/earendil-works/pi/blob/04fd0897e4df737cd8422bc99085d6953da804ec/packages/durable/docs/spec.md#55-structured-concurrency).

**Concurrent task admission checkpoint:** Owned-subagent admission and the post-handler graph decision share a task gate. If admission rewrites the running task unchanged while its handler runs, the scheduler retains the handler result and rebases its reservation checks, including staged keyed-child checks. An abort still fences the result, and changed task records are not accepted. Other document and graph checks remain in force. This uses optimistic storage checks rather than upstream's Session mutation line.

**Incremental watch operations checkpoint:** Opt-in merged and document watch APIs derive bounded top-level Chord sets, deletes and array-append splices from validated predecessor states. They fall back to root replacement for unsafe paths, unproven predecessors or non-beneficial/large deltas. These are state-derived operations, not upstream's original operation batches; progress remains whole-state data.

**Merged source lifetime checkpoint:** Merged pull watches and listeners automatically end after the last source-capable harness, worker and active progress callback releases its lease. They drain through the captured final commit boundary; a listener acknowledges an in-flight callback before draining. Read-only watch clones do not extend source lifetime, and detached raw store writers are outside it. Explicit host close remains an immediate separate signal.

**Merged listener checkpoint:** A merged watch can be transferred to a serialized callback driver with acknowledged-page cursors and explicit stop, abort and host-attested source-close reasons. In-flight callbacks are awaited; errors, panics or dropped runs leave the page available for replay. It does not provide upstream's background delivery, listener context or recoverable error frames.

**Merged watch lifecycle checkpoint:** `watch_merged_progress_handle` wraps existing v1/v2 merged cursors in a bounded pull handle with first-wins stop, abort and read-failure reasons. It resumes after reopen and retains the existing forward-only progress/document boundaries. Terminal progress is a frame, not a watch end; the separate callback driver supports host-attested source closure, and source-capable lease exhaustion now supplies an automatic drained end.

**Merged progress watch checkpoint:** A versioned from-now cursor merges proven runtime conversation observations and tracked forward-only progress by database commit sequence, preserving each atomic transaction as one paged frame across reopen. Previously overwritten progress remains outside this stream; frames contain whole replacements rather than upstream's windowed Chord diffs. Version 2 adds future conversation-scoped application-document states and deletions using an atomic revision-to-store-commit mapping, while version 1 cursors keep their original behavior. Document scope is a host convention. Oversized or untracked document commits fail closed; earlier mappings are not backfilled.

**Forward progress history checkpoint:** Runtime generation and tool progress checkpoints and terminal seals append bounded replacement-state records atomically with their existing writes. Versioned conversation-scoped cursors capture an explicit from-now boundary and resume paged polling after reopen. This does not backfill overwritten progress or cover standalone writers, streamed output or uncommitted provider deltas; it is not an upstream Chord delta stream.

**Committed view stream checkpoint:** `watch_committed_view` replays each tracked runtime conversation observation as a root-replacement frame from a conversation-scoped exclusive cursor, with explicit stop, abort and failure reasons. It validates that each observation and corresponding runtime fork snapshot share a tracked transaction, and fails closed on unproven history. The stream covers committed observer snapshots, not progress-only, application-document or other unlogged commits, and is not upstream's full windowed view or fine-grained operation stream.

**Document operation and watch-end checkpoint:** Document watches can page one synthesized Chord root replacement per committed put and a retirement frame per delete, with exclusive cursors that survive reopen. These represent final states, not original mutation operations; retirement exposes no previous value. Pull view watches expose first-wins stopped, aborted, and source-failure reasons, without upstream's listener lifecycle or automatic source-close notification.

**Ordered-block reset checkpoint:** `reset_with_blocks` admits a reset and ordered block occurrences together, placing the optional text handoff before the blocks and preserving their IDs through queued placement, reopen, and abort cleanup. Multiple queued resets are committed in admission order using separate transitions where necessary, preserving each intermediate block occurrence across reopen and abort. Queued user inputs are placed after the resets at the boundary, matching upstream write-before-input ordering. This explicit block-reset operation is a pi-rs extension to upstream’s text-handoff reset. A busy independent summary whose placement checkpoint follows multiple queued block resets settles stale after those resets are committed; their intermediate occurrence history survives reopen, including abort cleanup.

**Ordered-block interior fork checkpoint:** Proven state-stable interior cuts of ordered-block batches preserve the retained occurrence IDs, provenance, and exact ordered blocks through an immutable-source-linked child projection. This also covers a cut before the first retained block. Reopen checks the projection against its source batch and document cut. Legacy or unproven occurrence histories, incomplete tool batches, and unsafe cuts fail closed; this remains narrower than upstream entry-level forks.

**Task application-entry fork checkpoint:** `fork_at_application_entry` supports bounded local and proven inherited application-entry cuts. It truncates the application log inclusively, copies documents at the end of the entry commit, and uses a verified earlier runtime snapshot, all in the child creation transaction. Inherited cuts require an atomic immediate-parent lineage record at each fork and verify each copied prefix against that parent’s fenced history; older inherited forks without this evidence fail closed; historical documents come from the owner and current-policy documents from the immediate parent. A task can explicitly checkpoint unchanged runtime state between its staged application entries; its atomic order proof permits same-commit forks, with end-of-commit document state. An ordered task checkpoint may also atomically change an idle conversation’s model configuration; both sides inherit the final configuration while retaining their exact application-entry prefix. Untracked or ambiguous history and other state-changing runtime writes in the entry commit fail closed. This remains separate from upstream's unified entry history and general inherited entry forks.

**Display-write fork checkpoint:** `fork_by_display_entry_id` selects a locally placed display write when authenticated consecutive runtime observations prove an ordered append-only batch of placed writes and no other visible runtime change. The fork uses that commit's document revision and includes the placed writes through the selected write; notifications and live work are not copied. A bounded scan authenticates at most 256 observations and fences the inspected evidence and parent version through creation. The cut rejects legacy tracking, unplaced or withdrawn writes, queued-write histories, mixed runtime transitions, task application-log changes between the observations, and inherited display prefixes without lineage proof. A descendant with an empty display history can fork its own qualifying writes. This is narrower than upstream's arbitrary visible-entry forks, including inherited entries and mixed runtime transitions.

Display forks also validate reset and occurrence provenance for text-only contexts, and fence the visited transcript records and reset evidence through child publication. Transcript traversal remains unbounded in record count; each transcript, conversation, fork snapshot, observer, application-history, and pending tool-result record read during a display fork, including initial hydration and reset validation, is limited to 8 MiB before deserialization. Observer keys are bounded and scans hold at most one record and one lookahead. Document copying reads only the relevant scopes, with an 8 MiB aggregate key-and-value limit per historical or current document or policy scan. Oversized records fail closed. Chunked reset manifests authenticate each chunk's commit before accumulation and can exceed 8 MiB. Other transcript, fork, and reset operations retain their existing limits; runtime and transcript namespaces remain reserved and exclusive.

This is a fail-closed subset: valid conversations with a root or historical snapshot over 8 MiB, including large-reset histories, cannot use display-entry forks. Ordinary occurrence-based forks retain their large-reset support.

Chunked reset proof lookup authenticates the root, anchor, observer, document fence and transcript entries before reading chunks. Assembly is limited to 8 MiB plus 512 bytes per reset, bounded also by the authenticated transcript sequence; normal writer-produced manifests above 8 MiB remain supported.

**Host session transaction slice:** `Harness::session_transaction` and `Scheduler::session_transaction` synchronously stage display-only conversation application entries and JSON-object document replacements/deletions in the same checked runtime commit. It can also admit one input, continue or application write, including a settlement notification, before the first table write; immediate write settlement and its signal are committed with the staged entries and documents. Queued input/write and continue retain their notification for later settlement. `session_transaction_async` additionally supports ordered text/image block input via `tx.submit_fitted_user_blocks`, using the selected block-aware adapter and model image limits. The callback runs once; fitting and the staged document/entry/notification commit are fenced by the conversation version, and the adapter profile is checked after fitting and immediately before commit. The async callback must return a boxed future; callers can move owned or shared fitting dependencies into it. The callback sees its own document writes and is never replayed. Scoped conversation, application-write, submission and directly owned task reads must precede the first table write; directly owned ready tasks can be created with a running driver and matching registration. Each transaction targets one existing conversation. Document reads share one revision and remain fenced against create/delete cycles; the conversation version fences concurrent admissions and abort. Callback failure or conflict commits nothing. Entry IDs are provisional until commit. A read-only transaction validates its snapshot without publishing a new observation. Appending is rejected while a reset, independent summary or earlier application write is pending. See [session transaction tests](../crates/durable/tests/session_transaction.rs).

This is narrower than upstream [9cd49d2c §4](https://github.com/earendil-works/pi/blob/9cd49d2c/packages/durable/docs/spec.md): entries use pi-rs `ApplicationWrite` records with UUIDs and are visible as placed write submissions; no upstream entry tree, head field, arbitrary table writes, unfitted block-input admission, typed Chord drafts or document lifecycle is provided. Session transactions also stage keyed or unkeyed registered children of multiple exact running generic or TaskTool parent attempts, together with new conversation-owned root tasks. `create_child_of_staged_task` and `create_keyed_child_of_staged_task` admit descendants of tasks created earlier in that transaction. The combined candidate graph is checked for ownership and wait cycles and committed with documents, entries and settlement signals. New children require canonical fresh lifecycle fields. A prior scoped task or signal read that found the ID missing keeps an exact-key ABA fence when the child is created. They use the existing keyed-child journal and preserve its identity checks (including replay policy, version, checkpoint and restart limit in addition to kind and input, stricter than upstream); the task driver validates registration and serializes graph admission with finalization, checks pending abort, and applies a graph-prefix fence. Parent snapshots and pending abort are validated independently under the driver gate; keyed identity is scoped to each parent. Staged parents do not yet have an executor attempt, while their fresh task creation and ownership are checked in the same batch. This slice admits generic children of running TaskTool parents and in task-owned conversations. Under the task gate and failure-publication ledger, admission validates the complete task/conversation ownership chain, fences task and edge versions, conversation versions and foreground abort fences, and checks pending aborts; successful task ancestors remain valid anchors throughout the chain. Foreground cancellation stops at a background boundary, while structural ownership is still checked beyond it. The checks commit atomically with entries, documents and notifications. Interrupted attempts must recover before descendants execute. Creation of TaskTool children through this host API remains unsupported; upstream permits broader ownership. Generic children can execute concurrently with a live TaskTool parent; interrupted parents must recover before descendants execute. Successful settlement waits for owned work, while failure and explicit abort cascade through it. The separate ordinary nested-tool key journal is not unified with the keyed-child journal, so shared cross-kind key semantics remain unsupported. Cross-conversation creation and upstream definition initializers are also unsupported. See [session child tests](../crates/durable/tests/session_child_creation.rs) and [TaskTool parent tests](../crates/durable/tests/session_task_tool_parent.rs). Multiple pending block resets requiring separate commits are rejected for transactional continue. Admission after a table write, including a duplicate lookup, returns `ReadAfterWrite`; a duplicate encountered before a table write returns its original ID and keeps its original notification. `entries()` preserves the pi-rs staged-entry preview; `checked_entries()` enforces the read-before-write rule. A task observed missing by a signal can be created later in the transaction, with an ABA-aware absence fence. Task scans, cross-conversation access, general task updates and raw submission settlement remain unsupported. Document addresses use existing pi-rs scope conventions. Both synchronous and asynchronous session callbacks can call `tx.signal` with a typed token before the first table write. Delivery and deadline expiry mark a table write, so another explicit signal or admission then returns `ReadAfterWrite`; no-op duplicate, invalid, closed-target and not-found results retain their checks and permit subsequent admission. Documents and entry appends can follow. Internal settlement notifications assemble against the candidate signal and task overlay after all other writes, while retaining the original signal and deadline checks. Results remain provisional until commit. Concurrent `Promise.all`-style signal calls are not exposed by this synchronous Rust method. See [session signal tests](../crates/durable/tests/session_signal_transaction.rs). Profile checks cannot atomically fence changes inside externally mutable host adapter state; adapters should keep profiles stable during admission, as with the standalone fitted-input API.

**Checked task application-entry append:** `TaskDocuments::append_entry_if_head` stages an application record only when the last committed or locally staged application-record ID matches the caller's expectation (or the log is empty). The observed log remains a transaction read dependency even when the check fails, so a concurrent log change conflicts with the whole task transaction, including document writes. This is a pi-rs optimistic precondition on its separate task log; upstream [`tx.appendEntry`](https://github.com/earendil-works/pi/blob/main/packages/durable/src/session/transaction.ts) appends to the conversation entry stream, and its optional `head` is an entry field, not this precondition. The Rust API does not add general session transactions or upstream entry-tree semantics.

**Ownership abort recovery and CAS checkpoint:** Repeated conversation and standalone task aborts check the versions of all reached tasks, including already-marked or terminal tasks, without rewriting unchanged records; a conflicting owner-version update retries the traversal. After reopen, the task driver discovers an independently aborted owned conversation while its task owner remains live, across either edge mode; ordinary abort still respects background boundaries. Discovery uses one storage snapshot, ignores unrelated unmarked corrupt edges, and reports a marked child's missing or mismatched owner without clearing its abort mark. Abort also advances separate persisted ownership fence keys for each reached task and conversation, without changing task reservation versions. Low-level task-creation and ownership-edge batches prepared by this version check the applicable owner-chain fences, so a batch prepared before the abort conflicts if committed afterward; ordinary abort leaves background boundaries independent. Before traversal, abort records the store's put version and atomically checks that neither task nor ownership-edge namespace received a put after that boundary. A low-level creation committed after the scan therefore forces a complete retry without changing its batch or requiring it to advance an owner version. This prefix-wide check is conservative: unrelated task or edge puts can also cause retries, and sustained concurrent writes can delay abort. Successful `Store::commit` puts are tracked even if subsequently deleted; delete-only operations and direct SQLite writes are outside this prefix check, while visited record versions still fence their deletion. Batches prepared by older implementations and raw commits may omit the separate post-abort owner-fence checks, and low-level task creation newly prepared after abort is not an admission check; those writers require external fencing. A direct abort of an already-terminal task is still rejected; aborting its owning conversation can traverse terminal anchors. Upstream [ownership and abort](https://github.com/earendil-works/pi/blob/main/packages/durable/README.md#abort-and-subagents) models a tree and has no corresponding low-level legacy-cycle recovery contract. See `runtime_cas_tests`, `task_scheduler`, and `owned_subagent` tests.

**Ownership cycle checkpoint:** Task creation checks staged and persisted task and conversation ownership, including background edges, and fences missing owners against concurrent creation. This protects child-first abort cleanup; legacy corrupt cycles are not repaired. Cleanup waits for active descendants outside a cycle, then deterministically relaxes cyclic task-to-conversation waits and orders task-only cycles by task ID. Idle waits include persisted abort marks. Document transactions reject ownership insertions that overlap another component's missing-owner check. Raw `Store::commit` evaluates checks before writes and loses preparation boundaries; separately prepared ownership changes can therefore form cycles when concatenated, and remain the caller's responsibility. Jointly prepared task creations validate their staged graph. The document composition guard is conservative and may reject acyclic cross-component overlaps. Upstream models tasks and conversations as one ownership tree and drains owned work before its owner; pi-rs retains lower-level preparation APIs.

**Unified history checkpoint:** `Harness::unified_history_start` captures a finite store commit boundary and `unified_history` pages complete commit frames in sequence order (1–255 frames per page). Frames expose expanded runtime observation snapshots and full task application-log snapshots, including inherited records at a fork's own commit. They do not reconstruct parent commit history for a fork, per-entry order within one commit, or upstream's immutable transcript entry semantics. A snapshot can repeat earlier messages and application entries; task entries are not model context. On a store with any pre-tracking versions, the default start fails closed; explicitly accepting the migration boundary reads only tracked commits and does not reconstruct earlier ordering. Cursors are trusted, database-local, serializable host data; pages capture a fixed upper boundary and can resume after reopen. Sequence gaps include unrelated commits. Frames and values may be large; SQL work, expanded transcript traversal and application-log snapshots are not bounded by the page count. Raw namespace mutation/deletion, old writers and cross-database cursors invalidate guarantees. Existing history and application APIs are unchanged. See [tests](../crates/durable/tests/features.rs) and [upstream entries](https://github.com/earendil-works/pi/blob/main/packages/durable/README.md#concepts).

# Pi Durable compatibility inventory

**Current status:** This branch's experimental runtime supports durable execution and recovery, task scheduling, transactional admission and task document/application-entry commits, typed task-scoped signals, managed background anchors, keyed nested tools, document fork policies (`Copy`, `Initial`, and `Current`), and commit-ordered unified history snapshots. Generic-task wake hints and extension-error report subscriptions are available, as are opt-in provider and local coding-tool adapters. These are partial implementations with distinct contracts, not full upstream parity. Principal gaps include the remainder of general session transactions and Chord watches, arbitrary entry-ID forks and immutable entry history, complete ownership lifecycle and cycle prevention, full tool progress semantics, upstream wake/report coverage, and automatic integration with existing provider clients and the CLI. External effects and replayed hooks still require idempotency or reconciliation. The priority table is the current inventory; the checkpoints below are historical and may describe limitations since addressed.

Checkpoint descriptions record historical stages and can contain superseded limitations; use the current status and priority table for this revision.

**Extension callback panic reporting:** Section and hook panics while constructing or polling their futures are contained and recorded in the extension report log. Before-tool panics block tool dispatch; other phases retain their existing failure handling. The first report batch per operation and phase wins, and unacknowledged deliveries replay after reopen. [Upstream](https://github.com/earendil-works/pi/blob/c1d4b0ac3e35dc4eb1c5d00d90bf54003cf517c0/packages/durable/src/types.ts) reports thrown section and hook errors through `onReport`; Rust normalizes panic payloads to `extension panicked` and still does not cover the full upstream report taxonomy, including most tool execution failures.

**Tool execution panic report:** A caught model-issued tool panic produces a fixed redacted runtime report before waiting for nested calls; its committed identity prevents replay if a restart precedes the blocked phase. Resuming or reconciling repairs a missing report for a persisted blocked phase, with deduplication by operation ID. A crash before the report commits remains indistinguishable from interrupted dispatch. Upstream instead converts an execute throw to a tool error result and reports tool cleanup and invalid structured-output errors; those cases are not implemented here. Nested panics are also outside this report coverage.

**Extension report subscription:** `Harness` and `Scheduler` expose a bounded,
pull-based subscription and opt-in asynchronous dispatcher over persisted extension
error batches, with host-managed cursors and replay after reopening. Unlike upstream
`onReport`, the dispatcher delivers batches after commit, stops on listener failure,
and requires explicit awaited shutdown and checkpointing; it does not cover the
complete upstream report taxonomy; see the
[delivery guarantees](../crates/durable/README.md#extension-error-observation).


**Opt-in OpenAI Responses adapter:** The standalone [durable-openai crate](../crates/durable-openai/README.md) prepares, validates, and dispatches post-hook API-key Responses requests, with bounded SSE parsing and replay. It rejects final tool items at inconsistent output indices and tool items with empty arguments or an explicit unfinished status in completed responses. **Observer reconnect checkpoint:** The standalone observer can capture `head`
and use `read_through` to replay complete logged records through that fixed
cursor in bounded pages, then hand off to `watch` at the last processed cursor.
Later appends do not extend the catch-up, and the boundary can be reused after
reopening. This does not atomically attach a conversation or document view,
produce Chord operations, or include changes absent from the observer log; record
bytes and retained history are unbounded. Compare upstream's [watch contract](https://github.com/earendil-works/pi/blob/17d6ca759a070c377147f6d76b72dab9a3ba42a3/packages/durable/docs/spec.md).
`watch_for` adds a bounded polling wait with an explicit timeout and unchanged
cursor, not an upstream watch end reason. Upstream removed `watchEvents` in
favor of conversation views; its watches terminate with lifecycle reasons, which
this standalone log does not provide. See the [upstream changelog](https://github.com/earendil-works/pi/blob/827383a15262905f82e418483825a49dbb1adbf5/packages/durable/CHANGELOG.md) and [watch documentation](https://github.com/earendil-works/pi/blob/827383a15262905f82e418483825a49dbb1adbf5/packages/durable/README.md#watching-a-conversation).

**Conversation history replay checkpoint:** `Harness` and `Scheduler` expose
`history_head` and `history_through` for finite, paged replay of expanded
conversation snapshots. Persist the conversation ID, boundary and last
processed cursor to resume after reopening; then use `watch_history` from the
last processed cursor. Cursors are conversation-scoped, including across forks,
and numerical cursor values do not authenticate their origin. This replays only
the retained snapshot log, not Chord operations or every document change. Page
counts are bounded, but snapshot bytes, expansion work and retained history are not.

**Historical subsequent checkpoint:** Busy reset queues at safe boundaries, provider-overflow compaction and persisted bounded exponential retry were added. A host can attach a background generic task driver to the conversation store, with direct-child all/any/fail-fast waits and local descendant cancellation. A persistent subagent link can resume child admission. Task lifecycle/abort ownership is not yet integrated with conversation execution, reset ordering and tool handoff are incomplete, and subagent links do not yet supply automatic answer reporting or ownership-aware abort.

**Named background anchor (subsequently automated for managed sends):** `Harness::anchor_subagent` atomically attaches an immediately succeeded background task and foreground child edge to an existing named link. It is idempotent across process reopen, isolates ordinary parent abort, and allows background-inclusive parent abort to reach the child. Existing stop and reporter behavior is unchanged. Managed sends now create the anchor automatically; automatic cleanup orchestration remains unsupported. Explicit background-inclusive parent abort traverses terminal anchors and their child conversations. Its waiting form reports a missing or stopped task driver even while conversation cleanup is waiting on live tasks; persisted abort marks remain available for a later retry.

**Historical checkpoint:** Subagent completion can now be reported automatically to its parent, and reporter-driven conversations continue polling pending tools. Named child status is available as a read-only Rust API, including reservations and queued work; it is not a model-facing management tool. Managed sends now have default child tool restrictions and background anchor ownership; lower-level links remain independent unless explicitly anchored. Queued submissions can be withdrawn. Conversation extension selections, prompt sections, extension-provided tools, before/after-tool hooks and selected generation hooks are supported; the scheduler can preload an extension registry before automatic recovery. The remaining hooks and hook-created tasks are not yet integrated. Task sleeps can wait for a deadline or any named signal. Subagent cancellation is not yet an ownership-aware cascade. Later checkpoints and the table below supersede earlier statements where they differ.

**Nested root-attempt commit fence:** Runtime-owned nested invocations bind journal intents, results, diagnostics, gate writes, hook memo writes and report publication to the current root conversation operation and attempt. Each checked commit re-reads the root, rejects abort or a changed attempt, and retries only a root-version conflict while retaining all other checks; unrelated queued input therefore does not invalidate an otherwise live attempt. Suspended result-hook and poll commits bind to the persisted suspended attempt; legacy suspended hook finalization and automatic polling without an attempt require reconciliation. Standalone `NestedHost` retains its existing caller-managed lifetime. These checks fence durable publication, not external tool or hook effects, and do not implement independently scheduled nested ToolPark children. See nested-fence and nested recovery tests.

**Nested before-tool checkpoint:** Resolved nested calls with valid prepared arguments now run the selected before-tool chain before dispatch, persist its accepted arguments or rejection, and run after-tool hooks on blocked and invalid rewrites. Repeated keyed reads reuse the committed result; the child is not run on rejection. Nested before-tool sleep supports deadline or conversation signal wakes for a replay-safe parent that explicitly suspends on the pending child. Scheduler commits the wake and signal consumption atomically, replays the parent and reruns the child gate with the wake in `nested_before_tool_wake`; it prepares and validates the original child arguments again before rerunning hooks. Invalid gates settle through after-tool; abort fences the wake. A parent that does not explicitly suspend fails closed during ordinary execution. After a process interruption before suspension, a committed pre-dispatch gate can recover a replay-safe parent when every other child is terminal, has an accepted pending reference, a staged result, or a committed gate, and the configured parent passes existing identity and replay checks; unsafe parents and uncertain siblings remain blocked. The host must restore the same tool and hook implementations. The explicit parent waits for all children; gate receipts can commit during another poll, but child hooks and execution occur on parent replay in call order, unlike upstream independently scheduled children. Abort fences local polling and replay but does not guarantee cancellation of accepted external jobs. Resumes count against the existing restart limit. Unavailable or initially invalid nested calls still require reconciliation. Hook callbacks can repeat on interruption. See [nested hook tests](../crates/durable/tests/tool_diagnostic_recovery.rs) and the [upstream tool harness](https://github.com/earendil-works/pi/blob/main/packages/durable/src/harness/tool.ts).

**Before-tool gate rejection:** A sleep without a deadline or signal, with a negative deadline or empty signal name, or on a consumed/expired signal finishes as an `invalid_park` error without executing the tool. The rejected result is privately checkpointed and passes through after-tool hooks; interruption during those hooks does not redispatch the tool. When a rich or block hook replaces its text and retains `invalid_park`, pi-rs keeps that diagnostic in host metadata but withholds its original reason from the model; upstream renders retained diagnostics. The internal `output_redacted` notice is host-only. This matches the rejection path in [upstream tool harness](https://github.com/earendil-works/pi/blob/main/packages/durable/src/harness/tool.ts), while signal keys remain conversation-scoped strings and storage failures still fail the runtime. See [extension runtime tests](../crates/durable/tests/extension_runtime.rs).

**Extension safety checkpoint:** Tool results are checkpointed before after-tool hooks. Abort during preparation records skipped tool results; pending and reconciled operations retain the prepared arguments for result hooks. Older pending records without those arguments fall back to the original model arguments. Extension hooks may be replayed after interruption and must make external effects idempotent. See [extension runtime tests](../crates/durable/tests/extension_runtime.rs).

**Abort and reporter checkpoint:** `Scheduler::abort` persists conversation aborts, withdraws queued inputs unless marked `OnAbort::Keep` and fences both ordinary and reporter-driven dispatch; `abort_and_wait` waits for local workers. A dispatched uncertain effect requires reconciliation even if replay-safe. Background reporter children remain independent: parent abort does not propagate through an ownership tree. See [abort tests](../crates/durable/tests/abort.rs) and [reporter tests](../crates/durable/tests/reporter_pending.rs).

**Conversation-owned task abort checkpoint:** A conversation abort atomically marks its live generic and lifecycle task descendants and withdraws queued inputs unless marked `OnAbort::Keep`. Root and lifecycle admission are fenced while the mark is active; an in-flight task cannot publish children after its mark. Reopening resumes task cleanup child-first, and the conversation stays abort-marked until its owned tasks settle. This requires an attached task scheduler or driver to make progress. Handler interruption remains cooperative: active synchronous handlers cannot be signalled and must return before cleanup; cleanup can replay after a crash and must be idempotent. Missing abort handlers fail with an orphan diagnostic, and restart exhaustion can fail without cleanup. Direct TaskStore mutations and noncooperating executors are outside the ownership protocol. Unlike current upstream, pi-rs has no background-task ownership flag: all conversation-owned generic tasks are included; reporter/subagent conversation links remain independent. `abort_and_wait` waits for local conversation workers, which poll task cleanup; blocked external effects still require reconciliation.

**Historical background task boundary checkpoint:** Conversation-owned generic tasks can be marked background at creation. Ordinary conversation abort and its task-drain check skip that task and its descendants, including after reopening; explicitly aborting the task still marks its subtree. Child tasks cannot be marked background through this API. The preceding checkpoint's statement that all generic tasks are included is superseded. This is only a task-graph prerequisite: subagent links and reporters are not owned by these tasks, there is no conversation abort option to cross background boundaries, and upstream ownership-aware idle, terminal-owner traversal, task-to-conversation cascades and abnormal-completion propagation are not implemented. Existing reporter children therefore remain independent of parent abort, and foreground subagents are not yet supported as owned tool scopes.


**Bounded task-owned conversation discovery:** `Harness::scan_task_owned_subagents` and the scheduler counterpart scan up to 256 ownership edges per call and return those belonging to a task, with a task-bound continuation that survives reopen. This supports the discovery use of upstream `scanConversations({ ownerTaskId })`. Unlike upstream's ordered, filtered transaction scan, pages use child UUID order, the budget includes other tasks' edges, empty pages can have a continuation, and separate pages do not share a snapshot. Malformed or oversized encountered edges fail the page; this read-only discovery cannot authorize graph writes. See `owned_subagent` tests.

**Opt-in task-owned subagent admission:** `Harness::ensure_task_owned_subagent` and its scheduler counterpart atomically create an empty child conversation, permanent task-scoped reservation and ownership edge while advancing the parent task version. Matching retries return the same child, including after abort and reopen; changed owner, configuration or mode is rejected. Admission refuses an already aborting or terminal task. This does not submit input, schedule execution, seed history, or reject longer cycles. Harness abort traversal follows foreground ownership edges as described below. Existing named subagents remain independent. Storage errors require reopening before retry. See `owned_subagent` tests.

**Opt-in task-owned tool inheritance:** The `*_task_owned_subagent_inheriting_tools` APIs copy enabled and model-facing selections and tool filters from the nearest owning conversation under an atomic parent-version and ownership-chain fence. Unlike upstream examples that copy selected extensions, pi-rs rejects admission whenever the parent selects any extension, including restricted name collisions with host tools. Versioned provenance is committed with the reservation; older experimental reservations and collisions fail closed without migration. Matching retries and reopening use the committed snapshot, and existing non-opt-in defaults are unchanged. Before conversation or task scheduler recovery, stores containing an inheritance-marked reservation without matching v2 provenance are quarantined, as are malformed reservations; no automatic migration is attempted. Pre-copied stores without an inheritance marker cannot be identified automatically and require host review before opening. Direct store writers and executors are outside this fence. See `owned_subagent` tests.

**Provider adapter inheritance boundary:** Adapter `id()` is supplied by the host, and installing an adapter can replace an implementation with another using the same ID; the runtime cannot verify equivalent authorization, budget or endpoint behavior across replacement or reopen. Inherited admission therefore continues to reject selected parent adapters rather than treating matching IDs as implementation proof.

Upstream's `pi.provider` session ID is a conversation-facing correlation identity, not an attestation of the executable provider implementation. The host-declared nested-tool identity mechanism similarly requires cooperative host updates and does not independently verify a provider implementation across processes.

**Process-local adapter replacement fence:** `Harness::pin_provider_adapter` optionally pins the exact installed adapter allocation before any worker exists. Later installs through that Harness family reject different allocations, including same-ID implementations. The pin is memory-only and must be reapplied after reopen; it cannot attest implementation identity across processes or stop adapter-internal mutation. `Scheduler::open_with_pinned_provider_adapter` installs and pins before scheduling recovered work; `Scheduler::open_with_pinned_provider_adapter_and_tasks` also attaches the supplied task registry before scheduling, for task-backed tools. The host must reapply the constructor after every reopen. It does not enable task-owned adapter inheritance or alter unpinned installation. See `provider_adapter` and `owned_subagent` tests.

**Adapter-safe inheritance and upgrade quarantine:** Tool-inheriting admission rejects any selected parent provider adapter under the same snapshot fence, because omitting it could bypass its authorization, budget or endpoint restrictions. New inherited reservations atomically bind v3 policy provenance to the v2 snapshot. Existing inherited v2 reservations lack adapter evidence and quarantine the entire store before conversation or task recovery and on duplicate admission; host review and reconciliation are required, with no automatic migration. Non-inheriting legacy reservations remain valid. Unmarked experimental or externally copied children cannot be identified reliably; hosts must review pre-existing stores. See `owned_subagent` tests.

**Task-owned configuration snapshot:** Opt-in `*_task_owned_subagent_inheriting_settings` APIs capture the nearest owner's model, system prompt and output limit along with tool settings under the same parent-version fence, with configuration source recorded in private v3 provenance. Selected provider adapters and extensions remain rejected, and v2-only inherited records remain quarantined. Queues, environment and history are not copied. Retries and reopening retain the committed snapshot. See `owned_subagent` tests.

**Notified inherited task-owned child:** `submit_task_owned_subagent_notified_inheriting_tools` combines the extension-free inherited snapshot with the foreground settlement signal binding and initial input in one fenced commit; scheduler recovery schedules a committed child after interruption. Retries bind the same submission and destination, and conflicting reservations fail. Upstream's wait example copies a filtered extension set; pi-rs intentionally rejects any selected parent extension to avoid shadowed or restricted tool escalation. See `owned_subagent` tests.

**Task-owned initial input:** `Harness::submit_task_owned_subagent` atomically creates the ownership reservation, edge and runnable initial input under the parent task version fence. Matching retries return the original child and submission, including after abort or reopen; changing the input or using the empty-child API with the same key is rejected. `Scheduler::submit_task_owned_subagent` schedules after commit, and reopening recovers a committed child if scheduling was interrupted. Foreground abort traversal and background boundaries follow the ownership rules below. This opt-in API does not seed parent history or configure extensions; storage errors require reopening. See `owned_subagent` tests.

**Foreground ownership abort traversal:** `Harness::request_abort` and `Harness::request_abort_task` atomically persist abort marks across foreground task and conversation ownership edges, withdraw queued inputs except those marked `OnAbort::Keep`, skip background branches, and fence visited records and edges against concurrent admission. Cycles terminate; conflicts retry the complete traversal. Direct store writers outside the ownership protocol are not fenced. A standalone task scheduler can attach a conversation runtime with `open_with_conversation_runtime`; it shares the exclusive owner and marks the foreground graph. `tick_with_conversation_cleanup` incrementally settles marked conversation aborts without running retained queued input, and a task driver started from it runs the cleanup coordinator. Plain `open` still fails closed on foreground conversation edges. A storage error can have an uncertain outcome and requires reopening. See `owned_subagent` tests. Standalone cleanup persists a version-fenced attempt marker before dispatch; interrupted or failed attempts, including independent-summary recovery and explicit resume, remain blocked across reopen until the host reconciles external effects and explicitly calls `reconcile_owned_cleanup`. A missing child, malformed edge, or invalid abort mark in an unrelated graph is skipped during discovery. Task abort settlement holds all tasks when an edge is too malformed to identify its owner, while independent conversation cleanup can proceed; known affected tasks are held individually. Summary execution shares a per-conversation read fence against cleanup marker creation; a timeout before marker creation is retried by a later tick. Missing background children do not block their owner’s abort. All owned-conversation abort workers, including direct resume, use the same durable attempt fence; ownerless retries retain their existing behavior and a temporary marker fences concurrent ownership attachment. Held task completion scopes damaged edges only when an immutable reservation identifies their owner; uncertain unmarked failed owners are parked rather than cascaded, and unrelated outcomes require a verified outside owner chain. Attaching an existing named subagent is fenced against the child’s cleanup marker. The attached task driver uses the same durable cleanup attempt fence; per-conversation failures and malformed discovery records do not stop unrelated cleanup. Driver-side reconciliation clears a previously reconciled marker before retry.

**Child-first owned cleanup checkpoint:** Compared with upstream [abort and subagents](https://github.com/earendil-works/pi/blob/06f5671c924cd6eaa1d7501736925db0e5cb2a49/packages/durable/README.md#abort-and-subagents), which waits for the conversation to become idle and supports explicitly crossing background boundaries, this implementation retains the boundaries and limitations below. Task abort cleanup waits for each foreground owned conversation to finish its persisted abort, including that conversation's foreground task descendants. Restart-limit failures also wait for those children. `Scheduler::abort_and_wait` joins the workers for all conversations marked by the atomic traversal. Ordinary abort retains background boundaries; explicit background-inclusive abort crosses them. Cyclic ownership is drained by relaxing only waits in a cycle; their child-first order cannot be guaranteed. Blocked uncertain operations require reconciliation and generic tasks require a running driver. Standalone task schedulers and drivers support these aborts when opened with the conversation runtime; plain `open` still rejects them. See `owned_subagent` tests.

**Earlier scheduler propagation checkpoint (superseded by child-first checkpoint above):** `Scheduler::abort` and `abort_task` fence existing conversation polls while committing the foreground graph, cancel affected workers, and schedule each marked conversation for cleanup. Reopening schedules all persisted conversations. Background edges remain independent. Standalone task abort still rejects foreground child conversations, and task cleanup does not join child conversation cleanup; `abort_and_wait` waits only for the requested conversation's local workers. Active nested-conversation race and crash/reopen coverage remains incomplete. Legacy task cancellation fails closed when it would strand a foreground child. See `owned_subagent` tests.

**Ownership edge storage checkpoint:** `ownership_edge::EdgeStore` prepares checked, atomic task-to-existing-conversation links with explicit foreground/background metadata and a unique owner per child. Both endpoint versions and task ownership are fenced at commit, and edge creation advances the task version to invalidate a concurrent traversal's earlier task snapshot. Edges survive reopen. This is only a composable storage primitive: creation of the conversation and task must currently precede the edge; no traversal, cycle detection beyond a direct self-edge, scheduling, abort propagation, lifecycle cleanup, or subagent integration is provided. Edge mode is stored metadata and does not itself implement upstream background boundaries. See [ownership edge tests](../crates/durable/tests/ownership_edge.rs).

**Continue checkpoint:** `Harness::submit_continue` and `Scheduler::submit_continue` persist a distinct, deduplicated run submission without a user message, reject busy conversations, place queued steers and follow-ups according to the configured queue modes, and settle the participating submissions together. Empty or answered contexts settle `nothing_to_answer` without a model request; failed runs retain their unanswered user/tool context. Recovery resumes the committed phase, and truncated tool calls are recorded as skipped without dispatch. See [continuation tests](../crates/durable/tests/continue_submission.rs) and [runtime tests](../crates/durable/tests/runtime.rs). Unlike upstream, this runtime has no public transactional/tool-side admission or full `pi.live.runFailure` parity; it uses Rust status and reason strings and represents continue content as an empty compatibility field in memory (omitted from storage). Historical synthetic failure messages from older versions are not rewritten. Queued reset ordering and generic task ownership remain separate gaps.

**Submission settlement notifications:** `Harness` and `Scheduler` provide notification-bearing input, continue, and application-write admissions. Input variants with checked admission documents or fitted image blocks are also supported. A destination is persisted in the conversation snapshot keyed by submission ID and exposed by `Conversation::submission_notification`; the common conversation commit assembles `pi.submission-settled` after candidate task and signal writes, including multi-conversation aborts and immediately placed writes. Duplicate, closed and missing destinations do not fail the settlement; an incompatible, ambiguous or incorrectly keyed pre-existing receipt fails the commit rather than masquerading as a settled record. Notification-only target or receipt conflicts, including a notification deadline added to an existing task check, are re-evaluated with bounded retries while the original conversation, graph, task version, original deadline and document fences remain fixed; each notification retains a monotonic projection of its clock samples across reassembly even if the supplied clock freezes or moves backwards; remaining conflicts fail the transaction. Forks do not inherit notification destinations. See the `submission_notify_` runtime tests.

Upstream [spec §5.7 at 04fd0897](https://github.com/earendil-works/pi/blob/04fd0897/packages/durable/docs/spec.md) uses numeric submission, conversation and entry IDs, and the `SubmissionSettled` value is its settled submission record. pi-rs exposes UUIDs, answer text and an optional UUID `answerId`; for a display write its UUID is returned as `entry`. `submission_settled_signal()` validates this pi-rs value shape. pi-rs retains its own storage and admission APIs; duplicate request IDs return the original submission without changing its notification. General upstream session transactions and broader tool-side submission admission remain unsupported. Signal deadlines use the runtime's signal clock and elapsed monotonic time, as with the existing host API. See [runtime tests](../crates/durable/src/runtime.rs) and [host tests](../crates/durable/tests/host_signal_transaction.rs).

**Host session-membership foundation:** `session_membership::SessionMembership` lets a trusted storage-owning host create a durable session identity and explicitly enroll or revoke existing, non-aborting conversations. `authorize_pair` produces a one-shot proof for a host-owned checked store batch; both membership records, the session record, and both conversation snapshots are version-fenced with the effects. Revocation and re-enrollment invalidate old proofs, and enrollment fences intervening membership creation. Missing, unscoped, mismatched and aborting conversations fail closed. Authorization also requires an explicitly persisted `abort_requested` boolean and a valid model configuration; historical snapshots lacking that abort evidence remain unscoped for authorization until repaired, while historical snapshots missing unrelated defaulted fields remain supported. Session IDs identify records and are not credentials: access to this host API and the reserved storage namespace must remain privileged. Proof-backed mutations are limited to the host-owned `host/` namespace; storage failures can have unknown outcomes and require reopen. See [membership tests](../crates/durable/tests/session_membership.rs).

This is a host authorization building block, not upstream Session ownership or a task capability. The host proof itself does not authorize task submissions or conversation mutations; the bounded task-side input API described below independently resolves membership and composes its checks into the task transaction. Every supported conversation fork inherits the caller’s current explicit membership, including cuts whose history originated in another conversation. The parent membership, session record, parent snapshot, and child-membership absence are fenced in the child creation commit. A legacy unscoped parent produces an unscoped child under an ABA-aware absence fence; malformed scoped membership and aborting scoped parents fail closed. Settlement notifications are not inherited. Upstream binds `submit(tx, draft)` to the owning live Session rather than authorizing a transaction by ID; see [upstream submissions](https://github.com/earendil-works/pi/blob/9cd49d2c/packages/durable/src/harness/submissions.ts).

**Same-session cross-conversation task submissions:** `TaskDocuments::submit_input_to_session_conversation`, `submit_continue_to_session_conversation`, and `submit_write_to_session_conversation` stage keyed text input, continue, or display-only write to a different conversation; the corresponding `_without_request_id` methods stage distinct unkeyed drafts. The host must explicitly enroll the owning and target conversations in the same persisted session; the task supplies only the target and cannot supply or choose its session. The runtime resolves generic task ancestry with cycle, abort and terminal checks and derives session identity from the owner membership. The task transition, documents, target admission and wake marker commit together with the task ancestry, owner and target snapshots, session/membership versions, and target foreground ownership and abort fences. Successful terminal task owners remain valid foreground ownership anchors, including at multiple levels after reopen. Pending foreground ancestor failure, fail-fast cancellation, and uncertain conversation cleanup reject admission; background ownership boundaries stop that cancellation scope. Revocation or re-enrollment conflicts an uncommitted step; replay-safe steps retry, while unsafe steps follow existing reconciliation. Revocation does not withdraw an already committed submission or its notification. An optional settlement notification must target the submitting task and uses the normal target submission settlement path. A paused harness requires explicit driving; a running scheduler discovers the durable wake. Crash recovery follows the existing task attempt policy. A rejected admission is returned to the handler, which must handle it; it never falls back to the owning conversation. A duplicate request is rejected if its existing settlement notification differs from the requested notification. Continue requires an idle target; a display write waits behind queued resets or a pending write. A task step can stage up to 16 ordered submissions to one same-session target; each observes the preceding drafts. A rejected draft preserves the preceding candidates. Distinct task admissions must use different notification destinations, including across steps and reopen. Each new destination is permanently bound to its actual conversation and submission ID in the task commit; admission also checks legacy conversation notifications and retained typed receipts under conversation-prefix and signal-revision fences. Keyed duplicates retain their original notification. A conflicting explicit settlement signal in the same task step is rejected; unrelated signals may be composed. The legacy check scans persisted conversations, so its cost grows with the number of conversations. Reservation-only signal-revision and conversation-prefix conflicts can be rebuilt after rechecking receipt and notification absence, including for queued admissions; typed-wait keys are revalidated and independently observed handler, document, task, graph and deadline fences remain in force. Existing bounded graph and notification retry limits still apply under sustained contention. Mixing owning and cross-conversation targets or using multiple targets remains unsupported. Session membership and the store are host-controlled, not credentials exposed to tools. See [task submission tests](../crates/durable/tests/task_submission_transaction.rs).

**Task-side input, continue and display-write admission:** `TaskDocuments::submit_input`, `submit_input_with_options`, `submit_continue`, and `submit_write` stage up to 16 ordered submissions per task step for its owning conversation, including through generic task ancestors. Each draft observes earlier staged drafts; a rejected draft leaves the preceding candidates intact. This multi-admission behavior is a pi-rs extension: upstream `submit(tx, draft)` rejects another admission after the first table write. The keyed methods require a nonempty request ID; duplicates retain the original submission and notification. The `*_without_request_id` variants match upstream optional request IDs: each accepted draft is distinct, and a retry of the same uncommitted task step remains atomic under its attempt and conversation fences. Separate successful task steps do not deduplicate these admissions. Inputs use the host busy/idle policy and queue behavior. Continue deduplicates before its busy check and otherwise requires an idle conversation; it uses the existing transactional continue boundary and preserves its reset proof fences. A pending summary or unplaced display write remains a busy rejection, and multiple queued block-bearing resets remain unsupported in one continue. Display-only writes are placed immediately, including while busy, except behind a queued reset. Optional `SubmissionNotify` delivers a settlement signal; an immediate write's delivery is composed against the candidate task and signals in the same atomic commit. As with host signals, an existing valid receipt for the key wins. A notification-only deadline or signal-revision conflict rebuilds the delivery against the original task, graph, document, and signal checks, with a monotonic retry clock; original checks are never weakened. After three reassemblies, a further conflict follows the task’s replay-safe or reconciliation policy. Later input and queued-write settlements use the ordinary runtime notification path. The task step, checked documents, conversation, observer, and immediate notification commit together under the task, every traversed task ancestor version, and conversation fences. Cyclic, missing, terminal, or aborting ancestry is rejected; ancestry changes force the checked step to retry or reconcile. A failed or aborted step discards them; replay-safe conflicts replay the handler, and non-replay-safe work needs reconciliation. Capability validation uses the captured conversation snapshot. A running conversation scheduler discovers a durable wake marker; a paused `Harness` leaves work pending until resumed. Markers survive process death, are cleared after driving, and remain after failure for reopen or a newer admission. Runtime checkpoints cannot be combined with these admissions in one step. This slice returns no provisional submission ID and does not support multi-target batches, model-affecting writes, batches over 16 drafts, or general `submit(tx, draft)`. It uses pi-rs UUIDs and its existing settlement signal format. See [task submission tests](../crates/durable/tests/task_submission_transaction.rs) and [task input recovery tests](../crates/durable/tests/task_input_transaction.rs).

Reset-proof evidence observed during candidate preparation is fenced in the same commit, including for duplicate requests. Checked proof conflicts during handler admission or preparation discard the attempt and follow the task's replay-safety policy; non-replay-safe outcomes require reconciliation. Non-conflict storage failures retain their storage cause through validation and settlement and require scheduler recovery; malformed proof data remains an invalid admission.

**Admission policy checkpoint:** `Harness`, `Scheduler`, and the state-backed
conversation helper now support optional busy and idle rejection for input,
with request-ID deduplication before the policy check and version-checked
admission under contention. Busy means an active run, even when queued input
remains after a failed run. Duplicate input request IDs are resolved before content validation. Arbitrary host transactions / `submit(tx, draft)` are not supported. See the admission concurrency and recovery tests in
[`runtime_cas_tests.rs`](../crates/durable/src/runtime_cas_tests.rs). The
original audit table below remains a historical baseline.
**Write-submission checkpoint:** The experimental runtime accepts display-only application entries through `submit_write`, persists them immediately while busy, and delays placement behind queued resets. Request IDs deduplicate within the conversation before validating a repeated write’s kind and cannot be reused across input and write types. Entries are exposed in `Conversation.application_writes` and observer snapshots with a placement flag and preceding reset ID. This is a narrower API than upstream: model messages, head edits, stale-head handling and generic entry transactions are not implemented. Current forks and historical snapshots inherit placed application entries at the selected point, but not their request IDs. Queued and withdrawn writes are exposed as records, not placed transcript entries; observers must filter `placed`. The runtime still stores snapshots rather than an upstream ordered entry stream.

**Write withdrawal:** As at upstream revision `827383a15262905f82e418483825a49dbb1adbf5`, withdrawing a queued display-only write settles it unanswered with reason `aborted`; a placed or previously withdrawn write reports `settled`. pi-rs persists a `withdrawn` tombstone in `application_writes`, retaining the submission and request ID across reopen; `wait_for_submission` reports `WriteUnanswered`. Reset placement skips tombstones, and worker conflict merging preserves a withdrawal that committed before a stale placement. This applies to `submit_write`, not the separate task application-entry log.

**Image fitting checkpoint:** Against upstream `c3cc91632d0a1950fb122605b190233f2aa0006e`, host-provided processors or the optional image-rs `BuiltinImageProcessor` fit user input and opt-in runtime block hooks fit model-issued tool results before their transcript commit. The built-in codec decodes PNG, JPEG, GIF, WebP and BMP, applies JPEG/WebP orientation (including both WebP EXIF chunk forms), resizes and re-encodes within limits; transformed images use 8-bit RGBA, transformed animations become still first frames, and JPEG drops alpha. Source and decode sizes are bounded; image-rs resampling and compressed bytes may differ from Photon, potentially changing which candidate meets a tight limit. Direct processor calls reject mismatched MIME types; fitting helpers sniff supported formats. `ImageLimitsCatalog` resolves upstream-shaped model descriptors supplied by the host, not an automatically synchronized upstream catalog. Tool blocks, diagnostics, and occurrence IDs survive reopen and validated forks; nested calls also run the opt-in block-hook chain and retain changed blocks in their keyed journal. A custom adapter must explicitly support `DurableToolRequest`; bundled adapters opt in subject to the provider-specific limitations described below, while core model dispatch rejects tool blocks. Manual, automatic threshold/overflow, and independent compaction preserve retained tool blocks and omit summarized images while including tool text; reset retains earlier blocks in history. Hooks must opt into both block-aware and tool-block compaction, and stale snapshots fail closed. Core tools themselves still return text, so a block-aware hook must produce the blocks. Hook ordering differs from upstream: legacy and structured hooks run first, then opted-in block hooks. See [image fitting documentation](../crates/durable/README.md#preparing-host-supplied-images).

**Tool-result delivery:** OpenAI Responses joins text and attaches images to the function output; Ollama joins text and places tool images in a following user message. Neither upstream wire format carries a separate error flag. Anthropic emits `is_error` and moves images from error results after all tool results in the batch, while retaining successful result images. All four use the durable status binding and the runtime image profile; explicit host descriptors override the bundled profile. Google defaults to [upstream pi](https://github.com/earendil-works/pi/blob/c3cc91632d0a1950fb122605b190233f2aa0006e/packages/ai/src/api/google-shared.ts): it joins text blocks with newlines, attaches images to Gemini 3+ or unknown-model function responses, and places older Gemini images in an immediately following user message. This projection loses text/image interleaving in the model request, while storage retains the source blocks. The durable metadata-aware path delivers committed tool error flags to Google for both plain and block results, using an occurrence binding when available; ambiguous reused call IDs fail closed. Host-supplied model input descriptors override the catalog; Google also normalizes models/ aliases. Unknown models retain the prior image-capable default. Descriptors must be reinstalled on reopen. Legacy results without metadata use the `output` key. All bundled adapters opt into this metadata path. `GoogleAdapter::new_ordered_tool_blocks` explicitly selects an alternative adapter ID using [Google's `$ref` format](https://ai.google.dev/gemini-api/docs/generate-content/function-calling#multimodal); it preserves interleaving for recognized Gemini 3+ models but has not been verified against a real provider. Provider-hook validation rejects changes to either selected projection. Ollama follows upstream's separate user-image message rather than sending ordered images inside the tool message.

**Ordered user blocks checkpoint:** An opt-in durable provider can receive user block arrays stored atomically with occurrence IDs, including continuations from `onYield` and its tasks. Expanded history snapshots include their block bindings. The OpenAI Responses, Anthropic Messages, Google Gemini and Ollama adapters encode ordered text and images; Responses also supports image `detail`. Empty arrays and unsupported metadata fail before dispatch. Before-request hooks can inspect the block bindings but cannot replace them or the message list. Core model dispatch fails closed. Manual, automatic threshold, overflow and independent compaction preserve retained blocks and their provenance; selected hooks must opt into block-aware compaction. Busy independent placement rejects changed or new block bindings. Retention estimates count text and a fixed image cost and remain approximate. Reset and tool handoff create a new active context while earlier blocks and their provenance remain in historical snapshots; `reset_with_blocks` also admits ordered additions with sequential durable placement of overlapping resets as described above. Forks preserve ordered blocks and provenance at validated boundaries and proven state-stable interior cuts; unproven cuts remain unsupported. This remains a subset of upstream provider parity. See [durable storage documentation](../crates/durable/README.md#ordered-transcript-block-storage) and [provider tests](../crates/durable-openai/tests/http.rs).

**onYield checkpoint:** Final answers enter a persisted onYield phase with a stable hook memo. String continuations, including empty and whitespace-only strings, and representable nonempty content arrays keep the current submissions open and start a fresh turn budget. Core-compatible arrays may contain one text block followed by images, or images alone; image data must pass core validation. Without a durable-aware adapter, core cannot preserve multiple text blocks or text after an image, so those inputs are skipped. With a durable-aware adapter, ordered arrays are persisted and later validated by that provider; an unsupported empty array or metadata therefore fails closed instead of being truncated. Malformed inputs are skipped and invalid direct decisions are reported, unlike upstream's trusted typed hook path. The first valid child result in creation order wins. Queued steering, follow-ups, or resets take precedence; after-run hooks run only once an answer stands. Reports are persisted and deduplicated on replay; hook-created tasks and their wait are committed atomically. A registered task driver is required, and reopening resumes the persisted wait. Hooks may replay after interruption or concurrent admission and must make effects idempotent. As upstream resets the turn budget on continuation, extensions must bound their own continuation loops. pi-rs exposes the already-committed answer in the hook snapshot. Conversation abort marks owned hook children and descendants atomically and waits for cleanup with an attached task driver; synchronous effects still cannot be interrupted or rolled back. See [extension runtime tests](../crates/durable/tests/extension_runtime.rs).

**beforeCompact checkpoint:** Manual, threshold and overflow compactions persist the selected message range and a stable hook memo identity before calling selected hooks. Manual compaction accepts optional instructions, persisted for both the summary request and hook across recovery. The summary source uses upstream-style role-marked text, omits images and truncates tool results. The first decline or summary wins; hook errors are skipped, cancellation replays the phase, and hook summaries bypass model usage. Unlike upstream, the host exposes message indices instead of entry IDs and markers, has no hook report callback, rejects blank summaries, and still requires idle manual compaction. See [compaction tests](../crates/durable/tests/features.rs).

**Manual compaction operation identity:** Idle manual compaction exposes a persistent operation ID and running, applied, declined, stale, aborted, or restart-limit status. Admission rejects a pending abort and commits the selected hook identity and running record together; terminal status commits with the corresponding context or abort transition. A recovered summary attempt retains the operation ID while using a new model request ID. Records are not inherited by forks and have no retention policy. Existing recovery-required errors leave the operation running pending reopen or abort. This is an executable identity for the existing idle phase, not an independently scheduled task, and does not enable busy compaction or upstream stale-submission settlement. See [compaction tests](../crates/durable/tests/features.rs).

**Independent summary operation storage:** `SummaryStore` persists bounded preparations, attempt identities, completed results and terminal placement decisions independently of conversation phases. Version-checked reservation and transitions fence competing claims and stale completions; interrupted running attempts retain an unconfirmed usage marker. Request IDs are reserved across summary operations in this store. The private scheduler path uses a per-operation executor guard; an owner ID alone is not a lease. See [store tests](../crates/durable/src/summary_store.rs).

**Independent summary accounting checkpoint:** Completed generations are persisted before usage settlement, including invalid summaries whose usage still needs accounting. Per-attempt receipts record successful settlement for both measured generations and interrupted attempts; publication requires all relevant receipts. The private worker transfers a pending checkpoint only after acquiring the per-operation guard. A crash between provider acknowledgement and receipt requires replay with the same request ID and report, so external settlement must be idempotent. See [worker tests](../crates/durable/src/summary_worker_tests.rs).

model request or a proven model-issued tool attempt is running, or that tool
is parked on a known pending reference or an identified owned task. It checks
the issued call list and the exact preceding result sequence, including in a
multi-call round. A bounded durable selection snapshot proves that any
intervening changes retain the original submission and write identities and
configuration; the context generation and selected source prefix must also
match. Append-only model progress and fenced model restarts can therefore use a
later conversation version for the atomic placement ticket and pending marker
while the model or eligible tool is running or pending, in on-yield, after-run or after-tools hooks, in
parked lifecycle hook task waits, or at idle. An after-tools hook's completed
decision and child tasks commit with its phase transition; an admission race
does not rerun the hook. A parked after-tools task settles the round first; a tool handoff
changes context before the boundary and makes an older summary stale. The
unfinished tool round is retained, and all results settle before placement.
Interrupted unsafe calls remain blocked until explicitly reconciled; summary
recovery does not redispatch them. Task waits require a persisted adapter
identity and matching adapter and driver for recovery. Blocked or replay-ready
tools and unproven attempts remain ineligible; a
transient unsupported phase can conservatively settle a result stale. The
summary-and-task recovery constructor installs both registries before scheduling.
On-yield decisions are checkpointed before inbox
selection; an admission race does not rerun a completed hook. A crash before
a hook decision commits can replay it, so external effects require memo and
idempotency.
A preceding reset is
placed first and makes the summary stale; queued inputs follow the writes.
In-flight model saves merge the marker, and context-generation and source-prefix
checks guard the atomic settlement. Later writes follow the marker. Conversation
abort preserves a queued summary and passive writes; explicit operation abort
withdraws it. Pending work survives reopen. The selection and hook snapshots

This is not a general ordered inbox. See
[public tests](../crates/durable/tests/independent_compaction.rs) and

**Independent summary worker and placement:** An opt-in public idle path starts a scheduler-owned independent worker, runs selected `beforeCompact` hooks from a persisted snapshot with operation-scoped memo and optional instructions, settles usage under the per-operation fence, and automatically places or marks its result stale. Conversation graph abort marks running owned summaries and waits for cleanup while preserving an already queued summary write; foreground idle waits include them. Admission still checks the conversation's own phase and queue rather than its owned graph. Placement requires the exact captured conversation version and preserves retained provenance. The recovery constructor installs its adapter and extensions first, scans at most 128 total records of at most 4 MiB each, and resumes matching provider-bound execution and public automatic placement. Hook snapshots are limited to 512 KiB; a missing selected extension blocks execution. Legacy or mismatched identities are blocked; the host must identify the provider, tenant and idempotency namespace correctly. The record limit includes terminal records, public admission rejects a full store, and no retention policy exists. Individual store entries are materialized before size checks. The narrow busy path described above does not yet provide a general ordered inbox. See [public test](../crates/durable/tests/independent_compaction.rs) and [worker tests](../crates/durable/src/summary_worker_tests.rs).

**Independent placement ordering prerequisite:** An eligible completed result is first transitioned to pending placement in the same version-checked transaction that creates its immutable placement ticket. The ticket's store commit sequence can be compared with tracked conversation commits; duplicate admission conflicts and a missing or inconsistent ticket fail closed. The idle path still treats a later conversation change as stale. This does not yet order input, reset and write submission IDs in a shared inbox. See [ticket and recovery tests](../crates/durable/src/summary_worker_tests.rs).

**Persisted summary placement:** Hook-provided or accounted model summaries enter a durable placement phase before changing the conversation. Placement checks the saved context generation and source prefix and atomically commits either the resulting messages and applied status or a conservative stale status for a tracked manual operation; concurrent admissions force a fresh decision. Abort before that commit takes precedence. An OS-kill test reopens a committed placement checkpoint. This currently runs inside the idle-only conversation phase, rather than through an independently scheduled task and ordered inbox write. A generation change can reject a result even when upstream would retain its target.

**Manual summary/reset ordering:** A tracked manual summary placement records the queued reset IDs that precede its admission. The placement transaction applies those resets first and settles the summary stale; resets admitted after the placement checkpoint follow it. Worker conflict merging adds a reset that committed before the checkpoint to that ordered prefix. The prefix survives reopen, while legacy placement checkpoints retain their previous order. Tests cover a live pending summary, a merge conflict, later resets, and an OS-killed summarizer. This does not supply a shared inbox for independently scheduled compactions.

**Summary process recovery:** A process-kill regression records the actual in-flight summary request ID and checks that scheduler reopen settles it as unconfirmed before invoking a new request with a different ID. The operation ID survives, and the reset queued before the result makes the recovered result stale. This exercises the existing conversation-owned summary phase, not an independent summary worker.

**Retained compaction occurrence provenance:** A proven compaction replacement records its projection of the immediately preceding immutable transcript and materializes the retained messages’ original occurrence metadata. Its new summary gets a distinct ID. Loading a compacted context and authorizing a position or ID fork reconstruct and validate the predecessor chain, original observation links, matching runtime-owned fork snapshots, projection, and ID uniqueness; retained legacy messages without IDs remain unidentifiable and cannot authorize a position fork. Annotated origins lacking a matching runtime snapshot fail closed, since public observer appends alone cannot prove a runtime commit. Positioned page reads retain their bounded transcript-record limit and expose structurally checked stored metadata; full provenance validation occurs on context load and fork authorization. These validations scan the retained transcript history and can consume time and memory proportional to that history. This does not enable busy compaction; manual retained-target settlement is described below. See [runtime tests](../crates/durable/src/runtime_cas_tests.rs) and [feature tests](../crates/durable/tests/features.rs).

**Retained target settlement:** New tracked manual preparations pin the selected occurrence ID and immutable source cursor when provenance exists. Placement verifies that the source is an ancestor, the selected source occurrence matches the persisted target, and that the same provenance remains in the active context. A result can apply after another compaction retains its target; a removed or unprovable target settles stale. The placement transaction preserves retained occurrence provenance and remains ordered with queued resets. Legacy or unannotated preparations use the conservative generation and prefix check. Conversations without a proven reset-identity epoch also stay conservative until a newly committed reset establishes one; even an identical-text reset creates new occurrence IDs. Verification scans transcript history without a configured bound. The overlap regression uses a real competing compaction and stages the earlier result because independently scheduled manual compaction is not yet available. Busy manual compaction remains disabled; a separate fenced worker, durable operation lifecycle, and shared ordered inbox are still required.

**After-tools termination checkpoint:** A successful after-tools child result of exactly `{ "terminate": true }` settles active inputs with the tool-calling assistant answer, runs after-run hooks, and only then places queued inputs at the final boundary. The persisted child wait resumes after reopening. `null` and `{}` continue normally; other successful results produce a durable invalid-decision report attributed to the task's extension and continue normally. Opt-in `KeyedTool::invoke_controlled` can return a terminate control; a nonempty round ends when every call requests it, with controls committed alongside tool outcomes and preserved across reopen. Ordinary tools and synthesized errors have no control. Opt-in controls also support handoff: the last defined handoff in call order appends a durable reset after after-tools tasks and before queued items, including when the round terminates. Opt-in `add_tools` controls persist names in call order at that same boundary, updating exact lists or remove/add filters and retaining currently unavailable names. See [extension runtime tests](../crates/durable/tests/extension_runtime.rs).

Explicit tool selections and additions are offered in stored order. Empty added names are ignored to preserve the selection invariant. An addition expands the shared execution allowlist, including restricted subagents, so only trusted tools should be permitted to return controls.

**Queue delivery checkpoint:** Durable conversations persist independent steering and follow-up delivery modes, defaulting to one at a time for new and legacy records. `all` selects every queued input of that kind at the eligible boundary. Final boundaries settle the previous run before starting the selected successor inputs; post-tool boundaries select steers only. See [durable README](../crates/durable/README.md).

**Abort withdrawal result, pi-rs extension:** `Scheduler::abort_and_wait_withdrawn` returns the queued inputs withdrawn by the same atomic foreground abort; `abort_and_wait_with_background_withdrawn` includes the background scope. Each result carries the original conversation, mode and submission snapshot in that conversation's queue order. Retried abort commits return only inputs withdrawn by the successful commit; queued writes are retained. Repeating an abort returns no previously withdrawn inputs. The existing abort methods keep their previous return types and wait/ownership limits. Upstream briefly added an abort result in [6111062](https://github.com/earendil-works/pi/blob/61110626b8ca486ce4e0cb8e496aebe0d194b66d/packages/durable/src/harness/types.ts), then [reverted it](https://github.com/earendil-works/pi/commit/684fddee0b1bdfd04a4880751d363bd6b73042de); current upstream returns no withdrawal list. These opt-in Rust methods retain the capability as a pi-rs extension and use a nested `Submission` representation. See [abort tests](../crates/durable/tests/abort.rs).

**Typed signal checkpoint:** Task signals optionally record a versioned token and structured kind/key and survive reopen; matching is by kind and key. Typed keys hold a single value per task, reject conflicting deliveries, and close to further waits after consumption; identical retries with another ID do not create another receipt. Schema-bearing tokens validate constructed values and typed reads; older versions require an explicit read-only migration, and failures leave receipts unchanged. Legacy tokens, raw receipt reads and wake results bypass schema checking. `deliver_signal` returns upstream-shaped delivery outcomes. Typed deadline-or-signal sleeps retain wake reasons through recovery until checkpoint progress, another wait, or termination, and atomically expire empty keys against concurrent delivery; status delivery checks deadlines using wall time or an explicit clock. The older receipt-based `send_signal` reports expiry as an error. Opt-in `TaskDocuments::signal_at` stages multiple typed deliveries, including to the running task and distinct keys on the same target with the checkpoint and document batch; signals may be staged after document and application-entry updates; its outcome is provisional and task/version and signal-revision conflicts roll back the whole attempt. It anchors a caller-supplied staging time to monotonic elapsed time and conflicts if an empty matching key crosses its deadline before the storage commit boundary; replay must supply a fresh time, and clock jumps after staging are not observed. A repeated key after delivery or duplicate validates the new value and returns duplicate without staging another receipt; invalid values can be retried. Repeated missing and closed targets return their fenced outcome; repeated expired keys validate each value before returning closed. Self-delivery is committed with the handler transition and can satisfy its own typed wait after reopen; abort and failed transitions discard staged effects. Other batch participant overlaps can still conflict; it is not general upstream transactional delivery. Preexisting duplicate typed records are not consolidated and typed reads reject ambiguity. Legacy signals remain separate. See [typed signal tests](../crates/durable/tests/typed_task_signals.rs) and [deadline tests](../crates/durable/tests/typed_signal_deadlines.rs).

**Cross-owner task waits:** `WaitFor::Tasks` and `TasksAny` can name existing tasks outside the waiter's ownership; `TasksFailFast` remains restricted to direct children. Empty `TasksAny` wakes on the next scheduling pass. Scheduler admission rejects cycles through durable waits and live foreground task/conversation ownership, and fences supported graph puts until the wait commits. The ended IDs are refreshed at reservation, including after reopening; [process recovery tests](../crates/durable/tests/process_recovery.rs) cover an OS kill while waiting on an unowned task. The low-level task store still permits callers to construct waits without the scheduler's graph validation, and raw SQLite/delete-only writes are outside the graph fence. Cycle, missing-target and invalid fail-fast waits fail the invoking task without stopping unrelated work; their diagnostic does not yet match upstream's full invalid-wait reporting.

### Parallel parked nested calls: compatibility boundary

Compared with upstream pi at [`c1d4b0ac3e35dc4eb1c5d00d90bf54003cf517c0`](https://github.com/earendil-works/pi/blob/c1d4b0ac3e35dc4eb1c5d00d90bf54003cf517c0/packages/durable/README.md#tools-that-park), this is not just a concurrency restriction. Upstream starts or finds each nested call as a caller-owned tool task with `executeTool(..., { key, wait: false })`; the returned task ID can be used in a parent park with an `any` wait. A wake re-enters the parent with its checkpoint and ended task IDs. Explicit keys are required after a wake, and a parked parent retains its children across restart, including when the parent is replay-unsafe. Settlement or abort handles its remaining children; parking does not settle them. A normal awaited nested call instead keeps the parent invocation alive.

The present Rust path has different boundaries:

One bounded intermediate park is supported: a replay-safe root can invoke a
replay-safe keyed direct child which checkpoints while one to eight keyed descendants are
pending or already completed, with at least one pending. Completed results are
version-checked in the park transaction and replayed from the journal, including
results from replay-unsafe descendants. After an any wake, re-parking also
version-checks the previously completed siblings, including resolved jobs.
Only pending descendants appear in the wake IDs. Both invocations return normally without state or controls; the root
also checkpoints and parks, and must explicitly re-enter the same child after
wake. An all-settled park wakes after every descendant settles; an explicit
`suspend_pending_any_with_checkpoint` wakes when at least one settles. Its
ended IDs are frozen with checks on every job and survive crash and replay.
The root receives the same ended IDs, and the child receives its own checkpoint.
The child must re-park while descendants remain, and cannot admit new ones after
wake. Normal checkpoint wakes do not consume the restart budget, and a
successfully committed checkpoint resets the interrupted-execution count;
repeated crashes before the next checkpoint still exhaust the configured limit.
Results are ordered by key. Pollable descendant references can change
without redispatch. In-flight polls are dropped before replay; a still-pending
job may be polled again after re-parking, so external polling must tolerate
retries. The intermediate executor is retired before replay, and
its checkpoint, claim and effects are fenced by the current root attempt and
abort state. Selected extension hooks are supported for completed and pending
descendants, including early any wakes. The raw remote receipt and the final
hook-transformed result are stored separately and checked before the intermediate
wakes and when completed siblings are included in a later park. Older records without a
final projection retain the original exact-match check. Before-tool hooks run
before intent and are not repeated on a child wake; the ordered result hooks
finish before the intermediate wakes. During an any wait, a staged terminal
poll ends the current poll round: remaining inline poll futures are dropped and
their cancellation guards run before the result hooks start. A slow sibling
therefore does not delay hook finalization or the early wake; its accepted job
remains pending and can be polled again after re-parking. This does not cancel
the external job or join work detached by a tool implementation. If a host
reconciliation stages a valid terminal receipt while the any wake is being
frozen, the wake retries so the next round can finish the hook; malformed
receipts remain errors. Reconciliation of another still-pending child races
atomically with freezing: if freezing wins, reconciliation returns a storage
conflict and the host must retain and retry its authoritative receipt after
the parent resumes and re-parks. If reconciliation wins, the freeze retries.
The frozen ended IDs remain unchanged; no remote job is cancelled. A crash before hook-result commit can
repeat hooks; durable per-operation memos preserve decisions but cannot make
external side effects exactly once. Hosts must keep extension and tool
registrations compatible across reopen. Memo operations and result publication
are fenced by the root attempt and, where applicable, the intermediate claim.
This also applies to authoritative host reconciliation of pending descendants.
Regression tests cover a rewritten manual receipt, idempotent reconciliation,
and process loss in one child's hook after another child's result is committed;
only the interrupted hook is rerun and its memo is retained. An early-any
park with an already-completed unsafe sibling is also tested across process loss
during the remaining descendant's result hook and then through final wake.
This subset excludes nested before-tool gates at this checkpoint,
deeper intermediate parks, new descendants after a child wake, and independently
scheduled or parallel child handles. Unsupported and legacy unbound cases fail
closed; external job cancellation is not provided.

- [`NestedHost`](../crates/durable/src/nested.rs) holds a per-invocation lock throughout dispatch and rejects even distinct concurrent keyed calls. Its records contain an operation ID and outcome, not a scheduler-owned task and independently awaitable handle. Reusing a completed key checks tool, arguments and replay policy; replay must visit every recorded call in each re-executed scope.
- A pollable nested `Outcome::Pending` persists its reference and polls within the active parent invocation; replay reattaches to that reference without redispatch, including for unsafe children. Polling cancellation, failure, or an `Unknown` poll outcome retains the pending reference; interrupted replay-safe callers can reattach through replay-safe intermediate callers, while unsafe intermediate callers require reconciliation. Once uncertainty has been committed as a blocked parent, reopening does not automatically replay it. An explicit conversation abort does not replay or resume its parent after reopen: it remains blocked until the nested outcome is resolved and the parent is authoritatively reconciled. Upstream instead runs the tool task abort handler and settles it as aborted; this Rust path lacks an equivalent nested external-job cancellation or reconciliation API. Non-pollable pending outcomes remain unresolved and block parent settlement. The runtime seals and waits for the nested host before committing the parent outcome; invocation-scope closure cancels active nested work and marks it uncertain. True parallel parked child semantics remain missing: returning a parent pending outcome cannot preserve live nested children as a park.
- Generic [`TaskStore::commit_owned_tasks`](../crates/durable/src/task_store.rs), task `TasksAny` waits and the task driver provide useful primitives, but a model tool operation is not currently a task owner there, and no atomic transaction binds a nested key and its tool intent to an owned task and parent park. Generic task wake data is not the tool checkpoint/wake API. Passing the existing operation UUID as an owner or treating a pending reference as a task handle would not establish those invariants.
- Dropping the lock alone would not implement parking: duplicate keys could race admission or dispatch, positional identities could depend on scheduling, and the existing seal/inspection rules would still cancel or reject outstanding work. It would also change the established ownership and reconciliation contract without a durable handoff.

An internal [storage-only keyed child admission](../crates/durable/src/keyed_child.rs) now atomically creates a registered child task and a parent-scoped key record with its task ID, tool identity, arguments, replay policy, registration identity, initial checkpoint and restart limit. A duplicate with the same identity returns the original ID; a conflicting identity fails. Older experimental records without the initial checkpoint and restart limit fail closed; there is no automatic migration. Admission requires a current running, non-aborting task parent and a ready child owned by it. Creation advances the parent version to fence abort and settlement traversals, and checks the ownership ancestry; duplicate lookup also checks the recorded child exists and is still owned by that parent. Concurrent admissions, including different keys, can conflict and require a fresh snapshot and retry; an uncertain storage commit requires inspection before retry. The internal preparation must not be composed with separately prepared ownership changes: their ancestry checks see only pre-commit state. This primitive does not acquire an executor lease or validate a registration against a live registry: its eventual caller must do both. It is private and not connected to nested tool execution or exposed as `wait: false`.

A top-level opt-in [`TaskTool`](../crates/durable/src/task_tool.rs) maps a tool call to a conversation-owned generic task. The operation ID is its task ID. The runtime validates the handler against the attached driver and commits the task and a task-backed pending phase together; polling reads the durable terminal task state, including after reopen. A missing driver or registration fails before admission; an interrupted marker invocation is replay-safe because it performs no task effects. Conversation abort marks the owned task and waits for its cleanup before settling the pending tool. A synchronous handler must return before its abort handler can run. Install the same task definition when reopening; to attach the driver before resuming interrupted marker dispatch, use `Harness::open_paused`. Task output is the task's JSON result (a JSON string becomes text). Because generic task failures do not distinguish a reported error from uncertain effects, any failed task blocks the conversation for reconciliation. This is a single top-level task-backed tool, not upstream nested `wait: false`: nested dispatch, tool checkpoints, parallel child handles and a wake payload are not supplied by this adapter. The adapter fails closed outside its registered top-level runtime dispatch.

An opt-in [`AsyncTaskTool`](../crates/durable/src/async_task_tool.rs) additionally runs a registered ordinary async leaf Tool as an owned task in a `StandaloneNoHooksHost`. This host explicitly asserts that no hook policy applies and cannot attach to a conversation runtime. Admission records the Tool specification and a host-assigned implementation identity; dispatch verifies them again. A committed intent is the logical dispatch boundary: a preceding abort prevents dispatch, while a later abort requests cancellation and the driver joins the Tool before preserving its result in an independent receipt. A process loss after intent but before receipt remains uncertain and is not automatically replayed. The host must use stable identities and destination-side idempotency or reconciliation for external effects; the Tool can ignore cancellation or detach work. Receipts are limited to 64 KiB. A synchronous task handler can immediately admit a keyed sealed child through `AsyncTaskTool::start_child_now` using its live admission lease and checkpoint the returned handle. This does not expose admission to an async Tool or implement its park/wake. This path does not implement nested async calls, progress, UI, extension state, or before/after hooks, and is not equivalent to upstream ToolTask or its `wait: false` API. Tests cover intent/abort ordering, shutdown, identity changes, receipt recovery, and task-backed multilevel behavior; hook-enabled conversation dispatch remains unsupported.

For staged and immediate sealed children, admission checks that raw input is an object within 16 MiB and that the schema is valid. The tool prepares the arguments before the normalized value is checked against the schema and size limit; the original input remains part of the keyed identity. Ordinary synchronous TaskTool admission continues to validate its input directly.

A reserved sealed child defers before Tool intent or before-hook execution while its parent outcome awaits settlement, including when another abort graph is uncertain. The driver checks that the Tool intent is absent before returning the child to Ready; after the parent settles it rechecks the task, registration and ownership before any dispatch. If the release transaction cannot acquire the writer lock, the driver retains the reservation and retries that checked transition; an indeterminate commit still requires reconciliation.

A sealed after phase that already has a raw Tool result uses its original intent and receipt evidence when identity acquisition is temporarily busy; it does not claim the Tool was undispatched or invoke it again. The release and retry retain checks for the recorded Tool identity, original dispatch attempt, raw result and any final receipt.

Before a sealed Tool dispatch, an uncertain pending abort graph also defers an already-reserved child while its parent is still running. The retry checks the absent Tool intent and re-evaluates the graph and parent before dispatch.

`StandaloneBeforeHookHost` adds a limited task-owned before-tool phase for a single host-identified hook. Tool argument preparation and the hook must be replay-safe and side-effect-free; the host must change the identity for any hook implementation or configuration change. The hook sees a null snapshot. Before hooks can access durable first-writer-wins task memo under the task lease, attempt, ancestor abort and registration checks; memo keys are bounded to 4096 bytes and values to 64 KiB. A failed memo operation rejects the phase even if the hook ignores the error. `register_tool_with_after` opts a single host-identified hook into the legacy text after callback; `register_selected_tool_with_after` opts in an ordered, host-identified selection captured at registration. Its implementation and configuration must be replay-safe and side-effect-free except for the same fenced memo: the driver durably records a completed Tool outcome before calling it, and after process loss retries the hook from that outcome without rerunning the Tool. A final receipt already committed before interruption suppresses another hook invocation; recovery remains subject to the task restart limit. After may replace successful text output while retaining its details; replacement of other outcome kinds fails closed, and the serialized outcome is limited to 60 KiB. If after does not finish, the known raw outcome remains available for reconciliation through `AsyncTaskResult::AfterIncomplete` and `read_raw_outcome_for_reconciliation`, distinct from a final result. This restricted path does not run after on host-produced blocked, invalid, interrupted, restart-limit, or aborted results. Rich and block result hooks, live conversation extension selection, before-hook sleep, Tool parking and wake with a new intent, conversation attachment, and tool state remain unsupported. Before-tool completion persists rewritten arguments in an execute checkpoint before intent, and the driver revalidates size, schema and registration; a committed intent still has the existing uncertain-outcome semantics. Recovery of an interrupted running preflight is conservative and fails rather than replaying it. If abort cleanup is unavailable, the scheduler may mark the task orphaned; cancellation does not imply a clean terminal state. The standalone host can bind an ordered, host-identified extension selection to its before phase and durable identity; it is an immutable registration-time snapshot, not a live conversation selection. This is a restricted pi-rs extension and does not yet provide upstream's full ToolTask hook semantics.

The standalone `register_replay_safe_durable_tool` path supports host-attested replay-safe `DurableAsyncTool` attempts, keyed replay-safe TaskTool children, and atomic child admission with `All`/`Any` park and checkpoint. Wake invokes a new attempt with ended child IDs, and abort requests cancellation. On success after an early `Any` wake, newly admitted replay-safe tools retain their remaining children and finish after they settle; failures and aborts cancel them. Tasks admitted by the previous experimental version retain its prior cancellation policy. Process-kill tests cover parked recovery and loss before the park commit. `StandaloneBeforeHookHost::register_replay_safe_durable_tool_with_hook` additionally binds one host-identified before/after hook to this same driver. A before pass and rewritten, revalidated arguments commit before the first Tool intent; a park does not run after, and wake retains those arguments without rerunning before. A completed Tool outcome commits with an after checkpoint before after runs, so a process loss in after resumes that hook without executing the Tool again. Hook memo operations use the current task lease, attempt and ancestor-abort fence, and a memo error rejects subsequent accesses and fails the phase even when ignored. Hooks and preparation must be replay-safe; their identity must change with code or configuration. Before-hook block, failed argument preparation, and schema-invalid inputs or rewrites within the checkpoint bounds are committed as failed outcomes before invoking after; after receives a `blocked` or `invalid_arguments` diagnostic, can replace text, and cannot suppress the error or alter unrepresentable metadata. The final `Outcome` retains the error text but not the diagnostic metadata. Non-object or oversized prepared arguments still fail closed without after. The explicit `register_replay_safe_durable_tool_with_content_hooks` opt-in binds an ordered, host-identified extension snapshot and runs the existing block-aware after chain. It commits `DurableTaskResult::Rich` with ordered text/image blocks, details, structured output, attachments, error status and diagnostics; replay-safe parent tools read it as `AsyncTaskResult::Rich`. Block and invalid diagnostics are retained and cannot be suppressed. The Tool's initial outcome still comes from `Outcome`, not a native multi-block Tool result; each selected extension's `after_tool_result` runs first for a single plain-text block, followed by its block hook (whose default bridges legacy text); a later text-result hook is skipped if preceding blocks cannot be represented losslessly. This per-extension ordering adapts pi's single afterTool chain to pi-rs's distinct hook APIs. Every replacement is checked against the final envelope limit before the next hook. The registration identity changes with this dispatch behavior, so older in-flight definitions require their matching implementation. Content and known metadata are bounded, images are validated, and configured structured-output schemas are not supported. The raw outcome may expand beyond the final 60 KiB result limit when projected into both text and structured output; after hooks can inspect and shrink this initial projection, but an oversized no-op result fails the final limit. The separate `register_replay_safe_durable_tool_with_abort_after` opt-in runs the selected hooks on an aborted result after owned children drain, with a distinct definition identity and host attestation that cleanup is replay-safe, cooperative and has no detached work. Its dedicated cleanup reservation records an attempt- and lease-bound intent and a validated receipt; task cancellation checks the receipt and intent versions in the same transaction. A committed receipt is reused after a crash, including at the restart limit; otherwise cleanup retries remain bounded by the task restart limit. Abort cleanup denies all normal memo reads and writes, and an ignored memo error fails the hook. Its mandatory aborted diagnostic and error status cannot be suppressed, and structured output and attachments are unsupported. `read_aborted_after_result` reads the receipt after cancellation; parent `child_result` still reports `Cancelled`. The ordinary content registration retains its previous abort behavior. The separate `register_replay_safe_durable_tool_with_restart_after` opt-in runs at most one fenced restart-limit cleanup attempt after owned children drain, independently of abort hooks. The task remains in `CompletingFailed` during the attempt and ends `Failed("restart limit")`. Its task-, identity-, attempt- and lease-bound receipt is checked together with the final failure transition; process loss after the one attempt never dispatches it again, and an already committed receipt can be recovered. The mandatory `restart_limit` diagnostic preserves uncertainty about external effects. Normal memo is unavailable, as are structured output and attachments. `read_restart_after_result` exposes the result only after failure; parent `child_result` continues to report failure. An existing Tool outcome in the after checkpoint is retained instead of being replaced by a synthetic restart result. The separate `register_unavailable_tool_with_content_hooks` opt-in handles only a host-attested named placeholder known to be unavailable at admission, with an exact stable hook selection and distinct identity. It bypasses Tool resolution, argument preparation and before hooks, commits `tool_unavailable` before the fenced after chain, and never dispatches a Tool or writes a Tool intent. Its error status and diagnostic are immutable, and structured output and attachments are rejected. It is not a fallback for a missing or changed registration or an uncertain dispatched Tool. Hook sleep and live conversation selection remain unsupported. The separate `register_tool_with_interrupted_after` opt-in admits one host-attested cooperative, side-effect-free hook for a sealed unsafe Tool interrupted after its dispatch intent. A dedicated failed-state reservation binds the sealed registration, original dispatch intent and attempt, cleanup attempt and lease; owned children drain first. It denies normal memo access, requires an immutable interrupted diagnostic and error status, and stores a separate supplemental receipt. Both its result and the final failure transition atomically fence the original identity and intent and the absence of raw and final Tool receipts. Known late receipts win and are preserved for reconciliation; transaction conflicts retain the completed invocation and revalidate its evidence and ownership. Missing or changed definitions wait. A checkpoint interrupted before intent is separately settled as not dispatched, with intent and receipt absence checked atomically, and does not run the interrupted hook. Process loss allows at most one cleanup attempt: a committed supplemental receipt can be recovered, but a hook interrupted before saving is not rerun. Abort cancels the hook and removes the supplemental receipt. `read_interrupted_after_result` exposes the supplemental result only after the corresponding failure and only while original results remain absent; `read_sealed_outcome_evidence` still reports Unknown for the external outcome. This path supports one registration-time hook, a null snapshot, bounded text/image output, and no structured output, attachments or memo; it is narrower than upstream and does not enable cleanup for an unavailable or changed definition. `read_sealed_outcome_evidence` exposes terminal sealed tasks' checked no-dispatch, uncertain, after-incomplete and final evidence without authorizing replay. `read_replay_safe_after_evidence` exposes a committed raw outcome or host error from an incomplete after checkpoint on a failed or cancelled replay-safe task, solely as reconciliation evidence; it neither proves hook completion nor authorizes replay. Interrupted execution without that checkpoint has no known outcome. This hooked path does not support unsafe ToolTask execution; the host must ensure replay safety, restore matching identities, and join any work the tool starts. See the [standalone durable documentation](../crates/durable/README.md) for supported child outcomes and limits.

The separate standalone `register_replay_safe_durable_tool` path supports host-attested replay-safe `DurableAsyncTool` attempts, keyed TaskTool children, and atomic child admission with `All`/`Any` park and checkpoint. `register_unsafe_durable_tool` separately admits an unsafe Tool with explicit reconciliation authorization. Either parent may own explicitly registered unsafe checkpointable children: each child's own replay policy and park proof govern recovery, and interrupted or uncertain child results are exposed as `Uncertain` to its parent. A parent success, including one held after an `Any` wake, is withheld and fails with the descendant ID when an owned unsafe descendant has an intent and fails or is cancelled; there is not yet an in-band way to clear this conservative reconciliation fence. A checked, committed park can wake into a new attempt, while an interrupted unsafe running attempt requires reconciliation. Joined unsafe outcomes, pending references and Park proposals are retained independently for reconciliation even when abort prevents settlement; a Park proposal alone never authorizes wake. On success after an early `Any` wake, checkpointable tools retain remaining children until they settle; failures and aborts cancel them. These paths are not hook-enabled conversation ToolTasks; the host must restore matching identities and manage external jobs, effects and parked cancellation. See the [standalone durable documentation](../crates/durable/README.md) for recovery, child outcomes and limits.

An explicitly registered parked-tool cancel callback receives the retained arguments and checkpoint after child cleanup. Its claim and completion records are reconciliation evidence. The replay-safe cancel opt-in retries with the same verified park provenance within the restart limit; external idempotency is the host's responsibility. The separate `register_unsafe_durable_tool_with_park_cancel` opt-in binds a stable content-hook selection and a distinct unsafe Tool definition to either an at-most-once callback or, only with an explicit idempotence attestation, a bounded retryable callback. It authenticates the committed unsafe park proof, original intent, joined park evidence, result, arguments and wait; it rejects existing unsafe Tool receipts, later wake intents, unknown checkpoints and changed registrations. Evidence absence, the current abort attempt and lease, and owned-child cleanup are fenced at claim and checked again immediately before dispatch. Abort receipt and failure recovery retain the original unsafe evidence; `read_park_cancel_evidence`, `read_unsafe_durable_park_evidence`, and `read_unsafe_durable_receipts` expose separate reconciliation facts. Neither callback return nor task cancellation proves that external work stopped. An unsafe callback failure, timeout, or interrupted at-most-once claim whose completion is unknown fails the task for reconciliation and does not run the aborted-result hook. Hooks and cancel must be cooperative and spawn no detached work. A running or already-woken unsafe invocation, unsupported checkpoint, changed definition or inconsistent evidence fails closed; conversation-attached unsafe park cancellation and full upstream cleanup APIs remain unsupported. See the standalone durable documentation for recovery constraints.

Conversation-attached unsafe park cancellation has a claim and receipt foundation, but its callback is not enabled. If the process dies after a claim commits, recovery preserves the original claim and atomically settles its original running attempt with a terminal marker requiring reconciliation. It does not dispatch another callback or attribute the old claim to a new attempt. A late unsafe Tool receipt remains separate evidence and blocks receipt authorization. The process-kill regression also checks that an unrelated graph can progress.

The separate `register_unsafe_durable_tool_with_woken_cancel` contract uses distinct identities and applies only to a woken unsafe execution. The host must first register the exact Tool allocation with `nested_identity::register` and use its `IdentityHandle::update` for every Tool and cancel callback implementation, configuration, and tenant change. This identity is included in a new definition discriminator; tasks using the earlier woken-cancel identity need their original host or reconciliation. Recovery holds a nonblocking identity read lease while validating the live Tool spec and committing descendant aborts; a busy lease defers recovery for automatic retry, while an identity mismatch remains blocked. After children drain, a busy lease defers cleanup before worker reservation and before any cancel claim. A successful lease is retained from reservation through the bounded callback, closing the update window. Updates, including reentrant updates, return busy rather than wait. Other scheduler operations do not retain that identity lock. The 30-second async timeout cannot preempt a blocking or noncooperative callback; the host must ensure cooperation and no detached work. Bypassing the identity handle cannot be fenced. It binds cleanup to the uniquely identifiable post-park execution intent, its wake and committed park proof, normalized arguments and exact checkpoint, and requires the woken attempt's result, joined park proposal, and Tool receipt to remain absent. A cleanup claim records the woken attempt separately from the cleanup attempt and lease; receipt publication and the interrupted failure transition fence those records. An explicit abort drains children before cleanup. On process loss during the woken execution, recovery reserves cleanup only when the original attempt, ownership and evidence are proven. It atomically requests abort for owned task descendants and drains them before cleanup; unsupported owned conversations or uncertain ownership fail closed for reconciliation. A completed callback after process loss leaves the task failed with the original execution outcome uncertain. A late Tool receipt remains independently readable, and blocks cleanup or its finalization. This standalone opt-in does not cancel an unwoken park; use the separate parked registration for that contract. Recovery with owned conversations, uncertain ancestry, multiple woken intents, a joined result or park proposal, and missing or changed definitions remains conservative and may require reconciliation. The callback receives no nested-admission capability, and retry is available only with the host's explicit idempotence attestation and the restart limit. Upstream can cancel a wider set of interrupted woken calls.

Legacy parked cancel registrations use a distinct definition identity; when their provenance cannot be verified, abort requires reconciliation rather than automatic migration.

Cross-version fixtures created by the prior parked-cancel implementations cover parked, claimed and receipted recovery states.

An existing task with the operation ID causes admission to fail atomically; the scheduler does not retry an unchanged conversation indefinitely. The running marker and pending phase bind a versioned adapter identity, including its tool specification, task kind, replay policy and host-assigned definition version. Recovery blocks a missing or changed marker identity; because legacy running markers cannot distinguish task adapters from other tools, they also require reconciliation. Legacy task-pending records without identity cannot resume or start the task driver automatically. Harness-attached scheduler and driver attachment and registry replacement check the bound adapter, task and current handler before recovery. Hosts must assign a new kind or version whenever handler behavior changes: identity is a trusted declaration and cannot authenticate handler code. Register the matching version with `Registry::register_shared_versioned`; `register_shared` registers version 1.

A `TaskTool` handler can stage a keyed generic child, commit a checkpoint and wait, then inspect the frozen wake IDs and version-checked child result on its next handler invocation. If the child changes between its checked read and keyed lookup, settlement conflicts and follows the parent's replay policy; unsafe execution requires reconciliation. Live tool, child-first abort and process-kill tests exercise this path, including an unsafe parent parked while a replay-safe child restarts. This is scheduler task composition behind a top-level tool: it does not create a `NestedHost` tool handle, execute a nested tool adapter, or suspend and resume an async keyed tool invocation.

`TaskTool::stage_child` now constructs a keyed child from an actual TaskTool
definition in a running handler. It validates the input schema and binds the
tool name, kind, version, replay policy and initial checkpoint; the driver also
checks the registered handler identity before committing the child and the
parent transition together. A parent can wait for any child and inspect the
frozen wake IDs and checkpoint on resumption. Tests run two child tools through
the task driver, including process kill, reopen, abort and registration mismatch.
This remains a task-handler interface: admission takes effect at the handler's
settlement, and it is not asynchronous `KeyedHost` / upstream `wait: false`.

`Handler::run_with_admission` receives a borrowed `AdmissionHandle` and can make
a separate child-admission commit for a live TaskTool parent. Its default calls
`run_with_documents`, preserving existing handlers. It checks the reserved executor lease and recorded
attempt, parent abort, ownership and registered child definition, and atomically
creates or reattaches the keyed child. A running generic parent is rejected: the
current scheduler cannot run a child beneath it. TaskTool children can run while
their TaskTool parent remains live when ordinary worker capacity is available;
the reserved overflow worker is only for generic children. The borrowed API
cannot outlive its reservation, and retired or replaced leases fail closed.
The handle is borrowed for the handler call, including driver execution, and
cannot be retained after it returns; abort handlers receive no handle. It is
not available to ordinary async tools and does not provide nested
tool dispatch, hooks, result/wake delivery, async cancellation or upstream
`wait: false`; wiring those requires the separate executor integration. A crash
after admission leaves a durable child to reconnect after parent recovery, not
an atomic parent park. An uncertain storage commit requires reopen and inspection.
Tests exercise admission from the real driver handler, concurrent keyed calls,
parent abort, and the borrowed handle's lifetime. They also exercise both orders
and a race with conversation-root abort, and descendant admission racing its
ancestor's failure publication. The handle cannot survive its own handler's
return to race that handler's result publication.
An unwinding TaskTool handler panic after immediate admission publishes a
redacted failure and follows the owned-graph cleanup path. Running descendants
receive durable abort marks; their executors must return before their abort
handlers run and the parent can settle. Staged handler documents and input
conflicts are discarded, while already admitted children remain owned. A real
driver test exercises standalone and conversation-attached schedulers, safe and
unsafe parents, and an unsafe child with an already-started external effect.
Neither that effect nor its cancellation is proved by the task states. A crash
before the failure is durably recorded still uses interrupted-attempt recovery;
process-aborting panics are not caught.
The failure candidate includes withdrawable queued inputs in foreground owned
conversations even when those conversations are `FailedIdle`. This keeps the
parent in failure cleanup until the abort cascade withdraws those inputs, while
leaving Keep inputs queued. A live-driver regression and OS-kill tests before
and after the panic failure commit verify cleanup and non-replay on reopen.
The driver has four ordinary workers. A test occupies all four with TaskTool
parents and verifies that an admitted TaskTool child stays ready until an
ordinary worker becomes free; the overflow reservation cannot run that child.
Recursively blocking parents can therefore exhaust the pool. This primitive
does not guarantee progress for blocking parents. Synchronous TaskTool handlers
can instead return `Step::Wait` after immediate admission: this parks the task
and releases its worker. Real-driver tests exercise six task levels, two owned
children with any/all waits, checkpoint and ended-ID validation, re-parking,
abort, and OS-kill recovery before parent park, after park and after an any wake.
The tests verify no unsafe leaf re-dispatch once its park is persisted. This is
a synchronous task-handler path; ordinary async Tool execution, its tool-visible
wake and upstream `wait: false` remain separate integration work. Task wait
sets also support existing non-child tasks, an intentional broader behavior
than upstream's owned-task ToolPark rule.

The generic scheduler's live handler can also call `TaskDocuments::stage_keyed_child`. The scheduler validates the candidate registration and atomically commits the key, child, handler documents and parent transition under the captured parent version. The handler can wait on the returned ID in that same transition; a matching persisted or already-staged key returns its original ID. A conflicting identity or task-tool handler fails. New children cannot be staged on successful terminal settlement, and failed handlers discard the staged admission. Document or staged-key conflicts use the existing replay-safe retry policy; a changed parent fences settlement and requires reopening and recovery. This mechanism is limited to generic scheduler handlers: it does not wire nested tools, transfer executor ownership, or provide an asynchronous park.

An additional private `park_any` primitive commits a running generic task's checkpoint and any-child wait together, resolving explicit admission keys to distinct, existing direct children. Its transaction fences the parent, key records and child versions; admission, abort or child transitions that race it require a reload and retry. A private `park_with_documents` variant checks that staged `TaskDocuments` use the same store and task value, and commits those documents and the park atomically while holding the task gate. The caller must fence the parent executor: neither the task gate, a running snapshot nor matching document context proves executor ownership. The variant must not be called while already holding the task gate. Already admitted children are committed separately before the park, so a crash before the park is an interrupted parent execution, not a parked parent. The generic scheduler can execute these registered child tasks and wake the parent after one ends; it leaves a parked replay-unsafe parent untouched on reopen and applies each interrupted child's own replay policy. Its synchronous handlers execute one step at a time, not parallel async tools. A private generic-task wake payload records terminal IDs at wake, then refreshes them under child-version checks in the first reservation transaction, including children that finish between wake and reservation. That reservation freezes the payload across interrupted replay and definition migration until progress, another wait, abort or settlement. A registered task handler can inspect the frozen IDs with `Task::ended_children` and read a direct child with the checked `TaskDocuments::get_owned_child`; this does not expose a wake to ordinary or keyed tools. Its internal fields are also visible when a public Task is serialized; generic task transitions do not produce a durable event history. Records written by the earlier experimental wake-only format retain their older snapshot if reopened. The primitive is not connected to the conversation tool host, does not validate the live registry or supply tool cancellation hooks, and cannot yet be called inside a scheduler handler as a separate commit without reconciling the scheduler's running snapshot and staged documents.

The generic scheduler commits a fresh internal task-attempt UUID with each reservation and clears it when execution stops. When a handler returns and its transition commits, the same task record retains that attempt as a retired identity; reservation and abort clear it. A checked retired-attempt snapshot must be composed with dependent writes and conversation, ownership, and abort fences. Interrupted or discarded handler results do not record retirement, and legacy or standalone `Task::start` records have no such identity. A retired marker records a committed handler transition, not proof that detached work or a separate executor has joined. A private [executor identity binding](../crates/durable/src/executor_handoff.rs) can record a running conversation tool attempt and a running conversation-owned task attempt together. Checked dependent writes must include its conversation, task and binding versions in the same transaction; abort, replay, park or settlement invalidates those checks. Replacing a binding requires a different task attempt and the caller must first fence the old executor. This is a storage protocol, not permission to dispatch: it is not wired to either executor, and neither a stored UUID nor a binding proves exclusive ownership. Older serialized records without an attempt fail closed; older executors that ignore the new field cannot participate safely in this protocol.

An internal `ConversationLease` now acquires the same per-conversation worker mutex as conversation workers and retains it until drop. Acquisition and each checked commit validate the binding and cancellation epoch under the conversation poll gate followed by the task gate; timed version checks in composed batches retain their deadlines. Competing participating conversation workers cannot hold this lease simultaneously, and abort, attempt replacement or a stale transaction prevents its checked commit. A failed commit poisons that lease, requiring it to be dropped and the durable state inspected before a new attempt. It does not own or stop the independently running task-scheduler handler, cannot prove that a previous executor was joined, and is not wired to nested dispatch. In particular, a lock released by process death is not itself proof that task-side external work stopped or can be replayed. A host must establish both executor lifetimes and recovery policy before any tool effects are dispatched.

**Historical quiescent checkpoint:** The private task-driver `try_quiescent_commit` rejects active or poisoned scheduler execution and holds the scheduler mutex through its checked conversation lease. The concurrent driver additionally checks its active-invocation ledger and failure-publication fence; the old serial-handler mutex assumption no longer applies. It does not interrupt running handlers or extend the lease over asynchronous execution or external effects. The private method is not wired to nested dispatch; its busy result requires a later retry outside conversation/task gates.

The `live_tool_and_task_handler_have_no_existing_handoff_window` runtime regression exercises both actual executors rather than a fabricated running task: a scheduled conversation invokes a blocked tool while an attached task scheduler runs a registered blocked handler. Even after a binding is committed, the conversation lease is busy while the tool is live. When the handler returns, its active task attempt is cleared and its retired identity is retained, but while the tool remains live the worker is still busy. Once the tool returns an uncertain outcome, the conversation is blocked and the binding is stale. The retired identity now survives the handler transition, but this alone does not make the live conversation worker available for transfer or establish that detached work has joined.

Existing conversation polling releases its worker lock after driving reaches a persisted pending, hook, or task-wait boundary, and reacquires it before recovery and the next drive. Concurrent scheduling can therefore process a wake without waiting for the polling interval. Live model, tool, and hook futures remain under the worker lock; cancellation epochs fence abort and shutdown. This applies to the existing wait phases only, and does not transfer a live tool executor or implement durable tool suspension.

The missing integrated transition is not safely supplied by adding a scheduler-only retirement marker. The conversation must commit a distinct suspended tool phase and release its worker without treating the handoff as a `Pending`, `Unknown`, or terminal `ToolReply`; the scheduler must commit a distinct retired/transfer state, its attempt identity and staged documents at the handler settlement boundary. Their token and child ownership must be atomically related, or intermediate commits must have explicit fail-closed recovery. Abort must invalidate the token and drain owned children even if the scheduler handler has already returned; reopen must distinguish an interrupted unsafe run from a committed suspension. Current `NestedHost::seal_and_wait` cancels or rejects outstanding nested work, and the tool reply has no checkpoint/wake payload. Those changes, plus tool-visible wake data and real tool-executor cancellation, are required before this can be an end-to-end handoff. A scheduler-only transfer would still face the live conversation worker and could strand a `Running` task on abort or reopen. Upstream still describes owned `wait: false` children and a parked parent at [pi `76c79d8`](https://github.com/earendil-works/pi/blob/76c79d8bbe66993f2006b3c070544ca7c61150de/packages/durable/README.md#tools-that-park).


Tests cover competing prepared admissions, keyed park races with admission, abort and child transitions, identity and ownership validation, child replay policy, scheduler wake and abort across reopen, atomic document/park commits and conflicts, and uncommitted versus committed admission. A staged timed signal to a waited-for child retains its deadline fence when composed with the park; expiry rolls back the signal, document changes and park together. A process-kill regression now interrupts an actual generic task handler after child-wake reservation: replay-safe recovery sees the same frozen wake, while an unsafe interrupted handler is not reinvoked. It does not exercise a conversation-tool transfer. The conversation uses a per-conversation worker, poll gate and cancellation epoch; the generic scheduler instead owns a running task reservation and releases its task gate while invoking a handler. Actual transfer still needs scheduler and conversation integration that holds the correct worker/poll fences before the task gate and retires old work before replay. A separate commit from within the current handler would invalidate the scheduler's captured task version. Further work must integrate scheduler-backed tool execution with that lifecycle, expose wake information to the tool, and define cancellation and settlement before claiming parallel parked-tool compatibility. Existing nested replay and detached-child tests remain relevant but do not establish these guarantees.

Custom JSON-object documents have version-checked writes and deletes, historical reads at recorded revisions, and checked batches that compose document changes with prepared task writes. Admission can atomically compose checked document operations and task creation; conversation forks copy eligible conversation-scoped documents. These are narrower than upstream document drafts, lifecycle, observation, upstream document incarnations and lazy initializers, deferred visibility and general session transactions. See the [document API](../crates/durable/src/document.rs) and [transaction tests](../crates/durable/tests/document_transactions.rs).

## Verification baseline

For the already implemented subsets, run `cargo test -p durable-store` and `cargo test -p pi-rs-durable`; the standalone example `cargo run -p pi-rs-durable --example resume -- start DB_PATH` followed by `resume DB_PATH CONVERSATION_ID` demonstrates admission across two processes, not full upstream compatibility. Run upstream tests against the pinned upstream revision when implementing a specific compatibility gate. For crash cases use process termination and controlled barriers, not graceful shutdown or timing-dependent sleeps. No general exactly-once guarantee follows from local persistence.

### Opt-in provider request bodies

A host can install a `model::ProviderAdapter`, then select its stable, versioned
ID for a settled conversation with `Harness::select_provider_adapter`. Selection
is persisted (including in fork snapshots); after reopening, install the same
adapter and selected extensions on `open_paused` before resuming. A missing or
mismatched adapter fails closed. Unselected conversations continue to use the
existing `Model` interface. Core and built-in providers are unchanged.

The adapter prepares the provider JSON body without dispatching. The selected
`BeforeProviderRequest` hooks receive `{model, payload}` in selection order and
return `Replace({"payload": ...})` or `Pass`. The model here is the configured
model name, not upstream's full model descriptor. Each replacement feeds the
next hook. The runtime rejects hook errors, malformed replacements, non-object
or over-8-MiB bodies, then calls the host's provider-specific validation before
dispatch. The host must implement both validation and guarded dispatch, and
must send exactly the validated body while enforcing authorization, endpoint
and budget policy. The adapter is trusted code; the runtime cannot enforce its
internal behavior. Hook failures deliberately fail closed, whereas upstream
reports the error and continues the chain (upstream pi commit
`1cfb326bfcc5c221526809fa081c4ff85b459847`,
`packages/durable/src/harness/generation.ts` and `CHANGELOG.md`).

The attempt carries the committed conversation and request IDs, turn, retry
count and restart count. New generation attempts after retry or recovery get a
new request ID. Hook context contains the persisted conversation snapshot and
request-scoped durable memo. Bodies and arbitrary hook side effects are not
checkpointed: hooks and preparation run again for each attempt and should use
memo for stable values. Cancellation stops preparation, hook execution or
stream collection, but cannot prove a remote request did not execute; recovery
settles the abandoned request as unconfirmed. As upstream, compaction bypasses
this generation hook. Unlike upstream pi-ai, provider-internal HTTP retries or
body rebuilds are not intercepted; adapters must avoid hidden rebuilds or guard
them themselves. This interface does not retrofit built-in provider clients,
settlement, exactly-once network execution, or automatic adapter installation.

**Live executor observation:** `worker_activity()` returns a shared in-process view of task handler attempts, independent summary jobs, and scheduled conversation drivers, including conversation poll sleeps. `subscribe` delivers coalesced snapshots beginning at attachment; slow readers can skip transitions. `snapshot_with_revision` reads the worker list and its process-local change revision together; the revision also changes for registry replacement and failed migration even when the worker list is unchanged. Summary entries are keyed by operation ID. Guards disappear on completion, cancellation or unwind; multiple drivers of one conversation have separate entries. It includes scheduled conversation lock contenders, but does not include direct `Harness` drives, durable waiting tasks, or recovery work. Empty does not imply durable idleness, and the view alone cannot implement upstream `onWake` or an atomic wake decision. See [worker activity tests](../crates/durable/tests/worker_activity.rs) and [summary worker tests](../crates/durable/src/summary_worker_tests.rs).

**Retry worker release:** Scheduler-owned conversations park outside their worker lock while a persisted model retry deadline is in the future. Another scheduled driver can acquire the worker and abort remains responsive; the persisted deadline still controls the next model request. Direct `Harness` execution retains its existing awaited retry behavior. See [retry integration tests](../crates/durable/tests/model_retry_integration.rs).

**Commit notifications:** `Store::subscribe_commits` exposes the current sequence and coalesced notifications after successful local mutation batches. Failed and read-only batches do not notify. The subscription is scoped to one store instance; writes through another SQLite connection are reflected when a new subscription attaches, but do not wake existing subscribers. `Scheduler::subscribe_changes` combines these with worker lifecycle, task registry changes, failed task migrations and task-driver stops as coalesced hints. Registry and migration changes can produce unchanged worker snapshots, and the returned views are not an atomic wake decision. These hints also drive the opt-in combined wake subscription described below. See [store tests](../crates/durable-store/tests/store.rs), [worker tests](../crates/durable/tests/worker_activity.rs), and [wake tests](../crates/durable/tests/task_wake_snapshot.rs).

**Generic task wake hints and snapshot:** `Driver::subscribe_wake` supplies a
single initially signaled, capacity-one coalescing channel. `wake_snapshot(now)`
inspects generic task readiness, blocked definitions and the nearest future
durable deadline without invoking handlers or migrations. The standalone task
scheduler provides the same view. Unlike upstream
[`onWake`](https://github.com/earendil-works/pi/blob/c1d4b0ac3e35dc4eb1c5d00d90bf54003cf517c0/packages/durable/src/harness/scheduler.ts#L566),
notifications are hints rather than changes to `{active, at}`; polling continues,
conversation scheduling is excluded. The driver snapshot uses a separately published definition view and the task gate, so it does not wait for a running handler; it still can wait for a task commit or migration under that gate.
Scheduler and driver signal delivery is fenced with inspection; direct TaskStore
writes are outside that protocol. A child stays blocked when an ancestor's
persisted definition is incompatible with the registry, including after reopen;
restoring a compatible definition lets the child run. Satisfied waits with blocked definitions do not count as active; abort
cleanup candidates may still depend on conversations. Fail-fast sibling cleanup
is not independently represented. See [snapshot tests](../crates/durable/tests/task_wake_snapshot.rs).

**Conversation readiness:** `runtime::conversation_wake(store, id, now)` reads a
persisted conversation without driving it or consuming signals. It distinguishes
ready, parked with an optional future deadline, and unknown. Retry and tool-gate
deadlines, pending signals, and all-terminal hook children are inspected; failed
idle and blocked phases remain parked. Running operations, external pending work,
abort cleanup, nested recovery, and terminal task-backed tools with unchecked
adapter identity are unknown. This is a phase-level hint, not upstream's combined
`wake()` or `onWake`: it omits worker activity, task scheduling, independent
summaries, and handler availability. Reads across records are not an atomic
snapshot; callers must recheck before acting. See [tests](../crates/durable/src/conversation_wake_tests.rs).

`RuntimeOwner::wake_snapshot(now)` combines conversation readiness, generic task
readiness and local workers. It retries if the local commit sequence or worker
revision changes during inspection; sustained changes return an error instead
of an inconsistent result. Unknown conversations are returned separately and
must not be treated as idle. `RuntimeOwner::subscribe_wake` attaches to scheduler
changes before taking the initial snapshot and delivers coalesced `{active, at}`
values through `WakeDelivery`. Unknown conversations force `active: true`;
a later snapshot error reports the failure and offers `{active: true, at: None}`.
A failed callback is retried on the next change or explicit kick. The handle's
kick recomputes with the supplied clock; it does not run work or arm a timer.
Dropping the handle or shutting down/dropping the owner stops delivery, but an
already claimed callback may start or finish afterwards. The runtime must stay
running and callbacks must not block. Snapshot reads can wait on storage gates.

This opt-in subscription differs from upstream `onWake`: it is attached after
opening, uses Tokio scheduling rather than a microtask, and conservatively marks
unknown work active. Values are coalesced and can become stale before callback
execution; external SQLite writers do not notify the local subscription. The
host must arrange its own timer for `at`, resume work as appropriate, and kick
or otherwise cause a change when it fires. Snapshot errors and callback errors
are passed to the supplied error callback rather than upstream host reports.
See [subscription tests](../crates/durable/src/conversation_wake_tests.rs).

Nested pending-job reconciliation is a pi-rs host API with a narrower boundary
than upstream's nested task scheduler. A host can record a verified terminal
result or confirmed cancellation against the exact persisted operation and
opaque reference. A replay-safe direct parent can reattach to the recorded result
when its replay identity and policy still match; other parents require separate
authoritative reconciliation. Interrupted calls without pending references and
unresolved intermediate callers remain outside this automatic path.

The opt-in bounded keyed nested batch admits calls sequentially and polls their
persisted pending jobs concurrently, preserving key and operation identity over
reopen. It is not upstream's independent task admission or parked parent: the
conversation worker remains active and abort requires local polling to stop.

An opt-in keyed parent can instead call `call_keyed_unpolled` and then
`suspend_pending`. Once its invocation has returned and the nested host has
sealed and joined local calls, the existing blocked-operation transition
persists an explicit suspension marker and releases the conversation worker.
For a replay-safe parent, including one with selected extensions, the scheduler polls
pending children whose registered tools opt in to polling, commits their results
with conversation and child version checks, and automatically replays the
parent after all children have terminal results. Polling releases the parent
conversation worker; process-local poll rounds are serialized, while children
in a round are polled concurrently. Reopen resumes polling without redispatching
the accepted jobs. Abort fences polling and replay and retains unresolved
references for reconciliation. With selected extensions, a terminal child result
is staged before the ordered legacy and rich result hooks run; their committed
result is visible before the parent wakes. The hook receives the persisted
invocation snapshot and stable child memo. A crash during a hook can repeat it,
so external hook effects require idempotency or memoization; a completed hook
result is not repeated when the parent subsequently restarts. The host must
preserve extension and tool registration semantics across reopen; the journal
does not bind a versioned implementation identity. Extension-provided tools
remain unsafe for replay, and an extension override of the parent prevents
automatic parent replay. Process-kill tests cover polling, interrupted hooks,
and a parent killed after its child's hook committed.
Older blocked records that never committed an explicit suspension marker are
not inferred to be safe to replay. Nested results run legacy, rich and opt-in
ordered block hooks in that order. Block-aware keyed callers can read persisted
blocks after recovery; outcome-only callers fail closed if a hook changes the
blocks. This explicit access to nested model-output blocks is a pi-rs extension:
upstream nested callers receive result metadata rather than model-facing output.
The built-in image fitter continues to skip nested results.
This is a restricted external-pending-job bridge: it does not start an
independent task, cancel a remote job, store a tool checkpoint, implement
wait-any, or connect the private `nested_suspension` protocol to `TaskTool`.
Tools without polling support and unavailable, timed-out, panicking or uncertain
polls remain blocked for a later retry or host reconciliation. Abort can remain
blocked until a host confirms child outcomes and reconciles the parent. A crash
before the blocked transition is an interrupted tool attempt, subject to the
normal replay policy. See
[suspension tests](../crates/durable/tests/nested_explicit_suspend.rs).

A private versioned nested-suspension record now persists a bounded immutable
snapshot of pending job identities and opaque references with a checkpoint,
abort marker, and executor state. Conditional retirement, claim, and abort
transitions fence stale snapshots and claim-dependent writes. This is only a
storage prerequisite: retirement requires external proof that the old executor
stopped, and future integration must atomically compose conversation, task and
abort fences. It does not park a parent, release its worker, own or poll jobs,
or provide upstream task wake semantics.

Opt-in merged watch progress operations derive bounded Chord patches from the immediately preceding uniquely matching tracked running change. Other cases use replacements; overwritten pre-tracking history and original upstream operation batches are not reconstructed.

Opt-in document operation retention supports bounded decoded Chord operations over nested objects and arrays for existing versioned documents. UTF-16 truncation that would create an unpaired surrogate, sparse writes and unsafe or unrepresentable inputs are rejected; older batches and general Chord drafts remain unsupported.

Standalone document watches offer a bounded, acknowledged callback listener with explicit stop, abort and host source-close signals; automatic source-lifetime detection remains limited to harness-owned merged watches.

Self-delivery and its typed wait share the task transition transaction. Signal-revision fences reconcile concurrent deliveries; the API remains a restricted task-handler transaction, rather than upstream’s general `tx.signal`. See [self-signal tests](../crates/durable/tests/self_signal.rs).

Task-handler document and application-entry updates may precede `signal_at`, and their version checks commit atomically. Upstream permits signals after document drafts but rejects a sequential signal read after an entry table write; the latter is a pi-rs extension. Store-bound `HostTransaction` supports checked document writes and multiple typed signals per target with staged duplicate semantics and reconciled deadlines, with an explicit atomic wake using a committed or staged signal for a typed wait; task candidates staged before delivery are observed, while later writes to signalled task records and raw signal namespace writes are rejected. Sequential calls after a delivery are a pi-rs extension: upstream `Tx` rejects reads after a table write. It does not provide general upstream `tx.signal` composition. See [task tests](../crates/durable/tests/task_document_transaction.rs) and [host tests](../crates/durable/tests/host_signal_transaction.rs).

Host transactional signals reuse the task-handler staging protocol. Different target/key observations retain task and signal-revision CAS fences; duplicate staged keys keep their first value, and incompatible observations force a conflict. `wake_with_signal` (alias `wake_with_staged_signal`) atomically consumes a committed or staged receipt and wakes a typed wait, selecting the first available key in wait order. `wake_at` additionally supports deadline and time-only typed-sleep wakes with a caller-supplied clock: available values take precedence, and otherwise missing keys expire atomically at or after the deadline. Ambiguous duplicate records and consumed wait keys fail closed; a task candidate staged before delivery is supported, but a wake cannot follow a candidate task write and later writes to signalled targets remain excluded. This explicit atomic wake is a pi-rs API, not upstream’s general task-record replacement. See [host signal tests](../crates/durable/tests/host_signal_transaction.rs).

Normal Scheduler/Driver polling follows the same signal-first deadline ordering as upstream `sleepWake`, including at the boundary, and commits the wake and receipt changes with task and signal-revision fences. Unlike upstream’s normal well-formed records, mismatched identities and ambiguous duplicate receipts fail closed. A consumed receipt advances the signal revision. The [scheduler tests](../crates/durable/tests/scheduler_typed_wake.rs) cover delivery races, driver polling and process kill/reopen.

Host `wake_at` does not schedule a timer: callers supply a scheduler-consistent time and retry the whole transaction after conflicts. Timeout markers, the task wake and checked document writes commit together; delivery races are fenced by task and signal revisions. See [timeout tests](../crates/durable/tests/host_timeout_wake.rs).

**User image admission:** `UserImageAdmission` is an opt-in pi-rs admission
operation that fits user blocks against the selected model before the atomic
submission commit. It returns and stores preparation notes, supports queued
steering and follow-ups, and fences concurrent model changes. Fitted resets
support conversation-scoped request deduplication; host `onYield` hooks may
explicitly prepare continuations against the lifecycle model profile. Upstream
instead asks the host to call `fitImages` before submit; other pi-rs input
paths remain unchanged.

**Standalone wake callback delivery:** [`wake_delivery`](../crates/durable/src/wake_delivery.rs) provides a Tokio-scheduled, coalescing callback lane for host-supplied `{ active, at }` values. It suppresses only successful equal deliveries, retries failures on a later publication or kick, and permits callback reentry and nonblocking shutdown. A callback already claimed by the delivery task may start or finish after shutdown; the supplied runtime must remain running. The primitive is also usable independently. `RuntimeOwner::subscribe_wake` now connects it to the combined snapshot and scheduler hints, as described above; it does not connect built-in timers or upstream host reports. See [delivery tests](../crates/durable/tests/wake_delivery.rs).

### Task-backed nested handles (upstream 04fd0897)

`TaskTool::start_child` exposes a serializable keyed handle for the existing
task-backed child admission path. A handler can checkpoint handles, wait on
their task IDs, inspect `ended_children`, and retrieve fenced terminal results
after wake or reopen. The child and the parent transition commit together.
Unlike upstream `executeTool(..., { wait: false })`, this applies only to
registered task-backed tools, starts them at transition commit, and does not
run the ordinary nested tool pipeline or provide an asynchronous result wait.
It does not change normal `KeyedHost` calls or introduce independent ordinary
tool executors.

Upstream §7.3 aborts all live nested calls before parent settlement and waits
for cleanup. Newly admitted TaskTool parents and nested TaskTool children now
carry a durable adapter type. A completing TaskTool atomically marks all its
live direct nested TaskTool children and their foreground ownership subgraphs
for abort; it waits for owned foreground work before becoming terminal. Generic
owned tasks, including tasks of the same registered kind, are not selected by
this normal settlement cleanup. Generic task success remains unchanged. The
stored outcome and abort marks survive restart. A TaskTool handler error enters
this failure path; a panic or process death is governed by interrupted-task
recovery. A child cleanup failure is terminal and does not replace the held
parent result. As in upstream's fault rule, an abort handler's error, unwinding
panic or nonterminal return becomes a failed child; a failed outcome commit or
process death can still require cleanup replay. External effects require the
registered abort handler to clean up and cannot be guaranteed cancelled by an abort mark alone. Cleanup of owned
conversation subgraphs requires an attached conversation harness; the standalone
scheduler fails closed when it encounters a foreground conversation edge.

Legacy task records have no adapter type and remain generic; legacy keyed child
identities are not silently upgraded. Drain or reconcile old work before using
this behavior, and do not reopen new records with an older scheduler. In contrast
to upstream, child admissions staged by a handler that returns `Step::Fail` or
an error are discarded, generic owned foreground work also delays the parent's
settlement, and an explicit abort arriving during `Completing` preserves its
held outcome. Ordinary nested-tool hooks, autonomous ordinary Tool dispatch,
and cancellation of a running synchronous handler remain unsupported.

**Shared task schema integration:** The persisted TaskTool marker is part of the schema shared by the runtime and store. True survives task updates and document retirement; explicit false and missing legacy fields both decode as false, and false is omitted on serialization to retain the previous JSON shape. Legacy records without the marker cannot safely be identified as TaskTools.

### Checkpointed nested pending-job suspension

`KeyedHost::call_keyed_unpolled_with_id` exposes the existing keyed journal
operation ID and `suspend_pending_with_checkpoint` persists a bounded JSON
checkpoint with the parent suspension. Once all captured pending jobs settle,
`pending_wake()` supplies the checkpoint and ended operation IDs to the replayed
root invocation. The same wake survives a process death during that replay,
including after the replay commits another child's before-tool gate; recovery
retains it only for the same operation. A replay-unsafe `KeyedTool` may opt in
with a positive host-declared `unsafe_park_version` and checkpointed park. The
park commit binds the prior tool attempt, tool spec and version; wake verifies
the current unsafe registration and claims a distinct attempt before running.
Recovery can re-arm a wake only before the new claim and only when the prior
attempt still matches. A crash after claim does not replay that invocation.
The tool must branch on `pending_wake()` before pre-park effects and must not
leave detached effects; host declarations and external effects cannot be
verified by the runtime. Process-kill and abort tests cover both sides of that
boundary and the ordinary nested `Tool` path without re-dispatching the child.
A test-only stop after each actual conversation commit also exercises process
kill immediately after wake persistence and after the new attempt claim. The
former recovers the parked wake; the latter requires reconciliation even if
the handler had not started. Abort and changed spec, version or replay policy
remain fenced on both sides of the claim. These hooks are absent from production
builds.

This is a bounded extension of the existing external-pending path, not upstream
`executeTool(..., {wait: false})` or `ToolPark`: initial child execution is
awaited, operation IDs are not independently scheduled task handles, early
`any` is limited to the bounded keyed-intermediate subset, and checkpointed before-tool gates,
non-opted-in unsafe parents, tool sleep and independent synchronous children
are unsupported.
Abort fences local replay but does not abort an accepted remote job. TaskTool
handles cannot safely be reused here: their owner is a durable scheduler task,
whereas a `NestedHost` call is an operation journal entry owned by a live tool
invocation. A complete integration still needs an atomic parent tool-task
handoff, executor fencing, task-owned keyed admission, wake/park transitions,
and ordinary nested hook and cancellation semantics; it cannot be achieved by
relabeling an operation UUID as a task ID.

### Fail-fast sibling cancellation

Upstream pi 04fd0897 marks the other live children after a non-completed
outcome, then waits for all children to settle before resuming their parent.
pi-rs marks sibling ownership graphs in separate scheduling passes; failed and
cancelled outcomes trigger the cascade. Before publishing a handler result,
the scheduler rechecks fail-fast ownership and fences concurrent graph puts;
a relevant abort discards staged output and drains that graph. Graph-only conflicts revalidate ownership and retry the original checked batch
up to eight times without rerunning the handler. Persistent contention or document conflicts
follow the invocation's replay policy. Recovery holds interrupted invocations under pending fail-fast graphs
until their marks have been persisted. A completing TaskTool
similarly defers interrupted nested TaskTool roots until its nested abort mark;
direct generic children are not included in that normal settlement cascade. A
running synchronous handler is allowed to return before its abort cleanup and
terminal transition. The attached runtime also drains foreground child-owned
conversations; standalone scheduling supports those graphs when opened with a
conversation runtime. Plain standalone scheduling rejects them. Explicit
`cancel` uses durable child-first cleanup when a foreground conversation is owned;
otherwise it retains its immediate-cancellation semantics.

**Late ownership:** A successful result prepared as `Succeeded` is changed to
`Completing` if a graph-fenced retry finds newly admitted owned work. The same
checked transaction retains the staged documents, signals, keyed children and
runtime updates. A version-only rewrite is accepted only when the running task
is identical, including its attempt and abort state; only checks tied to that
version are rebased, preserving signal deadlines and independent observations.
Changed tasks, aborts, real document or signal conflicts and exhausted graph
retries still follow their existing conflict or cancellation paths. Task-owned
documents retire only when the held outcome becomes terminal. The tests cover
same-value rewrites, deadline and abort fences, staged effects, runtime updates
and process death after the held outcome commits. A process death before that
commit still follows the recorded replay policy and cannot recover an
uncommitted non-replay-safe external effect.

### Identity-bound nested pending recovery

Unsafe parks require the exact nested tool allocation to be registered with a
non-secret, host-declared implementation/configuration/tenant identity. A bound
job under any parent requires a matching registration before polling. Identity
is captured on child admission and
rechecked under a nonblocking read lease through the poll and its checked
commit. `IdentityHandle::update` takes a nonblocking write lease, returns busy
instead of deadlocking on reentry, and clears the identity before calling the
host's configuration update so a panic fails closed. The host must perform all
configuration changes under that handle. An unsafe parent additionally binds
its own live, host-declared identity and version; it is checked at invocation,
park, poll and wake, not cached by allocation. The host must restore equivalent
identity registrations before reopening.
Unsafe resume leases the parent and all child identities before claiming an
attempt and pins those exact tool allocations through its checked result commit.
Registered unsafe initial dispatch leases and records its parent definition
before argument preparation and before-tool hooks. An older busy-attempt marker
without that preparation proof requires reconciliation. Older experimental
unsafe park proofs without parent identity fail closed even after child binding;
they require authoritative parent reconciliation.

For compatibility, unbound pending jobs under replay-safe parents retain legacy
polling; their records cannot verify the backend or tenant, so the host must
restore the original backend. Unsafe parks never poll or resume unbound jobs.
Registered tools whose identity is unset cannot dispatch new children or poll
legacy jobs, including after an update panic. A temporarily busy registered
identity causes suspended polling to retry on a bounded timer without holding
the conversation worker lock; a changed or missing identity does not retry.
An operator who has
independently verified the original backend and reference can use
`bind_nested_pending_identity` to bind a missing identity to the currently
registered tool; the reference, operation and conversation versions are checked.
A conflicting existing binding cannot be overwritten. Authoritative terminal
reconciliation remains available instead. A bind is a host assertion and does
not itself verify the remote system.

Upstream returns either `ToolPark` or a result. This API first requests a park
and then returns a normal reply. For unsafe parents, a `Failed` or `Skipped` reply rejects the
park and is preserved in the blocked reason while unresolved children require
reconciliation. Safe parents retain the existing suspension behavior.

**Run failure architecture:** The runtime always receives an `Arc<dyn Model>` and has no typed missing-model result; an unavailable selected provider adapter is a recoverable host configuration error, not proof that the model is missing. Host shutdown during a model request is recovered as `AbandonedModel` and currently consumes the restart limit rather than a separately persisted request-interruption retry budget. Scheduler worker errors and panics leave work recoverable and report an in-memory worker error; uncertain storage failures poison the owner. Task-graph orphan states belong to generic child tasks, not the conversation generation. Consequently `no_model`, `interrupted`, `faulted`, and `orphaned` do not yet have safely identifiable terminal conversation settlements. Supporting them requires typed host signals and explicit terminal/retry decisions, preserving abort and uncertain-commit fences.

A conversation run is currently a persisted phase, not a task-graph task, so neither a request ID nor a child task ID identifies the run's generation. Transcript entry IDs identify immutable storage batches; they are not exposed per message and are not upstream `run.first`. True parity requires a persisted generation identity and lineage tied atomically to admissions, resets, continuation, fork, transcript placement, and settlement; existing IDs cannot be substituted safely.

**Multi-reset settlement investigation:** Atomic replacement across several block-bearing resets needs an ordered, multi-entry transcript batch, not only a relaxed final-state check. The batch must validate every reset against its preceding state and block identities, preserve intermediate occurrences for historical forks, and atomically install all entries and the final head with the failure and selected inputs. Retry must rebuild that proof from the latest inbox and respect abort, summary and write ordering. Current single-entry preparation and `BlockResetProof` validate only the last block-bearing reset, so that extension remains a separate increment.

**Harness-wide idle wait:** `Scheduler::wait_for_all_idle` traverses foreground work from all ownerless conversations in one storage snapshot, corresponding to upstream `Harness.waitForIdle`. It excludes background subtrees and inputs parked after a failed or aborted run, polls every 100 ms, requires a running driver for live generic tasks, and observes rather than fences concurrent admissions. Cancellation stops only the wait. See [idle tests](../crates/durable/tests/conversation_idle.rs).
**Transcript batch increment:** The low-level transcript store can prepare several ordered entries and their intermediate cursors under one checked atomic head update. Each block binding is validated independently, and historical transcript forks may capture an intermediate cursor after commit. Conversation settlement does not yet use this primitive: runtime observation and fork provenance still require a proof linking every intermediate reset to the same atomic commit, as well as verified intermediate configuration, reset, and write state.

**Atomic transcript proof increment:** The transcript store can verify that a contiguous cursor chain, an application-owned anchor and independently supplied exact cursor-bound snapshots were written in one commit. The proof also checks the anchor’s document cut against an independently supplied revision. It does not derive reset states, establish trust in the anchor or derive the correct revision, and is not yet connected to runtime fork or continuation logic; those checks remain required before use for conversation settlement.

**Fork anchor authentication increment:** Historical message-occurrence and positioned forks require their observer record, reserved fork snapshot, and conversation root update to belong to the same tracked store commit, with a recorded document cut. Rewriting either anchor record in a later transaction, including rewriting both together without the root, fails closed. This hardens existing single-position anchors; it does not yet derive or authenticate intermediate reset states in a multi-entry transaction.

**Anchored reset derivation increment:** Ordered reset cuts can be derived from the current version-checked conversation root after authenticating its observer/fork anchor and checking the fork-visible baseline fields. The derivation replays the pending reset prefix, block bindings, context identities, and write-placement limits on clones. The existing single block-reset placement uses this path. The derived cuts are not yet committed as a multi-entry batch or used to authorize intermediate forks; atomic continuation across multiple resets remains unsupported.

**Historical reset-baseline increment:** Fork snapshots written while block resets are pending retain the serialized conversation root at that commit. The runtime authenticates the snapshot against its observer and root commit, including a digest of the captured baseline payload, then restores its transcript and block bindings and recovers its document revision after the live root advances. Earlier captured baselines without this digest cannot be used for historical proof replay. Older snapshots without this payload remain usable by the current-version reset path but cannot supply a historical reset baseline. A baseline in `ToolFinished` is rejected because its separately stored pending tool-result metadata is not historically captured. This does not yet bind intermediate cuts or enable atomic multi-reset continuation.

**Explicit snapshot transaction check:** The store can verify an explicitly named snapshot and a runtime root were written in the same tracked commit even when several snapshots share that commit. It rejects missing roots, wrong namespaces, rewritten or deleted snapshots, and leaves the existing unique-snapshot lookup unchanged. This check does not validate a manifest, derived state, observer anchor, or document-cut semantics; it is not yet used to authorize intermediate forks.

**Final fork anchor with multiple snapshots:** The runtime checks the exact canonical snapshot and root against the observer commit, so another snapshot in that commit does not invalidate the final anchor. Anchored reset derivation falls back to selecting the unique canonical twenty-digit snapshot in that same root commit when the older unique-snapshot lookup is ambiguous, then authenticates its observer and captured baseline. Legacy single-snapshot lookup remains available. This does not authorize intermediate snapshots; atomic multi-reset writing and intermediate forks remain unsupported.

**Private reset manifest format:** An unconnected versioned format bounds the number and encoded size of reset cuts, checks structural cursor ordering and identities, and compares predecessor, anchor, document revision, and independently derived cut digests with caller-supplied expectations. It does not query storage, prove cursor links or document cuts, write manifests, authorize forks, or change continuation behavior.

**Private manifest candidate lookup:** A bounded lookup can find a raw candidate by transcript cursor and verify its same-commit entry, canonical observer and root anchor, and independently supplied document revision. The store records version-bound document cuts and the checked `DocumentRevision` fence for new fork snapshot writes; older snapshots are not backfilled. A checked prefix fence detects concurrent candidate puts, and ambiguous candidates fail closed. This only returns raw bytes: it does not decode the manifest, prove the cursor chain or reset state, authorize forks, or enable automatic multi-reset placement.

**Reset replay hint scaffold:** Private manifest candidates can expose size-bounded, structurally checked predecessor and cut hints for locating evidence. These hints are untrusted: callers must authenticate the predecessor and transcript chain, independently derive every cut and validate the complete manifest binding before authorizing a fork. Production multi-reset failure settlement and intermediate historical forks are not yet enabled.

**Stopped-model reset proof increment:** The private reader can replay an authenticated stopped-model predecessor through failure and ordered resets, compare a canonicalized digest for each cut, and fence the manifest and same-commit transcript evidence. Canonical JSON ordering is necessary because hash-map iteration can differ after reopening. This proof is not yet connected to public forks or production failure settlement.

**Atomic replayable failure with multiple block resets:** When a persisted stopped-model failure, a persisted turn-limit or restart-limit decision, or a nothing-to-answer failure with no active content blocks, uses `after_failed_run: continue`, at least two queued resets include block content, a replacement input is queued, and no pending summary or unplaced write prevents the boundary, the runtime settles the failure, places resets in admission order and starts selected inputs in one transaction. It replays from the latest admission baseline on a conflict. Each reset has its own same-commit transcript entry and identity. Complete intermediate entries can be forked by position or occurrence ID after independently authenticating the predecessor, replaying the failure and reset states, checking the transcript chain and final snapshot, and fencing predecessor entries, runtime anchors, and manifest evidence during child creation. Tests cover an admission race, process kill, continuation and historical forks after reopen. Turn-limit and restart-limit failures first persist a terminal decision with the selected nonzero limit, observed count, and an authenticated earlier runtime snapshot. Replay checks the bound, the source phase and counter, the unchanged transcript, and that the decision is the next runtime commit after its source. It fences both snapshots and observer records, and uses the saved decision after restart even when host options change. Admissions racing the decision trigger a fresh selection; admissions after it remain queued. Legacy counter-only checkpoints cannot authorize historical limit-failure proofs. Other failure kinds and cases outside these bounds retain the staged behavior. Intermediate message positions inside a reset batch remain unsupported. Within a synchronous traversal, validated reset batches and their fences are memoized per store and commit; the cache is discarded afterward. The proof still scans retained transcript history and has no benchmarked time bound.

**Cached reset proof fencing:** Cached proof hits recheck their original version and prefix fences. Nested proof evidence is retained in the dependent proof and in the transaction that creates a fork; conflicting evidence fails closed. A concurrent evidence rewrite is covered by the multi-batch regression.

**Atomic reset save fencing:** The synchronous proof scope covers preparation and commit of an atomic reset save, so nested predecessor evidence reaches its CAS transaction. Retryable conflicts discard proof results owned by that attempt before rebuilding. A concurrent predecessor-manifest rewrite between preparation and commit leaves the save unpublished.

**Independent limit configuration evidence:** A host validates and commits the configured limit in a separate checkpoint before recording the terminal decision. Replay authenticates both commits and their source counter, requires the decision limit to equal the earlier configuration, and verifies that turn-limit context ends in a user or tool message. Source and configuration checks fence both atomic and staged failure settlement, including keep, withdraw, and large reset queues. Older terminal-decision checkpoints without this independent configuration evidence fail closed and cannot automatically settle or authorize historical forks. The proof trusts the runtime-reserved storage namespaces; it does not authenticate an arbitrary writer with unrestricted access to those namespaces.

**Reset proof storage trust:** Limit configuration and terminal-decision evidence is trusted only when the host excludes untrusted writers from runtime-reserved storage namespaces. The store exposes raw commits and does not enforce that boundary or cryptographically authenticate the configured limit. A raw writer with access to those namespaces can fabricate matching low-bound evidence and decisions, so this case is not detected. If the host cannot guarantee namespace integrity, it must deny use of the affected atomic continuation and historical-fork paths; the runtime cannot safely infer that guarantee from the database.

**Large atomic reset batches:** Eligible failed-run continuations do not fall back to staged settlement at 65 or 16,385 resets. Version-3 shared manifests split their encoded evidence into bounded 64 KiB records committed with per-cut references; version-1 and version-2 manifests remain readable. Readers verify the batch, references, and every chunk against the same transaction and retain their fences. Version-3 cut commitments cover each deterministic reset step and its transcript projection; replay derives the remaining state from the authenticated predecessor and checks the final anchor. Scoped proof caching and reversible cut deltas let occurrence-only scans traverse a validated batch without cloning each conversation or rereading the manifest; changes to the store cause the original evidence to be checked again. Producing an owned conversation for each cut still costs proportional to the size of those results. Tests exercise more than 16,384 resets through settlement and reopen, bounded chunk lookup beyond 8 MiB, reverse scan work, conflict fencing, and process-kill recovery. The runtime-reserved namespace trust requirement above still applies.

**Large snapshot proof lookup:** Outside display-entry forks, runtime-owned root, fork snapshot and observer records are not subject to an independent 8 MiB lookup cap. The same namespace-trust requirement applies; hosts should bound admitted conversation data according to their resource limits.

**Late block reset validation:** Ordered reset derivation validates the pending and placed identity sets once, then updates the pending set as each reset is placed. This preserves reset and block identity checks without repeatedly scanning a large queue when a block-bearing reset is near its end.

**Predecessor batch fencing:** A later reset proof reads a shared predecessor manifest and its chunks once per predecessor batch, then checks each cut reference and transcript entry against that same commit. The dependent transaction retains the manifest, chunk, reference, anchor and entry fences.

**Task-side conversation scope:** The upstream invocation-bound conversation handle can select an existing conversation in the same Session and checks that the supplied transaction belongs to that Session. pi-rs has no persisted Session identity, target-conversation authorization grant, or equivalent task-side handle. Task ownership and conversation edges govern lifecycle; they do not establish permission to submit to an arbitrary other conversation. Task-side admission therefore remains limited to the task’s owning conversation, including through generic task ancestors.
