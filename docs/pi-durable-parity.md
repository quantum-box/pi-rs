**Task application-entry fork checkpoint:** `fork_at_application_entry` supports a bounded local application-entry cut. It truncates the application log inclusively, copies documents at the end of the entry commit, and uses a verified earlier runtime snapshot, all in the child creation transaction. Inherited application IDs, untracked or ambiguous history, and runtime writes in the entry commit fail closed. This remains separate from upstream's unified entry history and general inherited entry forks.

**Checked task application-entry append:** `TaskDocuments::append_entry_if_head` stages an application record only when the last committed or locally staged application-record ID matches the caller's expectation (or the log is empty). The observed log remains a transaction read dependency even when the check fails, so a concurrent log change conflicts with the whole task transaction, including document writes. This is a pi-rs optimistic precondition on its separate task log; upstream [`tx.appendEntry`](https://github.com/earendil-works/pi/blob/main/packages/durable/src/session/transaction.ts) appends to the conversation entry stream, and its optional `head` is an entry field, not this precondition. The Rust API does not add general session transactions or upstream entry-tree semantics.

**Ownership cycle checkpoint:** Task creation checks staged and persisted task and conversation ownership, including background edges, and fences missing owners against concurrent creation. This protects child-first abort cleanup; legacy corrupt cycles are not repaired. Document transactions reject ownership insertions that overlap another component's missing-owner check. Raw `Store::commit` evaluates checks before writes and loses preparation boundaries; separately prepared ownership changes can therefore form cycles when concatenated, and remain the caller's responsibility. Jointly prepared task creations validate their staged graph. The document composition guard is conservative and may reject acyclic cross-component overlaps. Upstream models tasks and conversations as one ownership tree and drains owned work before its owner; pi-rs retains lower-level preparation APIs.

**Unified history checkpoint:** `Harness::unified_history_start` captures a finite store commit boundary and `unified_history` pages complete commit frames in sequence order (1–255 frames per page). Frames expose expanded runtime observation snapshots and full task application-log snapshots, including inherited records at a fork's own commit. They do not reconstruct parent commit history for a fork, per-entry order within one commit, or upstream's immutable transcript entry semantics. A snapshot can repeat earlier messages and application entries; task entries are not model context. On a store with any pre-tracking versions, the default start fails closed; explicitly accepting the migration boundary reads only tracked commits and does not reconstruct earlier ordering. Cursors are trusted, database-local, serializable host data; pages capture a fixed upper boundary and can resume after reopen. Sequence gaps include unrelated commits. Frames and values may be large; SQL work, expanded transcript traversal and application-log snapshots are not bounded by the page count. Raw namespace mutation/deletion, old writers and cross-database cursors invalidate guarantees. Existing history and application APIs are unchanged. See [tests](../crates/durable/tests/features.rs) and [upstream entries](https://github.com/earendil-works/pi/blob/main/packages/durable/README.md#concepts).

**Current status (pi-rs `cef544942fc4770d1642e3ae523ed31019cc64ba`):** The experimental runtime supports durable execution and recovery, task scheduling, transactional admission and task document/application-entry commits, typed task-scoped signals, managed background anchors, keyed nested tools, document fork policies (`Copy`, `Initial`, and `Current`), and commit-ordered unified history snapshots. **Extension callback panic reporting:** Section and hook panics while constructing or polling their futures are contained and recorded in the extension report log. Before-tool panics block tool dispatch; other phases retain their existing failure handling. The first report batch per operation and phase wins, and unacknowledged deliveries replay after reopen. [Upstream](https://github.com/earendil-works/pi/blob/c1d4b0ac3e35dc4eb1c5d00d90bf54003cf517c0/packages/durable/src/types.ts) reports thrown section and hook errors through `onReport`; Rust normalizes panic payloads to `extension panicked` and still does not cover the full upstream report taxonomy, including most tool execution failures.

**Tool execution panic report:** A caught model-issued tool panic produces a fixed redacted runtime report before waiting for nested calls; its committed identity prevents replay if a restart precedes the blocked phase. Resuming or reconciling repairs a missing report for a persisted blocked phase, with deduplication by operation ID. A crash before the report commits remains indistinguishable from interrupted dispatch. Upstream instead converts an execute throw to a tool error result and reports tool cleanup and invalid structured-output errors; those cases are not implemented here. Nested panics are also outside this report coverage.

**Extension report subscription:** `Harness` and `Scheduler` expose a bounded,
pull-based subscription and opt-in asynchronous dispatcher over persisted extension
error batches, with host-managed cursors and replay after reopening. Unlike upstream
`onReport`, the dispatcher delivers batches after commit, stops on listener failure,
and requires explicit awaited shutdown and checkpointing; it does not cover the
complete upstream report taxonomy; see the
[delivery guarantees](../crates/durable/README.md#extension-error-observation).


**Opt-in OpenAI Responses adapter:** The standalone [durable-openai crate](../crates/durable-openai/README.md) prepares, validates, and dispatches post-hook API-key Responses requests, with bounded SSE parsing and replay. It rejects final tool items at inconsistent output indices and tool items with empty arguments or an explicit unfinished status in completed responses. It is not installed automatically; ChatGPT OAuth and hosted tools are unsupported.

**Opt-in Anthropic Messages adapter:** The standalone [durable-anthropic crate](../crates/durable-anthropic/README.md) validates and dispatches post-hook API-key requests and supports streamed text and tool calls. Extended thinking and signed reasoning replay are unsupported; unknown response blocks and ambiguous mixed initial/streamed tool input fail closed. It is not automatically installed or selected.

**Opt-in Google Gemini adapter:** The standalone [durable-google crate](../crates/durable-google/README.md) validates and sends post-hook API-key GenerateContent requests, with bounded SSE decoding and model-scoped replay; malformed or partial-argument calls and duplicate call IDs are rejected. It is not installed automatically; catalog discovery, OAuth, and configurable thinking are unsupported.

**Opt-in Ollama adapter:** The standalone [durable-ollama crate](../crates/durable-ollama/README.md) prepares and dispatches validated post-hook OpenAI-compatible chat-completions bodies to a numeric loopback endpoint. It rejects partial reported usage and tool calls missing their arguments field; malformed argument JSON is retained for tool-error handling. **Task document transaction checkpoint:** Generic task handlers can stage checked document reads and writes with a successful checkpoint transition and `Wait` children in one commit. Confirmed document conflicts retry replay-safe handlers, while unsafe handlers fail for reconciliation; other transaction conflicts require reopening. The reservation commits separately. Failures and abort handlers do not commit staged documents. Each invocation reads one immutable document revision, sees its staged writes, and validates every read address against intervening mutations, including create/delete cycles. This remains narrower than upstream §4: no general session transaction, mutable Chord drafts, or arbitrary child creation; optimistic conflict handling differs from the upstream mutation line. See [task transaction tests](../crates/durable/tests/task_document_transaction.rs) and the [durable README](../crates/durable/README.md).

**Task application-entry checkpoint:** Conversation-owned generic tasks and their task-owned descendants can stage ordered application entries with `TaskDocuments::append_entry`; a successful task transition, checked documents, and any Wait children commit together. Each entry retains its conversation ID, author task ID and provisional UUID, and `application_entry::list` reads committed entries after reopen. The full task ancestry must exist, be nonterminal and not be aborting, and its versions are checked with the commit; cycles fail closed. The root runtime conversation must exist, match its ID and not be aborting; its version is checked in the same commit. Traversal is linear in depth without a configured limit. Checked log and ancestor conflicts follow the existing replay-safe task retry policy; aborts and failed steps discard staged entries. The independent per-conversation JSON log is not the runtime transcript or `submit_write` stream: it is not included in observations, model context, resets, or entry-ID lookup; forks inherit their selected log snapshot, and the unified snapshot reader exposes its commit order alongside observation snapshots. General conversation transactions, read-your-staged-entry queries, and per-entry history cuts are unsupported. Each append rewrites the entire unbounded log; IDs can change on retry and must not be used externally before commit. Raw store access can bypass invariants. See [transaction tests](../crates/durable/tests/task_document_transaction.rs) and [upstream entry concepts](https://github.com/earendil-works/pi/blob/main/packages/durable/README.md#concepts).
Upstream was rechecked at commit `c1d4b0ac3e35dc4eb1c5d00d90bf54003cf517c0` on 2026-11-15; `packages/durable` is unchanged from the audited `827383a15262905f82e418483825a49dbb1adbf5` baseline below.

**Host task wait checkpoint:** `Driver::wait_for_task` returns a terminal persisted task, rejects unknown IDs and permits cancelling a wait independently of work. Unlike upstream's [Harness.waitForTask](https://github.com/earendil-works/pi/blob/main/packages/durable/src/harness/scheduler.ts), it polls every 100 ms and requires a running driver; it does not register scheduler waiters or start a driver automatically. It returns Rust task states and errors rather than upstream types. Reopening permits waiting on persisted tasks once a driver is started.

**Conversation idle checkpoint:** `Scheduler::wait_for_idle` observes queued and running conversation work, pending resets, and foreground owned tasks and child conversations, including through terminal task anchors; cancellation does not abort work. Like upstream's [durable scheduler](https://github.com/earendil-works/pi/blob/main/packages/durable/src/harness/scheduler.ts), ordinary idle excludes background branches. Unlike upstream it polls one database snapshot every 100 ms rather than registering scheduler waiters, and errors if live generic tasks lack a running driver. Reopen resumes observation of persisted work; blocked work can remain pending. No background-inclusive idle option is exposed. See [idle tests](../crates/durable/tests/conversation_idle.rs).

**Task migration checkpoint:** Generic tasks persist definition version and input, and registered migrations atomically commit the new checkpoint together with execution reservation. Missing, newer or unmigratable definitions block execution and can be reconsidered after their definition changes or after reopening. Registry clones preserve definition identity, so unrelated registration changes do not retry a failed migration. A migration panic that unwinds is caught and exposed as `MigrationFailed("migration panicked")`, without changing the stored task; aborting panics cannot be caught. An explicit abort waits for owned children and persists an orphan diagnostic with the blocking reason in `Failed(String)`; unlike upstream, this is not a typed orphan outcome and restart abandonment is not represented. The background driver can replace registrations at a handler boundary and wakes its worker; `blocked_tasks` polls live blocked definitions and migration failures. Upstream report callback coverage, graph integration, wake semantics and typed orphan outcomes remain incomplete; generic-task wake hints and extension-error subscriptions have since been added. See the durable README and task scheduler tests.

**Failed-run queue checkpoint:** Per-conversation `AfterFailedRun` defaults to `Keep` and can be set to `Continue` or `Withdraw`; withdrawal settles queued inputs with `run_failed` and preserves request-ID deduplication. The policy and outcomes persist over reopen. Compared with [upstream failure handling](https://github.com/earendil-works/pi/blob/main/packages/durable/docs/spec.md), continue places the next input in a subsequent commit, settings are per conversation, and independently created or task-owned children do not inherit the setting. Supported failure reasons and queued-write behavior retain the runtime's existing limits. See [tests](../crates/durable/tests/after_failed_run.rs) and the [durable README](../crates/durable/README.md).

**Document fork policy checkpoint:** Per-address `Current` copies the latest committed source value and policy atomically with fork creation, including for historical cuts; absent or deleted values remain absent. Historical `Copy` and `Initial` keep their cut semantics, and policies for missing addresses persist. A database-wide revision fence retries on unrelated writes and returns a conflict after eight failed attempts. The eager stored `Initial` value and mutable address policies differ from upstream’s lazy initializer and document incarnations. See the [document API](../crates/durable/README.md) and [upstream fork spec](https://github.com/earendil-works/pi/blob/main/packages/durable/docs/spec.md#37-forks).


**Completed tool progress retention:** Completed attempt snapshots and terminal events retain the last committed replacement partial, just as aborted attempts do; legacy completed snapshots remain readable. A sidecar keeps oversized completed partials readable by this version while preserving the old snapshot size limit; older versions can read the completed state but cannot see a sidecar or distinguish a null partial from no partial. This progress remains display-only; the separate opt-in streamed-output adapter described below has its own records. Upstream also retains an interrupted unsafe tool’s committed output in its error result; Rust does not. See [upstream tool documentation](https://github.com/earendil-works/pi/blob/main/packages/durable/README.md#defining-tools) and the [polling contract](../crates/durable/README.md).

**Opt-in streamed-output fallback:** The separate `StreamedToolAdapter` on the durable keyed adapter records bounded text per model-issued attempt and uses it only for an explicitly omitted successful output. Attempt fencing, replay, errors, and reopen semantics and remaining differences are described in the [durable README](../crates/durable/README.md). Upstream's [tool harness](https://github.com/earendil-works/pi/blob/main/packages/durable/src/harness/tool.ts) additionally supports byte and line limits, truncation diagnostics, last-details fallback, and interrupted unsafe output in its error result; these are not implemented by the adapter.

**Tool progress polling checkpoint:** Per-attempt cursor pages retain committed replacement partials and terminal seals atomically with the attempt fence, including across abort, safe replay and reopen. Records identify both operation and attempt; old attempts are not backfilled. Unlike upstream's throttled live-document diffs and watch operations, this is an unbounded retained log of whole replacements, with no cross-attempt ordering or automatic attempt discovery. See [runtime tests](../crates/durable/tests/runtime.rs) and the [polling contract](../crates/durable/README.md).

**Tool attempt identity checkpoint:** A model-issued tool operation keeps its stable operation ID for reconciliation and nested calls, while each initial execution and safe replay commits a fresh attempt UUID before dispatch. The current attempt is available on running, pending, blocked and finishing conversation snapshots; polling, abort and reconciliation do not create another attempt. Older records without an attempt ID remain readable and report none until a replay is claimed. Conversation-scoped bounded attempt discovery records new claims in commit order, including retries; earlier claims are not backfilled, and clients filter by operation ID. This is a pi-rs prerequisite for progress fencing, not upstream API parity: tool progress is now wired to attempt IDs and fenced on commit, but nested-tool attempt IDs are not exposed. External effects still require their own idempotency. **Coding tools checkpoint:** The opt-in `coding-tools` feature registers the existing workbench local `read`, `write`, `edit`, and `bash` tools with unsafe replay policies. Interrupted effects need interruption handling or reconciliation. **Managed background anchors:** First managed send creates the named link, child, completed background anchor and ownership edge in one checked commit, fencing parent abort. Existing compatible explicit links are anchored before managed delivery, and reuse is rejected while the parent abort mark is visible. This check does not atomically fence subsequent reporter or input admission. Reopen reuses the same anchor; stop leaves the child reusable. Upstream [Durable](https://github.com/earendil-works/pi/blob/main/packages/durable/README.md) commits conversation work before exposing it and provides bounded transcript views; pi-rs still reconstructs full snapshots, copies metadata and subagent reservation seeds, and has no transcript garbage collection or downgrade compatibility. **Message-position fork checkpoint:** `fork_at_position` accepts a positioned message only when it is the last message of a nonempty immutable batch and the first observation referencing that batch has complete fork metadata with the same transcript cursor. It uses that commit's configuration and state, validates the complete tool transcript, and creates an idle child atomically using the existing fork path. Later configuration changes do not alter the cut. Positions survive resets and reopening. Missing, legacy, incomplete or mismatched metadata, positions within a batch and positions without a matching observation fail closed. Migrated legacy batches do not acquire fabricated entry identities and position forks reject them. Inherited entry IDs can be forked only when their annotated batch is visible in the selected conversation’s captured immutable chain; the origin observation and its document cut are used. This includes complete replacement boundaries. Unannotated chains, ambiguous inherited IDs and original IDs lost to materialized interior forks fail closed. Inherited positions without an observation in the selected conversation are rejected. Observation history is scanned linearly; cursors are trusted host data, not authorization tokens. Upstream's [fork](https://github.com/earendil-works/pi/blob/main/packages/durable/README.md#more-conversations-and-forks) supports entries more generally: arbitrary message cuts, changes between entries, application entries and full owned-task history are not reconstructed here. **Historical custom document history and fork checkpoint:** New conversation snapshots atomically record the post-commit document revision, including admission writes. Pre-feature cuts fail closed; interior cuts require unchanged global document revision, which can reject unrelated writes. Current forks capture a revision during the call. Optional persisted per-address policies choose a stored initial object or a copy at the selected cut, and are inherited atomically, including when their documents are missing. Missing policies retain legacy copy behavior. Upstream also offers current-at-fork behavior for historical forks; that mode, enforced ownership and general transactions remain unsupported. **Document watch checkpoint:** A pull-based document watch captures an initial state at an immutable revision and pages later committed states, including deletes, in order. It can resume from a consumed cursor after reopening. It does not implement upstream Chord operations, automatic notifications or watch lifecycle, and retained history and individual values are not byte-bounded. Legacy history begins at migration. See the [document README](../crates/durable/README.md) and [watch tests](../crates/durable/tests/document_watch.rs).

**Same-commit configuration checkpoint:** Compared with upstream [`session-forks.test.ts`](https://github.com/earendil-works/pi/blob/17d6ca759a070c377147f6d76b72dab9a3ba42a3/packages/durable/test/session-forks.test.ts), which copies final document state from the selected entry’s commit, new tool-free append batches can be forked at an interior entry when only model configuration changes in that commit. The child receives the final model, prompt and token limit and the message prefix, even after reopening and later parent changes. This proof applies only to newly written append batches; configuration-changing batches containing any tool calls or results, other fork-state changes, replacement batches, missing metadata and changes to the global document revision across the commit still fail closed. Complete tool context is still required, and interior forks assign new message IDs. The newer shared-chain checkpoint describes inherited ID support. This does not implement upstream’s general per-entry document or task history.

**Interior entry fork checkpoint:** New append batches record a versioned proof when all runtime fork-state fields (configuration, queue modes, extensions, provider adapter, allowed tools, tool state, resets and application writes) are unchanged across the atomic commit. A fork by occurrence ID or position may truncate such a batch at an interior message, using that commit's state, only when the resulting context has complete and valid tool calls and results. Child creation remains atomic and the parent is unchanged; reopening preserves the child. Older batches, other state-changing batches, and replacement batches do not acquire proof retroactively and reject interior cuts; the same-commit configuration checkpoint above describes the tool-free exception. Interior forks materialize a new transcript and assign fresh IDs; original IDs are not retained in that materialized transcript. Application document inheritance is described in the newer custom document history and fork checkpoint; task history is not reconstructed. This remains narrower than upstream's ordered entries and per-entry document history.

**Entry metadata checkpoint:** New immutable message batches carry a UUID per message occurrence and the originating conversation and observation sequence for the atomic commit that stored them. The matching historical fork snapshot contains that commit's configuration, tool state and runtime documents. These values describe the whole commit; only the last message in a batch has an exact commit boundary. Intermediate messages must not be interpreted as having independently captured state. Existing inline and transcript batches remain readable without fabricated IDs; position forks reject unannotated batches. Replacement batches (including reset/compaction) assign new IDs to replacement occurrences; they do not preserve identities across context reconstruction. Inherited entries retain their original conversation/commit association. `fork_by_entry_id` resolves IDs by scanning retained observations in bounded pages, including after resets and reopening, and forks only a proven final batch message using its original commit. Visible inherited chains are checked for ambiguous IDs before selecting a local match, and duplicate occurrences or unprovable chains fail closed. Missing provider/tool settings and unproven foreign occurrences fail closed; the inherited-entry checkpoint above describes the supported shared-chain case. The child starts idle without parent abort work; the parent abort state is untouched. Historical state between messages in one batch, application entries and complete external document/task history remain unsupported. Metadata grows linearly with message count (one UUID per occurrence plus one origin and sequence per batch); UUID generation and JSON serialization add CPU, while existing full snapshot reconstruction and retained commit snapshots remain unbounded. No benchmark was performed.

Both message count and record visits are bounded, but individual stored batches and metadata are not byte-bounded. This is a pull snapshot, not upstream's watch, operation stream, automatic window adjustment or complete entry stream. See the durable README for migration and size limitations.

favor of conversation views; its watches terminate with lifecycle reasons, which
this standalone log does not provide. See the [upstream changelog](https://github.com/earendil-works/pi/blob/827383a15262905f82e418483825a49dbb1adbf5/packages/durable/CHANGELOG.md) and [watch documentation](https://github.com/earendil-works/pi/blob/827383a15262905f82e418483825a49dbb1adbf5/packages/durable/README.md#watching-a-conversation).

**Conversation history replay checkpoint:** `Harness` and `Scheduler` expose
`history_head` and `history_through` for finite, paged replay of expanded
conversation snapshots. Persist the conversation ID, boundary and last
processed cursor to resume after reopening; then use `watch_history` from the
last processed cursor. Cursors are conversation-scoped, including across forks,
and numerical cursor values do not authenticate their origin. This replays only
the retained snapshot log, not Chord operations or every document change. Page
counts are bounded, but snapshot bytes, expansion work and retained history are not.

**Historical subsequent checkpoint:** Busy reset queues at safe boundaries, provider-overflow compaction and persisted bounded exponential retry were added. A host can attach a background generic task driver to the conversation store, with direct-child all/any/fail-fast waits and local descendant cancellation. A persistent subagent link can resume child admission. Task lifecycle/abort ownership is not yet integrated with conversation execution, reset ordering and tool handoff are incomplete, and subagent links do not yet supply automatic answer reporting or ownership-aware abort.

**Named background anchor (subsequently automated for managed sends):** `Harness::anchor_subagent` atomically attaches an immediately succeeded background task and foreground child edge to an existing named link. It is idempotent across process reopen, isolates ordinary parent abort, and allows background-inclusive parent abort to reach the child. Existing stop and reporter behavior is unchanged. Managed sends now create the anchor automatically; automatic cleanup orchestration remains unsupported. Explicit background-inclusive parent abort traverses terminal anchors and their child conversations. Its waiting form reports a missing or stopped task driver even while conversation cleanup is waiting on live tasks; persisted abort marks remain available for a later retry.

**Historical checkpoint:** Subagent completion can now be reported automatically to its parent, and reporter-driven conversations continue polling pending tools. Named child status is available as a read-only Rust API, including reservations and queued work; it is not a model-facing management tool. Managed sends now have default child tool restrictions and background anchor ownership; lower-level links remain independent unless explicitly anchored. Queued submissions can be withdrawn. Conversation extension selections, prompt sections, extension-provided tools, before/after-tool hooks and selected generation hooks are supported; the scheduler can preload an extension registry before automatic recovery. The remaining hooks and hook-created tasks are not yet integrated. Task sleeps can wait for a deadline or any named signal. Subagent cancellation is not yet an ownership-aware cascade. Later checkpoints and the table below supersede earlier statements where they differ.

**Extension safety checkpoint:** Tool results are checkpointed before after-tool hooks. Abort during preparation records skipped tool results; pending and reconciled operations retain the prepared arguments for result hooks. Older pending records without those arguments fall back to the original model arguments. Extension hooks may be replayed after interruption and must make external effects idempotent. See [extension runtime tests](../crates/durable/tests/extension_runtime.rs).

**Abort and reporter checkpoint:** `Scheduler::abort` persists conversation aborts, withdraws queued inputs and fences both ordinary and reporter-driven dispatch; `abort_and_wait` waits for local workers. A dispatched uncertain effect requires reconciliation even if replay-safe. Background reporter children remain independent: parent abort does not propagate through an ownership tree. See [abort tests](../crates/durable/tests/abort.rs) and [reporter tests](../crates/durable/tests/reporter_pending.rs).

**Conversation-owned task abort checkpoint:** A conversation abort atomically marks its live generic and lifecycle task descendants and withdraws queued inputs. Root and lifecycle admission are fenced while the mark is active; an in-flight task cannot publish children after its mark. Reopening resumes task cleanup child-first, and the conversation stays abort-marked until its owned tasks settle. This requires an attached task scheduler or driver to make progress. Handler interruption remains cooperative: active synchronous handlers cannot be signalled and must return before cleanup; cleanup can replay after a crash and must be idempotent. Missing abort handlers fail with an orphan diagnostic, and restart exhaustion can fail without cleanup. Direct TaskStore mutations and noncooperating executors are outside the ownership protocol. Unlike current upstream, pi-rs has no background-task ownership flag: all conversation-owned generic tasks are included; reporter/subagent conversation links remain independent. `abort_and_wait` waits for local conversation workers, which poll task cleanup; blocked external effects still require reconciliation.

**Historical background task boundary checkpoint:** Conversation-owned generic tasks can be marked background at creation. Ordinary conversation abort and its task-drain check skip that task and its descendants, including after reopening; explicitly aborting the task still marks its subtree. Child tasks cannot be marked background through this API. The preceding checkpoint's statement that all generic tasks are included is superseded. This is only a task-graph prerequisite: subagent links and reporters are not owned by these tasks, there is no conversation abort option to cross background boundaries, and upstream ownership-aware idle, terminal-owner traversal, task-to-conversation cascades and abnormal-completion propagation are not implemented. Existing reporter children therefore remain independent of parent abort, and foreground subagents are not yet supported as owned tool scopes.


**Opt-in task-owned subagent admission:** `Harness::ensure_task_owned_subagent` and its scheduler counterpart atomically create an empty child conversation, permanent task-scoped reservation and ownership edge while advancing the parent task version. Matching retries return the same child, including after abort and reopen; changed owner, configuration or mode is rejected. Admission refuses an already aborting or terminal task. This does not submit input, schedule execution, seed history, or reject longer cycles. Harness abort traversal follows foreground ownership edges as described below. Existing named subagents remain independent. Storage errors require reopening before retry. See `owned_subagent` tests.

**Task-owned initial input:** `Harness::submit_task_owned_subagent` atomically creates the ownership reservation, edge and runnable initial input under the parent task version fence. Matching retries return the original child and submission, including after abort or reopen; changing the input or using the empty-child API with the same key is rejected. `Scheduler::submit_task_owned_subagent` schedules after commit, and reopening recovers a committed child if scheduling was interrupted. Foreground abort traversal and background boundaries follow the ownership rules below. This opt-in API does not seed parent history or configure extensions; storage errors require reopening. See `owned_subagent` tests.

**Foreground ownership abort traversal:** `Harness::request_abort` and `Harness::request_abort_task` atomically persist abort marks across foreground task and conversation ownership edges, withdraw queued inputs, skip background branches, and fence visited records and edges against concurrent admission. Cycles terminate; conflicts retry the complete traversal. Direct store writers outside the ownership protocol are not fenced. The standalone task scheduler and task driver still fail closed on foreground conversation edges; they do not signal or join child conversation workers. Hosts must stop and drive those workers separately, including after reopening, until scheduler propagation is implemented. A storage error can have an uncertain outcome and requires reopening. See `owned_subagent` tests.

**Child-first owned cleanup checkpoint:** Compared with upstream [abort and subagents](https://github.com/earendil-works/pi/blob/06f5671c924cd6eaa1d7501736925db0e5cb2a49/packages/durable/README.md#abort-and-subagents), which waits for the conversation to become idle and supports explicitly crossing background boundaries, this implementation retains the boundaries and limitations below. Task abort cleanup waits for each foreground owned conversation to finish its persisted abort, including that conversation's foreground task descendants. Restart-limit failures also wait for those children. `Scheduler::abort_and_wait` joins the workers for all conversations marked by the atomic traversal. Ordinary abort retains background boundaries; explicit background-inclusive abort crosses them. Cyclic ownership may deadlock cleanup; blocked uncertain operations require reconciliation and generic tasks require a running driver. The standalone task scheduler and driver still reject aborts involving foreground conversation edges. See `owned_subagent` tests.

**Earlier scheduler propagation checkpoint (superseded by child-first checkpoint above):** `Scheduler::abort` and `abort_task` fence existing conversation polls while committing the foreground graph, cancel affected workers, and schedule each marked conversation for cleanup. Reopening schedules all persisted conversations. Background edges remain independent. Standalone task abort still rejects foreground child conversations, and task cleanup does not join child conversation cleanup; `abort_and_wait` waits only for the requested conversation's local workers. Active nested-conversation race and crash/reopen coverage remains incomplete. Legacy task cancellation fails closed when it would strand a foreground child. See `owned_subagent` tests.

**Ownership edge storage checkpoint:** `ownership_edge::EdgeStore` prepares checked, atomic task-to-existing-conversation links with explicit foreground/background metadata and a unique owner per child. Both endpoint versions and task ownership are fenced at commit, and edge creation advances the task version to invalidate a concurrent traversal's earlier task snapshot. Edges survive reopen. This is only a composable storage primitive: creation of the conversation and task must currently precede the edge; no traversal, cycle detection beyond a direct self-edge, scheduling, abort propagation, lifecycle cleanup, or subagent integration is provided. Edge mode is stored metadata and does not itself implement upstream background boundaries. See [ownership edge tests](../crates/durable/tests/ownership_edge.rs).

**Continue checkpoint:** `Harness::submit_continue` and `Scheduler::submit_continue` persist a distinct, deduplicated run submission without a user message, reject busy conversations, place queued steers and follow-ups according to the configured queue modes, and settle the participating submissions together. Empty or answered contexts settle `nothing_to_answer` without a model request; failed runs retain their unanswered user/tool context. Recovery resumes the committed phase, and truncated tool calls are recorded as skipped without dispatch. See [continuation tests](../crates/durable/tests/continue_submission.rs) and [runtime tests](../crates/durable/tests/runtime.rs). Unlike upstream, this runtime has no public transactional/tool-side admission, `pi.live.runFailure`; it uses Rust status and reason strings and represents continue content as an empty compatibility field in memory (omitted from storage). Historical synthetic failure messages from older versions are not rewritten. Queued reset ordering and generic task ownership remain separate gaps.

**Admission policy checkpoint:** `Harness`, `Scheduler`, and the state-backed
conversation helper now support optional busy and idle rejection for input,
with request-ID deduplication before the policy check and version-checked
admission under contention. Busy means an active run, even when queued input
remains after a failed run. Duplicate input request IDs are resolved before content validation. Arbitrary host transactions / `submit(tx, draft)` are not supported. See the admission concurrency and recovery tests in
[`runtime_cas_tests.rs`](../crates/durable/src/runtime_cas_tests.rs). The
original audit table below remains a historical baseline.
**Write-submission checkpoint:** The experimental runtime accepts display-only application entries through `submit_write`, persists them immediately while busy, and delays placement behind queued resets. Request IDs deduplicate within the conversation before validating a repeated write’s kind and cannot be reused across input and write types. Entries are exposed in `Conversation.application_writes` and observer snapshots with a placement flag and preceding reset ID. This is a narrower API than upstream: model messages, head edits, stale-head handling and generic entry transactions are not implemented. Current forks and historical snapshots inherit placed application entries at the selected point, but not their request IDs. Queued and withdrawn writes are exposed as records, not placed transcript entries; observers must filter `placed`. The runtime still stores snapshots rather than an upstream ordered entry stream.

**Write withdrawal:** As at upstream revision `827383a15262905f82e418483825a49dbb1adbf5`, withdrawing a queued display-only write settles it unanswered with reason `aborted`; a placed or previously withdrawn write reports `settled`. pi-rs persists a `withdrawn` tombstone in `application_writes`, retaining the submission and request ID across reopen; `wait_for_submission` reports `WriteUnanswered`. Reset placement skips tombstones, and worker conflict merging preserves a withdrawal that committed before a stale placement. This applies to `submit_write`, not the separate task application-entry log.

**onYield checkpoint:** Final answers enter a persisted onYield phase with a stable hook memo. A string continuation keeps the current submissions open and starts a fresh turn budget; queued steering, follow-ups, or resets take precedence, and after-run hooks run only once an answer stands. Hook-created tasks and their wait are committed atomically; after all children terminate, the first successful child in creation order with a nonempty string `{"continue": "..."}` is selected. Failed and invalid child outcomes are ignored. A registered task driver is required, and reopening resumes the persisted wait. Hooks may replay after interruption or a concurrent admission and must make effects idempotent. Unlike upstream, this subset accepts only string continuation input, exposes the already-committed answer in the hook snapshot, and treats invalid hook decisions or hook errors as recoverable phase errors rather than reporting and skipping them. Conversation abort marks owned hook children and descendants atomically and waits for cleanup with an attached task driver; synchronous effects still cannot be interrupted or rolled back. See [extension runtime tests](../crates/durable/tests/extension_runtime.rs).

**beforeCompact checkpoint:** Manual, threshold and overflow compactions persist the selected message range and a stable hook memo identity before calling selected hooks. Manual compaction accepts optional instructions, persisted for both the summary request and hook across recovery. The first decline or summary wins; hook errors are skipped, cancellation replays the phase, and hook summaries bypass model usage. Unlike upstream, the host exposes message indices instead of entry IDs and markers, has no hook report callback, rejects blank summaries, and still requires idle manual compaction. See [compaction tests](../crates/durable/tests/features.rs).

**Manual compaction operation identity:** Idle manual compaction exposes a persistent operation ID and running, applied, declined, aborted, or restart-limit status. Admission, the selected hook identity, and the running record commit together; terminal status commits with the corresponding context or abort transition. A recovered summary attempt retains the operation ID while using a new model request ID. Records are not inherited by forks and have no retention policy. Existing recovery-required errors leave the operation running pending reopen or abort. This is an executable identity for the existing idle phase, not an independently scheduled task, and does not enable busy compaction or stale-result settlement. See [compaction tests](../crates/durable/tests/features.rs).

**Compaction context guard:** New runtime-owned preparations persist the active context generation with the request. Committed resets and successful compactions replace that generation; before applying a summary the runtime checks it along with the existing message-prefix check. This prevents a reset followed by identical message text from reviving an old preparation across reopen. Existing in-flight preparations without a generation can resume while their conversation also has no generation; a reset, compaction, or fork fences them. This is a conservative guard, not upstream stale-submission settlement: even a later compaction retaining the target invalidates the old generation. Busy manual compaction remains disabled. Supporting it requires a separately scheduled, conversation-owned durable compaction operation with restart, abort, usage and hook accounting; an atomic ordered boundary write and durable `stale` settlement; and stable retained-entry identities across transcript replacements, including forks and legacy records. The generation guard alone cannot order competing cuts or prove that a retained target is still active.

**After-tools termination checkpoint:** A successful after-tools child result of exactly `{ "terminate": true }` settles active inputs with the tool-calling assistant answer, runs after-run hooks, and only then places queued inputs at the final boundary. The persisted child wait resumes after reopening. Other results are ignored without upstream’s invalid-decision report. Opt-in `KeyedTool::invoke_controlled` can return a terminate control; a nonempty round ends when every call requests it, with controls committed alongside tool outcomes and preserved across reopen. Ordinary tools and synthesized errors have no control. Opt-in controls also support handoff: the last defined handoff in call order appends a durable reset after after-tools tasks and before queued items, including when the round terminates. Opt-in `add_tools` controls persist names in call order at that same boundary, deduplicating additions to the shared allowlist and retaining currently unavailable names; an unset allowlist already enables all tools. An optional exact model-facing selection is updated as well; unlike upstream, remove filters and deferred tool loading are not implemented. See [extension runtime tests](../crates/durable/tests/extension_runtime.rs).

Explicit tool selections and additions are offered in stored order. Empty added names are ignored to preserve the selection invariant. An addition expands the shared execution allowlist, including restricted subagents, so only trusted tools should be permitted to return controls.

**Queue delivery checkpoint:** Durable conversations persist independent steering and follow-up delivery modes, defaulting to one at a time for new and legacy records. `all` selects every queued input of that kind at the eligible boundary. Final boundaries settle the previous run before starting the selected successor inputs; post-tool boundaries select steers only. See [durable README](../crates/durable/README.md).

**Typed signal checkpoint:** Task signals optionally record a versioned token and structured kind/key and survive reopen; matching is by kind and key. Typed keys hold a single value per task, reject conflicting deliveries, and close to further waits after consumption; identical retries with another ID do not create another receipt. Schema-bearing tokens validate constructed values and typed reads; older versions require an explicit read-only migration, and failures leave receipts unchanged. Legacy tokens, raw receipt reads and wake results bypass schema checking. `deliver_signal` returns upstream-shaped delivery outcomes. Typed deadline-or-signal sleeps retain wake reasons through recovery until checkpoint progress, another wait, or termination, and atomically expire empty keys against concurrent delivery; status delivery checks deadlines using wall time or an explicit clock. The older receipt-based `send_signal` reports expiry as an error. Opt-in `TaskDocuments::signal_at` stages multiple distinct typed deliveries to other tasks, including distinct keys on the same target with the checkpoint and document batch; its outcome is provisional and task/version and signal-revision conflicts roll back the whole attempt. It anchors a caller-supplied staging time to monotonic elapsed time and conflicts if an empty matching key crosses its deadline before the storage commit boundary; replay must supply a fresh time, and clock jumps after staging are not observed. It rejects repeated typed keys within one invocation (upstream returns duplicate), excludes self-delivery (upstream permits it), and rejects overlaps with other batch participants’ checked keys; it is not general upstream transactional delivery. Preexisting duplicate typed records are not consolidated and typed reads reject ambiguity. Legacy signals remain separate. See [typed signal tests](../crates/durable/tests/typed_task_signals.rs) and [deadline tests](../crates/durable/tests/typed_signal_deadlines.rs).

### Parallel parked nested calls: compatibility boundary

Compared with upstream pi at [`c1d4b0ac3e35dc4eb1c5d00d90bf54003cf517c0`](https://github.com/earendil-works/pi/blob/c1d4b0ac3e35dc4eb1c5d00d90bf54003cf517c0/packages/durable/README.md#tools-that-park), this is not just a concurrency restriction. Upstream starts or finds each nested call as a caller-owned tool task with `executeTool(..., { key, wait: false })`; the returned task ID can be used in a parent park with an `any` wait. A wake re-enters the parent with its checkpoint and ended task IDs. Explicit keys are required after a wake, and a parked parent retains its children across restart, including when the parent is replay-unsafe. Settlement or abort handles its remaining children; parking does not settle them. A normal awaited nested call instead keeps the parent invocation alive.

The present Rust path has different boundaries:

- [`NestedHost`](../crates/durable/src/nested.rs) holds a per-invocation lock throughout dispatch and rejects even distinct concurrent keyed calls. Its records contain an operation ID and outcome, not a scheduler-owned task and independently awaitable handle. Reusing a completed key checks tool, arguments and replay policy; replay must visit every recorded call in each re-executed scope.
- A nested `Outcome::Pending` is stored as an unresolved outcome and makes root inspection fail. It is not attached to the runtime's top-level pending poll path. The runtime seals and waits for the nested host before it commits the parent outcome; invocation-scope closure cancels active nested work and marks it uncertain. Thus returning a parent pending outcome cannot preserve live nested children as a park.
- Generic [`TaskStore::commit_owned_tasks`](../crates/durable/src/task_store.rs), task `TasksAny` waits and the task driver provide useful primitives, but a model tool operation is not currently a task owner there, and no atomic transaction binds a nested key and its tool intent to an owned task and parent park. Generic task wake data is not the tool checkpoint/wake API. Passing the existing operation UUID as an owner or treating a pending reference as a task handle would not establish those invariants.
- Dropping the lock alone would not implement parking: duplicate keys could race admission or dispatch, positional identities could depend on scheduling, and the existing seal/inspection rules would still cancel or reject outstanding work. It would also change the established ownership and reconciliation contract without a durable handoff.

An internal [storage-only keyed child admission](../crates/durable/src/keyed_child.rs) now atomically creates a registered child task and a parent-scoped key record with its task ID, tool identity, arguments, replay policy, registration identity, initial checkpoint and restart limit. A duplicate with the same identity returns the original ID; a conflicting identity fails. Older experimental records without the initial checkpoint and restart limit fail closed; there is no automatic migration. Admission requires a current running, non-aborting task parent and a ready child owned by it. Creation advances the parent version to fence abort and settlement traversals, and checks the ownership ancestry; duplicate lookup also checks the recorded child exists and is still owned by that parent. Concurrent admissions, including different keys, can conflict and require a fresh snapshot and retry; an uncertain storage commit requires inspection before retry. The internal preparation must not be composed with separately prepared ownership changes: their ancestry checks see only pre-commit state. This primitive does not acquire an executor lease or validate a registration against a live registry: its eventual caller must do both. It is private and not connected to nested tool execution or exposed as `wait: false`.

An additional private `park_any` primitive commits a running generic task's checkpoint and any-child wait together, resolving explicit admission keys to distinct, existing direct children. Its transaction fences the parent, key records and child versions; admission, abort or child transitions that race it require a reload and retry. A private `park_with_documents` variant checks that staged `TaskDocuments` use the same store and task value, and commits those documents and the park atomically while holding the task gate. The caller must fence the parent executor: neither the task gate, a running snapshot nor matching document context proves executor ownership. The variant must not be called while already holding the task gate. Already admitted children are committed separately before the park, so a crash before the park is an interrupted parent execution, not a parked parent. The generic scheduler can execute these registered child tasks and wake the parent after one ends; it leaves a parked replay-unsafe parent untouched on reopen and applies each interrupted child's own replay policy. Its synchronous handlers execute one step at a time, not parallel async tools. A private generic-task wake payload records terminal IDs at wake, then refreshes them under child-version checks in the first reservation transaction, including children that finish between wake and reservation. That reservation freezes the payload across interrupted replay and definition migration until progress, another wait, abort or settlement. The payload has no public accessor and is not yet exposed to tools, but its internal fields are visible when a public Task is serialized; generic task transitions do not produce a durable event history. Records written by the earlier experimental wake-only format retain their older snapshot if reopened. The primitive is not connected to the conversation tool host, does not validate the live registry or supply tool cancellation hooks, and cannot yet be called inside a scheduler handler as a separate commit without reconciling the scheduler's running snapshot and staged documents.

The generic scheduler now commits a fresh internal task-attempt UUID with each reservation, clears it when execution stops, and leaves legacy or standalone `Task::start` records without one. A private [executor identity binding](../crates/durable/src/executor_handoff.rs) can record a running conversation tool attempt and a running conversation-owned task attempt together. Checked dependent writes must include its conversation, task and binding versions in the same transaction; abort, replay, park or settlement invalidates those checks. Replacing a binding requires a different task attempt and the caller must first fence the old executor. This is a storage protocol, not permission to dispatch: it is not wired to either executor, and neither a stored UUID nor a binding proves exclusive ownership. Older serialized records without an attempt fail closed; older executors that ignore the new field cannot participate safely in this protocol.

An internal `ConversationLease` now acquires the same per-conversation worker mutex as conversation workers and retains it until drop. Acquisition and each checked commit validate the binding and cancellation epoch under the conversation poll gate followed by the task gate; timed version checks in composed batches retain their deadlines. Competing participating conversation workers cannot hold this lease simultaneously, and abort, attempt replacement or a stale transaction prevents its checked commit. A failed commit poisons that lease, requiring it to be dropped and the durable state inspected before a new attempt. It does not own or stop the independently running task-scheduler handler, cannot prove that a previous executor was joined, and is not wired to nested dispatch. In particular, a lock released by process death is not itself proof that task-side external work stopped or can be replayed. A host must establish both executor lifetimes and recovery policy before any tool effects are dispatched.

The private task-driver `try_quiescent_commit` now takes the scheduler mutex without waiting, rejects active or poisoned scheduler execution, and holds it through acquisition of that conversation lease and its checked commit. Since the driver holds the same mutex across each synchronous handler and settlement, a successful commit cannot overlap such a handler. Failed scheduler ticks publish the stopped state before releasing that mutex, including errors before attempt reservation. It checks driver shutdown at entry; shutdown can race a commit already in progress. Callers must hold no conversation worker, poll, control-registry, or task gate when entering; the scheduler try-lock does not make the later fences nonblocking. It neither interrupts a running handler nor joins work detached by a handler, and does not extend the lease over asynchronous execution or external effects. A normally settled handler has already left `Running`, so this method alone does not create a usable transfer point; the interleaving test sets up a running binding directly to test the fence. The private method is not wired to nested dispatch; its busy result requires a later retry outside conversation/task gates.

The `live_tool_and_task_handler_have_no_existing_handoff_window` runtime regression exercises both actual executors rather than a fabricated running task: a scheduled conversation invokes a blocked tool while an attached task scheduler runs a registered blocked handler. Even after a binding is committed, the conversation lease is busy while the tool is live. When the handler returns, its task attempt has already been cleared; while the tool remains live the worker is still busy. Once the tool returns an uncertain outcome, the conversation is blocked and the binding is stale. This confirms there is no existing point at which the old task handler has retired, its attempt is retained, and the live conversation worker is available for transfer.

The missing integrated transition is not safely supplied by adding a scheduler-only retirement marker. The conversation must commit a distinct suspended tool phase and release its worker without treating the handoff as a `Pending`, `Unknown`, or terminal `ToolReply`; the scheduler must commit a distinct retired/transfer state, its attempt identity and staged documents at the handler settlement boundary. Their token and child ownership must be atomically related, or intermediate commits must have explicit fail-closed recovery. Abort must invalidate the token and drain owned children even if the scheduler handler has already returned; reopen must distinguish an interrupted unsafe run from a committed suspension. Current `NestedHost::seal_and_wait` cancels or rejects outstanding nested work, and the tool reply has no checkpoint/wake payload. Those changes, plus tool-visible wake data and real tool-executor cancellation, are required before this can be an end-to-end handoff. A scheduler-only transfer would still face the busy conversation worker and could strand a `Running` task on abort or reopen. Upstream still describes owned `wait: false` children and a parked parent at [pi `76c79d8`](https://github.com/earendil-works/pi/blob/76c79d8bbe66993f2006b3c070544ca7c61150de/packages/durable/README.md#tools-that-park).


Tests cover competing prepared admissions, keyed park races with admission, abort and child transitions, identity and ownership validation, child replay policy, scheduler wake and abort across reopen, atomic document/park commits and conflicts, and uncommitted versus committed admission. A staged timed signal to a waited-for child retains its deadline fence when composed with the park; expiry rolls back the signal, document changes and park together. A process-kill regression now interrupts an actual generic task handler after child-wake reservation: replay-safe recovery sees the same frozen wake, while an unsafe interrupted handler is not reinvoked. It does not exercise a conversation-tool transfer. The conversation uses a per-conversation worker, poll gate and cancellation epoch; the generic scheduler instead owns a running task reservation and releases its task gate while invoking a handler. Actual transfer still needs scheduler and conversation integration that holds the correct worker/poll fences before the task gate and retires old work before replay. A separate commit from within the current handler would invalidate the scheduler's captured task version. Further work must integrate scheduler-backed tool execution with that lifecycle, compose the park within the scheduler's own handler commit, expose wake information to the tool, and define cancellation and settlement before claiming parallel parked-tool compatibility. Existing nested replay and detached-child tests remain relevant but do not establish these guarantees.

Custom JSON-object documents have version-checked writes and deletes, historical reads at recorded revisions, and checked batches that compose document changes with prepared task writes. Admission can atomically compose checked document operations and task creation; conversation forks copy eligible conversation-scoped documents. These are narrower than upstream document drafts, lifecycle, observation, upstream document incarnations and lazy initializers, deferred visibility and general session transactions. See the [document API](../crates/durable/src/document.rs) and [transaction tests](../crates/durable/tests/document_transactions.rs).

## Verification baseline

For the already implemented subsets, run `cargo test -p durable-store` and `cargo test -p pi-rs-durable`; the standalone example `cargo run -p pi-rs-durable --example resume -- start DB_PATH` followed by `resume DB_PATH CONVERSATION_ID` demonstrates admission across two processes, not full upstream compatibility. Run upstream tests against the pinned upstream revision when implementing a specific compatibility gate. For crash cases use process termination and controlled barriers, not graceful shutdown or timing-dependent sleeps. No general exactly-once guarantee follows from local persistence.

### Opt-in provider request bodies

A host can install a `model::ProviderAdapter`, then select its stable, versioned
ID for a settled conversation with `Harness::select_provider_adapter`. Selection
is persisted (including in fork snapshots); after reopening, install the same
adapter and selected extensions on `open_paused` before resuming. A missing or
mismatched adapter fails closed. Unselected conversations continue to use the
existing `Model` interface. Core and built-in providers are unchanged.

The adapter prepares the provider JSON body without dispatching. The selected
`BeforeProviderRequest` hooks receive `{model, payload}` in selection order and
return `Replace({"payload": ...})` or `Pass`. The model here is the configured
model name, not upstream's full model descriptor. Each replacement feeds the
next hook. The runtime rejects hook errors, malformed replacements, non-object
or over-8-MiB bodies, then calls the host's provider-specific validation before
dispatch. The host must implement both validation and guarded dispatch, and
must send exactly the validated body while enforcing authorization, endpoint
and budget policy. The adapter is trusted code; the runtime cannot enforce its
internal behavior. Hook failures deliberately fail closed, whereas upstream
reports the error and continues the chain (upstream pi commit
`1cfb326bfcc5c221526809fa081c4ff85b459847`,
`packages/durable/src/harness/generation.ts` and `CHANGELOG.md`).

The attempt carries the committed conversation and request IDs, turn, retry
count and restart count. New generation attempts after retry or recovery get a
new request ID. Hook context contains the persisted conversation snapshot and
request-scoped durable memo. Bodies and arbitrary hook side effects are not
checkpointed: hooks and preparation run again for each attempt and should use
memo for stable values. Cancellation stops preparation, hook execution or
stream collection, but cannot prove a remote request did not execute; recovery
settles the abandoned request as unconfirmed. As upstream, compaction bypasses
this generation hook. Unlike upstream pi-ai, provider-internal HTTP retries or
body rebuilds are not intercepted; adapters must avoid hidden rebuilds or guard
them themselves. This interface does not retrofit built-in provider clients,
settlement, exactly-once network execution, or automatic adapter installation.

**Generic task wake hints and snapshot:** `Driver::subscribe_wake` supplies a
single initially signaled, capacity-one coalescing channel. `wake_snapshot(now)`
inspects generic task readiness, blocked definitions and the nearest future
durable deadline without invoking handlers or migrations. The standalone task
scheduler provides the same view. Unlike upstream
[`onWake`](https://github.com/earendil-works/pi/blob/c1d4b0ac3e35dc4eb1c5d00d90bf54003cf517c0/packages/durable/src/harness/scheduler.ts#L566),
notifications are hints rather than changes to `{active, at}`; polling continues,
conversation scheduling is excluded, and inspection can wait for a handler.
Scheduler and driver signal delivery is fenced with inspection; direct TaskStore
writes are outside that protocol. Satisfied waits count as active even when their definition is blocked, and abort
cleanup candidates may still depend on conversations. Fail-fast sibling cleanup
is not independently represented. See [snapshot tests](../crates/durable/tests/task_wake_snapshot.rs).
