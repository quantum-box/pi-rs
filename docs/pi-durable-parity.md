**Unified history checkpoint:** `Harness::unified_history_start` captures a finite store commit boundary and `unified_history` pages complete commit frames in sequence order (1–255 frames per page). Frames expose expanded runtime observation snapshots and full task application-log snapshots, including inherited records at a fork's own commit. They do not reconstruct parent commit history for a fork, per-entry order within one commit, or upstream's immutable transcript entry semantics. A snapshot can repeat earlier messages and application entries; task entries are not model context. On a store with any pre-tracking versions, the default start fails closed; explicitly accepting the migration boundary reads only tracked commits and does not reconstruct earlier ordering. Cursors are trusted, database-local, serializable host data; pages capture a fixed upper boundary and can resume after reopen. Sequence gaps include unrelated commits. Frames and values may be large; SQL work, expanded transcript traversal and application-log snapshots are not bounded by the page count. Raw namespace mutation/deletion, old writers and cross-database cursors invalidate guarantees. Existing history and application APIs are unchanged. See [tests](../crates/durable/tests/features.rs) and [upstream entries](https://github.com/earendil-works/pi/blob/main/packages/durable/README.md#concepts).

**Historical fork checkpoint:** `fork_at` accepts a committed observation cursor even when the parent was active, provided the captured model context has a complete tool-call/result batch. **Message-position fork checkpoint:** `fork_at_position` accepts a positioned message only when it is the last message of a nonempty immutable batch and the first observation referencing that batch has complete fork metadata with the same transcript cursor. It uses that commit's configuration and state, validates the complete tool transcript, and creates an idle child atomically using the existing fork path. Later configuration changes do not alter the cut. Positions survive resets and reopening. Migrated legacy batches do not acquire fabricated entry identities and position forks reject them. Inherited entry IDs can be forked only when their annotated batch is visible in the selected conversation’s captured immutable chain; the origin observation and its document cut are used. **Same-commit configuration checkpoint:** Compared with upstream [`session-forks.test.ts`](https://github.com/earendil-works/pi/blob/17d6ca759a070c377147f6d76b72dab9a3ba42a3/packages/durable/test/session-forks.test.ts), which copies final document state from the selected entry’s commit, new tool-free append batches can be forked at an interior entry when only model configuration changes in that commit. **Interior entry fork checkpoint:** New append batches record a versioned proof when all runtime fork-state fields (configuration, queue modes, extensions, provider adapter, allowed tools, tool state, resets and application writes) are unchanged across the atomic commit. A fork by occurrence ID or position may truncate such a batch at an interior message, using that commit's state, only when the resulting context has complete and valid tool calls and results. Child creation remains atomic and the parent is unchanged; reopening preserves the child. Older batches, other state-changing batches, and replacement batches do not acquire proof retroactively and reject interior cuts; the same-commit configuration checkpoint above describes the tool-free exception. **Entry metadata checkpoint:** New immutable message batches carry a UUID per message occurrence and the originating conversation and observation sequence for the atomic commit that stored them. The matching historical fork snapshot contains that commit's configuration, tool state and runtime documents. These values describe the whole commit; only the last message in a batch has an exact commit boundary. Intermediate messages must not be interpreted as having independently captured state. Existing inline and transcript batches remain readable without fabricated IDs; position forks reject unannotated batches. Replacement batches (including reset/compaction) assign new IDs to replacement occurrences; they do not preserve identities across context reconstruction. Inherited entries retain their original conversation/commit association. `fork_by_entry_id` resolves IDs by scanning retained observations in bounded pages, including after resets and reopening, and forks only a proven final batch message using its original commit. Visible inherited chains are checked for ambiguous IDs before selecting a local match, and duplicate occurrences or unprovable chains fail closed. Missing provider/tool settings and unproven foreign occurrences fail closed; the inherited-entry checkpoint above describes the supported shared-chain case. The child starts idle without parent abort work; the parent abort state is untouched. Historical state between messages in one batch, application entries and complete external document/task history remain unsupported. Metadata grows linearly with message count (one UUID per occurrence plus one origin and sequence per batch); UUID generation and JSON serialization add CPU, while existing full snapshot reconstruction and retained commit snapshots remain unbounded. **Conversation-owned task abort checkpoint:** A conversation abort atomically marks its live generic and lifecycle task descendants and withdraws queued inputs. Root and lifecycle admission are fenced while the mark is active; an in-flight task cannot publish children after its mark. Reopening resumes task cleanup child-first, and the conversation stays abort-marked until its owned tasks settle. This requires an attached task scheduler or driver to make progress. Handler interruption remains cooperative: active synchronous handlers cannot be signalled and must return before cleanup; cleanup can replay after a crash and must be idempotent. Missing abort handlers fail with an orphan diagnostic, and restart exhaustion can fail without cleanup. Direct TaskStore mutations and noncooperating executors are outside the ownership protocol. Unlike current upstream, pi-rs has no background-task ownership flag: all conversation-owned generic tasks are included; reporter/subagent conversation links remain independent. `abort_and_wait` waits for local conversation workers, which poll task cleanup; blocked external effects still require reconciliation.

**Historical background task boundary checkpoint:** Conversation-owned generic tasks can be marked background at creation. Ordinary conversation abort and its task-drain check skip that task and its descendants, including after reopening; explicitly aborting the task still marks its subtree. Child tasks cannot be marked background through this API. The preceding checkpoint's statement that all generic tasks are included is superseded. This is only a task-graph prerequisite: subagent links and reporters are not owned by these tasks, there is no conversation abort option to cross background boundaries, and upstream ownership-aware idle, terminal-owner traversal, task-to-conversation cascades and abnormal-completion propagation are not implemented. Existing reporter children therefore remain independent of parent abort, and foreground subagents are not yet supported as owned tool scopes.


**Opt-in task-owned subagent admission:** `Harness::ensure_task_owned_subagent` and its scheduler counterpart atomically create an empty child conversation, permanent task-scoped reservation and ownership edge while advancing the parent task version. Matching retries return the same child, including after abort and reopen; changed owner, configuration or mode is rejected. Admission refuses an already aborting or terminal task. This does not submit input, schedule execution, seed history, or reject longer cycles. Harness abort traversal follows foreground ownership edges as described below. Existing named subagents remain independent. Storage errors require reopening before retry. See `owned_subagent` tests.

**Task-owned initial input:** `Harness::submit_task_owned_subagent` atomically creates the ownership reservation, edge and runnable initial input under the parent task version fence. Matching retries return the original child and submission, including after abort or reopen; changing the input or using the empty-child API with the same key is rejected. `Scheduler::submit_task_owned_subagent` schedules after commit, and reopening recovers a committed child if scheduling was interrupted. Foreground abort traversal and background boundaries follow the ownership rules below. This opt-in API does not seed parent history or configure extensions; storage errors require reopening. See `owned_subagent` tests.

**Foreground ownership abort traversal:** `Harness::request_abort` and `Harness::request_abort_task` atomically persist abort marks across foreground task and conversation ownership edges, withdraw queued inputs, skip background branches, and fence visited records and edges against concurrent admission. Cycles terminate; conflicts retry the complete traversal. Direct store writers outside the ownership protocol are not fenced. The standalone task scheduler and task driver still fail closed on foreground conversation edges; they do not signal or join child conversation workers. Hosts must stop and drive those workers separately, including after reopening, until scheduler propagation is implemented. A storage error can have an uncertain outcome and requires reopening. See `owned_subagent` tests.

**Child-first owned cleanup checkpoint:** Compared with upstream [abort and subagents](https://github.com/earendil-works/pi/blob/06f5671c924cd6eaa1d7501736925db0e5cb2a49/packages/durable/README.md#abort-and-subagents), which waits for the conversation to become idle and supports explicitly crossing background boundaries, this implementation retains the boundaries and limitations below. Task abort cleanup waits for each foreground owned conversation to finish its persisted abort, including that conversation's foreground task descendants. Restart-limit failures also wait for those children. `Scheduler::abort_and_wait` joins the workers for all conversations marked by the atomic traversal. Ordinary abort retains background boundaries; explicit background-inclusive abort crosses them. Cyclic ownership may deadlock cleanup; blocked uncertain operations require reconciliation and generic tasks require a running driver. The standalone task scheduler and driver still reject aborts involving foreground conversation edges. See `owned_subagent` tests.

**Earlier scheduler propagation checkpoint (superseded by child-first checkpoint above):** `Scheduler::abort` and `abort_task` fence existing conversation polls while committing the foreground graph, cancel affected workers, and schedule each marked conversation for cleanup. Reopening schedules all persisted conversations. Background edges remain independent. Standalone task abort still rejects foreground child conversations, and task cleanup does not join child conversation cleanup; `abort_and_wait` waits only for the requested conversation's local workers. Active nested-conversation race and crash/reopen coverage remains incomplete. Legacy task cancellation fails closed when it would strand a foreground child. See `owned_subagent` tests.

**Ownership edge storage checkpoint:** `ownership_edge::EdgeStore` prepares checked, atomic task-to-existing-conversation links with explicit foreground/background metadata and a unique owner per child. Both endpoint versions and task ownership are fenced at commit, and edge creation advances the task version to invalidate a concurrent traversal's earlier task snapshot. Edges survive reopen. This is only a composable storage primitive: creation of the conversation and task must currently precede the edge; no traversal, cycle detection beyond a direct self-edge, scheduling, abort propagation, lifecycle cleanup, or subagent integration is provided. Edge mode is stored metadata and does not itself implement upstream background boundaries. See [ownership edge tests](../crates/durable/tests/ownership_edge.rs).

**Continue checkpoint:** `Harness::submit_continue` and `Scheduler::submit_continue` persist a distinct, deduplicated run submission without a user message, reject busy conversations, place queued steers and follow-ups according to the configured queue modes, and settle the participating submissions together. Empty or answered contexts settle `nothing_to_answer` without a model request; failed runs retain their unanswered user/tool context. Recovery resumes the committed phase, and truncated tool calls are recorded as skipped without dispatch. See [continuation tests](../crates/durable/tests/continue_submission.rs) and [runtime tests](../crates/durable/tests/runtime.rs). Unlike upstream, this runtime has no public transactional/tool-side admission, `pi.live.runFailure`; it uses Rust status and reason strings and represents continue content as an empty compatibility field in memory (omitted from storage). Historical synthetic failure messages from older versions are not rewritten. Queued reset ordering and generic task ownership remain separate gaps.

**Admission policy checkpoint:** `Harness`, `Scheduler`, and the state-backed
conversation helper now support optional busy and idle rejection for input,
with request-ID deduplication before the policy check and version-checked
admission under contention. Busy means an active run, even when queued input
remains after a failed run. Duplicate input request IDs are resolved before content validation. Arbitrary host transactions / `submit(tx, draft)` are not supported. See the admission concurrency and recovery tests in
[`runtime_cas_tests.rs`](../crates/durable/src/runtime_cas_tests.rs). The
original audit table below remains a historical baseline.
**Write-submission checkpoint:** The experimental runtime accepts display-only application entries through `submit_write`, persists them immediately while busy, and delays placement behind queued resets. Request IDs deduplicate within the conversation and cannot be reused across input and write types. Entries are exposed in `Conversation.application_writes` and observer snapshots with a placement flag and preceding reset ID. This is a narrower API than upstream: model messages, head edits, stale-head handling, generic entry transactions and write withdrawal are not implemented. Current forks and historical snapshots created after this change inherit application entries at the selected point, but not their request IDs. Queued writes are exposed as pending records, not placed transcript entries; observers must filter `placed`. The runtime still stores snapshots rather than an upstream ordered entry stream.

**onYield checkpoint:** Final answers enter a persisted onYield phase with a stable hook memo. A string continuation keeps the current submissions open and starts a fresh turn budget; queued steering, follow-ups, or resets take precedence, and after-run hooks run only once an answer stands. Hook-created tasks and their wait are committed atomically; after all children terminate, the first successful child in creation order with a nonempty string `{"continue": "..."}` is selected. Failed and invalid child outcomes are ignored. A registered task driver is required, and reopening resumes the persisted wait. Hooks may replay after interruption or a concurrent admission and must make effects idempotent. Unlike upstream, this subset accepts only string continuation input, exposes the already-committed answer in the hook snapshot, and treats invalid hook decisions or hook errors as recoverable phase errors rather than reporting and skipping them. Conversation abort marks owned hook children and descendants atomically and waits for cleanup with an attached task driver; synchronous effects still cannot be interrupted or rolled back. See [extension runtime tests](../crates/durable/tests/extension_runtime.rs).

**beforeCompact checkpoint:** Manual, threshold and overflow compactions persist the selected message range and a stable hook memo identity before calling selected hooks. The first decline or summary wins; hook errors are skipped, cancellation replays the phase, and hook summaries bypass model usage. Unlike upstream, the host exposes message indices instead of entry IDs and markers, has no manual instructions parameter or hook report callback, rejects blank summaries, and still requires idle manual compaction. See [compaction tests](../crates/durable/tests/features.rs).

**After-tools termination checkpoint:** A successful after-tools child result of exactly `{ "terminate": true }` settles active inputs with the tool-calling assistant answer, runs after-run hooks, and only then places queued inputs at the final boundary. The persisted child wait resumes after reopening. Other results are ignored without upstream’s invalid-decision report. Opt-in `KeyedTool::invoke_controlled` can return a terminate control; a nonempty round ends when every call requests it, with controls committed alongside tool outcomes and preserved across reopen. Ordinary tools and synthesized errors have no control. Handoff and other tool controls are not implemented. See [extension runtime tests](../crates/durable/tests/extension_runtime.rs).

**Queue delivery checkpoint:** Durable conversations persist independent steering and follow-up delivery modes, defaulting to one at a time for new and legacy records. `all` selects every queued input of that kind at the eligible boundary. Final boundaries settle the previous run before starting the selected successor inputs; post-tool boundaries select steers only. See [durable README](../crates/durable/README.md).

**Typed signal checkpoint:** Task signals optionally record a versioned token and structured kind/key and survive reopen; matching is by kind and key. Typed keys hold a single value per task, reject conflicting deliveries, and close to further waits after consumption; identical retries with another ID do not create another receipt. Schema-bearing tokens validate constructed values and typed reads; older versions require an explicit read-only migration, and failures leave receipts unchanged. Legacy tokens, raw receipt reads and wake results bypass schema checking. `deliver_signal` returns upstream-shaped delivery outcomes. Typed deadline-or-signal sleeps retain wake reasons through recovery until checkpoint progress, another wait, or termination, and atomically expire empty keys against concurrent delivery; status delivery checks deadlines using wall time or an explicit clock. The older receipt-based `send_signal` reports expiry as an error. Opt-in `TaskDocuments::signal_at` stages multiple distinct typed deliveries to other tasks, including distinct keys on the same target with the checkpoint and document batch; its outcome is provisional and task/version and signal-revision conflicts roll back the whole attempt. It anchors a caller-supplied staging time to monotonic elapsed time and conflicts if an empty matching key crosses its deadline before the storage commit boundary; replay must supply a fresh time, and clock jumps after staging are not observed. It rejects repeated typed keys within one invocation (upstream returns duplicate), excludes self-delivery (upstream permits it), and rejects overlaps with other batch participants’ checked keys; it is not general upstream transactional delivery. Preexisting duplicate typed records are not consolidated and typed reads reject ambiguity. Legacy signals remain separate. See [typed signal tests](../crates/durable/tests/typed_task_signals.rs) and [deadline tests](../crates/durable/tests/typed_signal_deadlines.rs).

## Verification baseline

For the already implemented subsets, run `cargo test -p durable-store` and `cargo test -p pi-rs-durable`; the standalone example `cargo run -p pi-rs-durable --example resume -- start DB_PATH` followed by `resume DB_PATH CONVERSATION_ID` demonstrates admission across two processes, not full upstream compatibility. Run upstream tests against the pinned upstream revision when implementing a specific compatibility gate. For crash cases use process termination and controlled barriers, not graceful shutdown or timing-dependent sleeps. No general exactly-once guarantee follows from local persistence.

### Opt-in provider request bodies

A host can install a `model::ProviderAdapter`, then select its stable, versioned
ID for a settled conversation with `Harness::select_provider_adapter`. Selection
is persisted (including in fork snapshots); after reopening, install the same
adapter and selected extensions on `open_paused` before resuming. A missing or
mismatched adapter fails closed. Unselected conversations continue to use the
existing `Model` interface. Core and built-in providers are unchanged.

The adapter prepares the provider JSON body without dispatching. The selected
`BeforeProviderRequest` hooks receive `{model, payload}` in selection order and
return `Replace({"payload": ...})` or `Pass`. The model here is the configured
model name, not upstream's full model descriptor. Each replacement feeds the
next hook. The runtime rejects hook errors, malformed replacements, non-object
or over-8-MiB bodies, then calls the host's provider-specific validation before
dispatch. The host must implement both validation and guarded dispatch, and
must send exactly the validated body while enforcing authorization, endpoint
and budget policy. The adapter is trusted code; the runtime cannot enforce its
internal behavior. Hook failures deliberately fail closed, whereas upstream
reports the error and continues the chain (upstream pi commit
`1cfb326bfcc5c221526809fa081c4ff85b459847`,
`packages/durable/src/harness/generation.ts` and `CHANGELOG.md`).

The attempt carries the committed conversation and request IDs, turn, retry
count and restart count. New generation attempts after retry or recovery get a
new request ID. Hook context contains the persisted conversation snapshot and
request-scoped durable memo. Bodies and arbitrary hook side effects are not
checkpointed: hooks and preparation run again for each attempt and should use
memo for stable values. Cancellation stops preparation, hook execution or
stream collection, but cannot prove a remote request did not execute; recovery
settles the abandoned request as unconfirmed. As upstream, compaction bypasses
this generation hook. Unlike upstream pi-ai, provider-internal HTTP retries or
body rebuilds are not intercepted; adapters must avoid hidden rebuilds or guard
them themselves. This interface does not retrofit built-in provider clients,
settlement, exactly-once network execution, or automatic adapter installation.

**Generic task wake hints and snapshot:** `Driver::subscribe_wake` supplies a
single initially signaled, capacity-one coalescing channel. `wake_snapshot(now)`
inspects generic task readiness, blocked definitions and the nearest future
durable deadline without invoking handlers or migrations. The standalone task
scheduler provides the same view. Unlike upstream
[`onWake`](https://github.com/earendil-works/pi/blob/c1d4b0ac3e35dc4eb1c5d00d90bf54003cf517c0/packages/durable/src/harness/scheduler.ts#L566),
notifications are hints rather than changes to `{active, at}`; polling continues,
conversation scheduling is excluded, and inspection can wait for a handler.
Scheduler and driver signal delivery is fenced with inspection; direct TaskStore
writes are outside that protocol. Satisfied waits count as active even when their definition is blocked, and abort
cleanup candidates may still depend on conversations. Fail-fast sibling cleanup
is not independently represented. See [snapshot tests](../crates/durable/tests/task_wake_snapshot.rs).
