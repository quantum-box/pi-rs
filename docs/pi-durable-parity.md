# Pi Durable compatibility inventory

This is an audit, not an implementation plan or a claim of complete compatibility.
Compared 2026-11-14: upstream [`earendil-works/pi` 827383a15262905f82e418483825a49dbb1adbf5](https://github.com/earendil-works/pi/tree/827383a15262905f82e418483825a49dbb1adbf5/packages/durable) (the fetched upstream HEAD) with pi-rs `4ab1c4f442698d8b3888e603f6675e808d36fa16`. All pi-rs paths below refer to that commit. The experimental `pi-rs-durable` runtime is independent of the existing CLI, RPC, TUI and session journal; none is automatically backed by it ([README](../crates/durable/README.md)). A helper or a state type alone does not imply scheduler or user-facing support. This is an evidence-based inventory, not an exhaustive API or wire-format equivalence test.

P0 means recovery/effect safety or fundamental execution semantics; P1 means core user-visible behavior; P2 means integration, observability or scalability. These are suggested engineering priorities, not claims about implementation order. “Missing” means absent from the integrated runtime at this revision; “partial” means the stated subset exists, not that the feature has parity. “Intentional” requires documentation of the decision; an unimplemented feature is not automatically intentional. Tests below are proposed acceptance tests unless explicitly identified as existing. Existing tests are evidence of their own scope, not proof of complete parity.

**Later checkpoint:** Since the audited revision, the runtime gained one-at-a-time active steering, bounded-page observation, settled historical-snapshot forks, bounded generation progress recovery, and context-window-triggered compaction. These cover subsets only: upstream busy/idle policies and arbitrary entry forks, full live/aborted transcript semantics and provider-overflow compaction remain open. A generic task scheduler is available as a separately owned, explicitly ticked component; it is not integrated into the conversation scheduler. The table retains the original audit baseline for reproducibility.

**Subsequent checkpoint:** Busy reset queues at safe boundaries, provider-overflow compaction and persisted bounded exponential retry were added. A host can attach a background generic task driver to the conversation store, with direct-child all/any/fail-fast waits and local descendant cancellation. A persistent subagent link can resume child admission. Task lifecycle/abort ownership is not yet integrated with conversation execution, reset ordering and tool handoff are incomplete, and subagent links do not yet supply automatic answer reporting or ownership-aware abort.

**Latest checkpoint:** Subagent completion can now be reported automatically to its parent, and reporter-driven conversations continue polling pending tools. Queued submissions can be withdrawn. Conversation extension selections, prompt sections and before-tool gates are persisted; the scheduler can preload an extension registry before automatic recovery. Extension-provided tools and the remaining hooks are not yet integrated. Subagent cancellation is not yet an ownership-aware cascade. The original table below remains a historical audit and should be read together with these checkpoints.

**Abort and reporter checkpoint:** `Scheduler::abort` persists conversation aborts, withdraws queued inputs and fences both ordinary and reporter-driven dispatch; `abort_and_wait` waits for local workers. A dispatched uncertain effect requires reconciliation even if replay-safe. Background reporter children remain independent: parent abort does not propagate through an ownership tree. See [abort tests](../crates/durable/tests/abort.rs) and [reporter tests](../crates/durable/tests/reporter_pending.rs).

**Admission policy checkpoint:** `Harness`, `Scheduler`, and the state-backed
conversation helper now support optional busy and idle rejection for input,
with request-ID deduplication before the policy check and version-checked
admission under contention. Busy means an active run, even when queued input
remains after a failed run. Unlike upstream, runtime input validation still
precedes deduplication, and arbitrary host transactions / `submit(tx, draft)`
are not supported. See the admission concurrency and recovery tests in
[`runtime_cas_tests.rs`](../crates/durable/src/runtime_cas_tests.rs). The
original audit table below remains a historical baseline.

| **P0 — generic tasks, ownership and crash recovery** | **Partial / missing integration.** Upstream schedules registered checkpointed tasks and owned children, including abort and restart handling ([spec §5](https://github.com/earendil-works/pi/blob/827383a15262905f82e418483825a49dbb1adbf5/packages/durable/docs/spec.md#5-tasks)). Existing [recovery fixtures](../crates/durable-tests/README.md) are **not executable tests**. |
| **P0 — durable sleeps, signals and child waits** | **Partial / missing integration.** Upstream tasks and parked tools can sleep on deadlines/signals and wait for owned tasks ([spec sleep](https://github.com/earendil-works/pi/blob/827383a15262905f82e418483825a49dbb1adbf5/packages/durable/docs/spec.md#56-sleeping-timers-and-wakeups), [signals](https://github.com/earendil-works/pi/blob/827383a15262905f82e418483825a49dbb1adbf5/packages/durable/docs/spec.md#57-signals)). Test fake-clock downtime past deadline, duplicate signals and all/any child completion across kill/reopen; separately assert pending poll does not redispatch ([existing pending tests](../crates/durable/tests/pending.rs)). |
| **P0 — tool effects and reconciliation** | **Partial; intentional extension.** Upstream persists intent and replays interrupted tools only when both recorded and current registrations permit it; otherwise it produces interruption ([tool docs](https://github.com/earendil-works/pi/blob/827383a15262905f82e418483825a49dbb1adbf5/packages/durable/README.md#tools)). Rust implements that default plus opt-in `RequireReconciliation`, and blocks explicit unknown outcomes ([recovery](../crates/durable/src/recovery.rs), [runtime](../crates/durable/src/runtime.rs)). | Unsafe calls are not blindly repeated; reconciliation can hold a conversation until resolved, an intentional pi-rs difference. External exactly-once effects still require destination idempotency. Test real process death after dispatch and before result commit, both policy changes, unknown and conflicting resolutions; existing [runtime tests](../crates/durable/tests/runtime.rs) cover selected crash and policy cases. |
| **P0 — atomic commits and storage** | **Partial; intentional storage difference.** Upstream session transactions atomically publish entries, tasks and documents, and also support explicitly deferred document-only visibility ([spec §4](https://github.com/earendil-works/pi/blob/827383a15262905f82e418483825a49dbb1adbf5/packages/durable/docs/spec.md#4-transactions-and-storage-ownership)). Rust provides atomic checked key/value batches and SQLite WAL/FULL, but no upstream session/document transaction API or deferred visibility; the runtime stores a conversation as one growing JSON value ([store README](../crates/durable-store/README.md), [runtime](../crates/durable/src/runtime.rs), [design](pi-durable-design.md)). | A host cannot atomically combine arbitrary application documents, upstream task creation and submission via the upstream API; no provisional deferred updates are exposed. No deferred visibility and local single-owner scope are documented design choices, not storage-format parity. Test commit failure/kill before and after transaction, reopen for all-or-none state, lost acknowledgement and contention between independent processes. |
| **P1 — admission, steering and settlement** | **Partial.** Upstream input supports follow-up, steer, busy/idle rejection, writes and continue, with submission settlement ([busy conversations](https://github.com/earendil-works/pi/blob/827383a15262905f82e418483825a49dbb1adbf5/packages/durable/README.md#busy-conversations)). Runtime `submit` accepts durable input and request IDs, and queues behind a run; it does not steer during a run ([runtime](../crates/durable/src/runtime.rs), [README](../crates/durable/README.md)). `state`/`conversation` helpers are not evidence that runtime steering is wired up. | A new message waits for the active run instead of changing its next tool-round context. Reusing a request ID returns the original submission even if the supplied content differs; upstream busy/idle and write/continue semantics should not be assumed. Test concurrent input at a held tool round, duplicate ID with same/different content and crash after admission; existing [admission recovery test](../crates/durable/tests/admission_recovery.rs) covers committed admission/resend. |
| **P1 — nested tools and subagents** | **Partial.** Upstream nested calls support positional or explicit keys, parallel parked children and task ownership; a built-in subagent is available ([nested calls](https://github.com/earendil-works/pi/blob/827383a15262905f82e418483825a49dbb1adbf5/packages/durable/README.md#calling-tools-from-tools)). Rust journals nested calls in order, serializes and bounds depth, and has no built-in subagent or integrated generic child graph ([nested](../crates/durable/src/nested.rs), [README](../crates/durable/README.md)). | Replayed parent calls can reuse completed children; dynamic keyed/parallel orchestration and upstream subagent behavior cannot be assumed. Test crash/replay, reordered or changed arguments, unsafe child, parent cancellation and depth/parallel cases; existing [nested runtime tests](../crates/durable/tests/nested_runtime.rs) cover reuse and uncertain children. |
| **P1 — model generation and progress** | **Partial.** Upstream commits partial generation/tool progress, exposes live views and has deferred persistence windows ([watching](https://github.com/earendil-works/pi/blob/827383a15262905f82e418483825a49dbb1adbf5/packages/durable/README.md#watching-a-conversation)). Rust collects progress separately from an authoritative completed generation and retries interrupted requests; durable streaming partials are absent ([model](../crates/durable/src/model.rs), [README](../crates/durable/README.md)). | A client cannot recover or watch upstream-style durable partial text; a retried model request may incur additional cost and produce different text. Test kill mid-stream and after completion commit, verify partials do not become a committed answer and committed output is not regenerated; existing [model tests](../crates/durable/src/model_tests.rs) cover stream completion/cancellation. |
| **P1 — compaction and reset** | **Partial.** Upstream manual compaction may run concurrently and automatic threshold/overflow compaction is supported; reset/handoff changes context while retaining history ([compaction](https://github.com/earendil-works/pi/blob/827383a15262905f82e418483825a49dbb1adbf5/packages/durable/README.md#compaction), [reset](https://github.com/earendil-works/pi/blob/827383a15262905f82e418483825a49dbb1adbf5/packages/durable/README.md#reset-and-handoff)). Rust supports explicit idle compaction, not automatic/background compaction or upstream reset/handoff ([runtime](../crates/durable/src/runtime.rs), [compact](../crates/durable/src/compact.rs)). | Long conversations do not automatically compact at upstream thresholds; callers must request compaction while idle. Test idle compaction and reopen, busy rejection, old history preservation, threshold/overflow and stale concurrent summaries. Existing [feature test](../crates/durable/tests/features.rs) covers explicit compaction and old snapshots. |
| **P1 — historical forks** | **Partial.** Upstream forks at a chosen entry and inherits the agent as of that entry ([forks](https://github.com/earendil-works/pi/blob/827383a15262905f82e418483825a49dbb1adbf5/packages/durable/README.md#more-conversations-and-forks)). Rust forks only a settled conversation at its current state; submissions are not inherited ([runtime](../crates/durable/src/runtime.rs), [feature test](../crates/durable/tests/features.rs)). | A user cannot branch from an arbitrary earlier message through this runtime. Test multiple entry points, configuration at cut, independent subsequent changes and rejection of invalid cuts; existing test covers settled current-state copying. |
| **P1 — cancellation and structured abort** | **Partial.** Upstream aborts task subtrees and can withdraw queued submissions or cancel parked tools ([spec scheduler](https://github.com/earendil-works/pi/blob/827383a15262905f82e418483825a49dbb1adbf5/packages/durable/docs/spec.md#54-scheduler-abort-and-ownership), [busy conversations](https://github.com/earendil-works/pi/blob/827383a15262905f82e418483825a49dbb1adbf5/packages/durable/README.md#busy-conversations)). Rust has cancellation tokens and conservative handling of dropped execution, but not the integrated upstream task graph and abort API ([runtime](../crates/durable/src/runtime.rs), [nested tests](../crates/durable/tests/nested_runtime.rs)). | Cancelling a host future is not equivalent to upstream submission withdrawal and subtree abort; interrupted effects may need recovery. Test queued withdrawal, active child abort, parked cleanup and process death after abort mark, checking no orphan child or duplicate effect. |
| **P2 — observation and history** | **Partial, different surface.** Upstream watch exposes a bounded transcript window, live documents and folded operations ([watching](https://github.com/earendil-works/pi/blob/827383a15262905f82e418483825a49dbb1adbf5/packages/durable/README.md#watching-a-conversation)). Rust offers cursor-based `history`/`watch_history` of committed snapshots, scanning the stream; old pre-observer history is not backfilled ([observer](../crates/durable/src/observer.rs), [README](../crates/durable/README.md)). | Reconnecting readers can request later snapshots, but do not receive upstream live-view patches, transcript windows or streaming partials. Test slow reader/reconnect, exclusive cursor, pagination and old records; existing observer tests cover polling and reconnection. |
| **P2 — extensions, hooks and runtime integration** | **Partial.** Upstream has registry, per-conversation extensions and generation/tool/task hooks ([extensions](https://github.com/earendil-works/pi/blob/827383a15262905f82e418483825a49dbb1adbf5/packages/durable/README.md#extensions), [hooks](https://github.com/earendil-works/pi/blob/827383a15262905f82e418483825a49dbb1adbf5/packages/durable/README.md#hooks)). Rust supports selected extension tools, sections, before/after-tool hooks, before-request and after-response hooks; the existing pi-rs extension/CLI engine is separate ([runtime](../crates/durable/src/runtime.rs), [README](../crates/durable/README.md)). | Extension tools default to unsafe replay. Hook-requested tasks, on-yield, after-tools, after-run, provider-body hooks, and durable hook sleeps remain unintegrated; existing CLI extensions do not automatically gain Durable hooks. |
| **P2 — operational limits** | **Intentional current constraints / partial.** Upstream supports multiple storage adapters and windowed views ([upstream README](https://github.com/earendil-works/pi/blob/827383a15262905f82e418483825a49dbb1adbf5/packages/durable/README.md#persist-and-resume)); Rust uses local owner locking on cooperating Unix processes, growing whole-conversation JSON, snapshot scans and bounded model responses, and has no flow control ([README](../crates/durable/README.md), [owner](../crates/durable-store/src/owner.rs)). | This is a local experimental host, not distributed failover or an unbounded long-lived workload service. Test concurrent process ownership, crash/reacquire, supported filesystem aliases, large histories, bounded submissions and response limits. |

## Verification baseline

For the already implemented subsets, run `cargo test -p durable-store` and `cargo test -p pi-rs-durable`; the standalone example `cargo run -p pi-rs-durable --example resume -- start DB_PATH` followed by `resume DB_PATH CONVERSATION_ID` demonstrates admission across two processes, not the missing capabilities above. Run upstream tests against the pinned upstream revision when implementing a specific compatibility gate. For crash cases use process termination and controlled barriers, not graceful shutdown or timing-dependent sleeps. No general exactly-once guarantee follows from local persistence.
