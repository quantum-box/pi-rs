# Pi Durable compatibility inventory

Upstream was rechecked at commit `8636e211e7834e4ca46a22aec1d65dfd2eac8677` on 2026-11-14; `packages/durable` is unchanged from the audited `827383a15262905f82e418483825a49dbb1adbf5` baseline below.

**Task migration checkpoint:** Generic tasks persist definition version and input, and registered migrations atomically commit the new checkpoint together with execution reservation. Missing, newer or unmigratable definitions block execution and can be reconsidered after registry replacement or reopening. The background driver can replace registrations at a handler boundary and wakes its worker; `blocked_tasks` polls live blocked definitions and migration failures. Upstream report callbacks, graph integration, host wake notifications, migration panic handling and typed orphan outcomes remain incomplete. See the durable README and task scheduler tests.

**Current status:** The runtime supports durable model and tool execution, automatic recovery, task scheduling, transactional input/document admission, queue modes, continuation, extension gates and lifecycle tasks, local coding-tool adapters, snapshot views, and safe historical snapshot forks. These are subsets of upstream behavior. Principal open gaps include complete ownership lifecycle and cycle prevention; fully general entry-ID forks and upstream Chord watch operations; complete tool-output progress semantics; typed task-scoped signals; provider-body hooks for existing provider implementations; richer continuation inputs; and upstream storage and transaction surfaces. Hook callbacks and external effects still need idempotency. The dated checkpoints record incremental progress; later checkpoints supersede earlier ones. The priority table summarizes the current foundation revision.

**Tool attempt identity checkpoint:** A model-issued tool operation keeps its stable operation ID for reconciliation and nested calls, while each initial execution and safe replay commits a fresh attempt UUID before dispatch. The current attempt is available on running, pending, blocked and finishing conversation snapshots; polling, abort and reconciliation do not create another attempt. Older records without an attempt ID remain readable and report none until a replay is claimed. This is a pi-rs prerequisite for progress fencing, not upstream API parity: tool progress is now wired to attempt IDs and fenced on commit, but nested-tool attempt IDs are not exposed. External effects still require their own idempotency. See [runtime tests](../crates/durable/tests/runtime.rs), [pending tests](../crates/durable/tests/pending.rs), and [abort tests](../crates/durable/tests/abort.rs).

**Coding tools checkpoint:** The opt-in `coding-tools` feature registers the existing workbench local `read`, `write`, `edit`, and `bash` tools with unsafe replay policies. This is not a sandbox or an upstream environment adapter; schemas, structured results, streaming, diagnostics, image behavior, and file mutation serialization retain workbench behavior. Interrupted effects need interruption handling or reconciliation. Upstream reference: `packages/durable/src/tools` and `packages/durable/src/harness/tool.ts` at commit `3035f08d06c3054f99b6226ea1ad22353c49fc12`.

This is an audit, not an implementation plan or a claim of complete compatibility.
Compared 2026-11-14: upstream [`earendil-works/pi` 827383a15262905f82e418483825a49dbb1adbf5](https://github.com/earendil-works/pi/tree/827383a15262905f82e418483825a49dbb1adbf5/packages/durable) (the fetched upstream HEAD) with pi-rs `4ab1c4f442698d8b3888e603f6675e808d36fa16`. The original audit used that pi-rs commit; the current priority table was checked against pi-rs `f770aff39feb4c2c30349da64fbd0222dacc5532` and upstream `827383a15262905f82e418483825a49dbb1adbf5`. The experimental `pi-rs-durable` runtime is independent of the existing CLI, RPC, TUI and session journal; none is automatically backed by it ([README](../crates/durable/README.md)). A helper or a state type alone does not imply scheduler or user-facing support. This is an evidence-based inventory, not an exhaustive API or wire-format equivalence test.

P0 means recovery/effect safety or fundamental execution semantics; P1 means core user-visible behavior; P2 means integration, observability or scalability. These are suggested engineering priorities, not claims about implementation order. “Missing” means absent from the integrated runtime at this revision; “partial” means the stated subset exists, not that the feature has parity. “Intentional” requires documentation of the decision; an unimplemented feature is not automatically intentional. The table links existing tests as evidence of the stated subsets; suggested tests identify remaining verification work. Existing tests are evidence of their own scope, not proof of complete parity.

**Later checkpoint:** Since the audited revision, the runtime gained one-at-a-time active steering, bounded-page observation, settled historical-snapshot forks, bounded generation progress recovery, and context-window-triggered compaction. These cover subsets only: upstream busy/idle policies and arbitrary entry forks, full live/aborted transcript semantics and provider-overflow compaction remain open. A generic task scheduler is available as a separately owned, explicitly ticked component; it is not integrated into the conversation scheduler. The current table reflects subsequent implementation as well.

**Historical fork checkpoint:** `fork_at` accepts a committed observation cursor even when the parent was active, provided the captured model context has a complete tool-call/result batch. It shares the immutable transcript position and atomically creates an idle child with the cut's configuration, tool state, placed application writes, and placed reset markers; queued inputs, pending resets, unplaced writes, and active work are excluded. Reopening preserves the cut. Older snapshots lacking reset metadata fail closed. This is still narrower than upstream entry-ID forks: snapshots may contain multiple messages, have no arbitrary per-entry selectors, and cuts inside unresolved tool batches are rejected. Reset/compaction model context is captured at the selected commit; the runtime does not yet expose upstream's complete ordered entry history.

**Conversation tool selection:** Hosts can persist an exact enabled-tool name list on a settled conversation, including an empty list, and clear it back to the host default. It filters model specs, direct and nested execution, and recovery. Forks retain their captured list; legacy conversations default to unrestricted. Unlike upstream's [agent configuration](https://github.com/earendil-works/pi/blob/main/packages/durable/README.md), this API does not support remove patches or a separate `modelTools` visibility list, and independent children do not automatically inherit it. Selection is not atomic with child creation or submission; the opt-in management tool does not apply it. See [durable README](../crates/durable/README.md).

**Opt-in background management checkpoint:** A scheduler can install a parent-bound `subagent` extension exposing `status` (also `list`), stop and asynchronous send, using named-child reservations, operation IDs and the durable reporter. Selection is restricted to its bound parent. Upstream's [background example](https://github.com/earendil-works/pi/blob/8636e211e7834e4ca46a22aec1d65dfd2eac8677/packages/durable/test/examples/22-subagent-background.ts) has no `wait` action; its separate [foreground example](https://github.com/earendil-works/pi/blob/8636e211e7834e4ca46a22aec1d65dfd2eac8677/packages/durable/test/examples/43-subagent-waits.ts) parks on a task-owned child's submission signal. That parking, background task ownership and inherited settings remain unsupported here; child-tool restrictions are opt-in and extension calls are not automatically replayed after interruption. See [durable README](../crates/durable/README.md) for setup and recovery limits.

**Transcript integration checkpoint:** New runtime commits atomically store message deltas in the immutable transcript together with conversation, observation and historical-fork metadata. Reads reconstruct the same snapshot API; legacy inline state migrates on its next successful commit and older history remains readable. Upstream [Durable](https://github.com/earendil-works/pi/blob/main/packages/durable/README.md) commits conversation work before exposing it and provides bounded transcript views; pi-rs still reconstructs full snapshots, copies metadata and subagent reservation seeds, and has no transcript garbage collection or downgrade compatibility. Compaction/reset preserve historical observations, but their replacement context may be copied once. The current table reflects subsequent implementation as well.

**Message-position fork checkpoint:** `fork_at_position` accepts a positioned message only when it is the last message of a nonempty immutable batch and the first observation referencing that batch has complete fork metadata with the same transcript cursor. It uses that commit's configuration and state, validates the complete tool transcript, and creates an idle child atomically using the existing fork path. Later configuration changes do not alter the cut. Positions survive resets and reopening. Missing, legacy, incomplete or mismatched metadata, positions within a batch and positions without a matching observation fail closed. Migrated legacy batches do not acquire fabricated entry identities and position forks reject them. Inherited positions without an observation in the selected conversation are rejected. Observation history is scanned linearly; cursors are trusted host data, not authorization tokens. Upstream's [fork](https://github.com/earendil-works/pi/blob/main/packages/durable/README.md#more-conversations-and-forks) supports entries more generally: arbitrary message cuts, changes between entries, application entries and full owned-task history are not reconstructed here. Reset or compaction replacement batches likewise expose only their complete snapshot boundary. See [position tests](../crates/durable/src/runtime_cas_tests.rs).

**Custom document history and fork checkpoint:** New conversation snapshots atomically record the post-commit document revision, including admission writes. Known addresses can be read at observation cuts, and forks copy documents scoped by the parent conversation UUID into independent child scope with fresh CAS versions. Other scopes remain shared. Pre-feature cuts fail closed; interior cuts require unchanged global document revision, which can reject unrelated writes. Current forks capture a revision during the call. Copying scans retained history, and upstream per-document fork policies, enforced ownership and general transactions remain unsupported. See [document API](../crates/durable/src/document.rs), [runtime](../crates/durable/src/runtime.rs), and [transaction tests](../crates/durable/tests/document_transactions.rs).

**Interior entry fork checkpoint:** New append batches record a versioned proof when all runtime fork-state fields (configuration, queue modes, extensions, provider adapter, allowed tools, tool state, resets and application writes) are unchanged across the atomic commit. A fork by occurrence ID or position may truncate such a batch at an interior message, using that commit's state, only when the resulting context has complete and valid tool calls and results. Child creation remains atomic and the parent is unchanged; reopening preserves the child. Older batches, state-changing batches, and replacement batches do not acquire proof retroactively and reject interior cuts. Interior forks materialize a new transcript and assign fresh IDs; inherited IDs cannot be selected in the child. Application document inheritance is described in the newer custom document history and fork checkpoint; task history is not reconstructed. This remains narrower than upstream's ordered entries and per-entry document history.

**Entry metadata checkpoint:** New immutable message batches carry a UUID per message occurrence and the originating conversation and observation sequence for the atomic commit that stored them. The matching historical fork snapshot contains that commit's configuration, tool state and runtime documents. These values describe the whole commit; only the last message in a batch has an exact commit boundary. Intermediate messages must not be interpreted as having independently captured state. Existing inline and transcript batches remain readable without fabricated IDs; position forks reject unannotated batches. Replacement batches (including reset/compaction) assign new IDs to replacement occurrences; they do not preserve identities across context reconstruction. Inherited entries retain their original conversation/commit association. `fork_by_entry_id` resolves IDs by scanning retained observations in bounded pages, including after resets and reopening, and forks only a proven final batch message using its original commit. Missing provider/tool settings and inherited or foreign occurrences fail closed. The child starts idle without parent abort work; the parent abort state is untouched. Historical state between messages in one batch, application entries and complete external document/task history remain unsupported. Metadata grows linearly with message count (one UUID per occurrence plus one origin and sequence per batch); UUID generation and JSON serialization add CPU, while existing full snapshot reconstruction and retained commit snapshots remain unbounded. No benchmark was performed.

**Current-view checkpoint:** `view` provides a newest-first message window, persisted conversation metadata and committed generation progress; `view_page` walks the captured immutable transcript backwards across later commits. Both message count and record visits are bounded, but individual stored batches and metadata are not byte-bounded. This is a pull snapshot, not upstream's watch, operation stream, automatic window adjustment or complete entry stream. See the durable README for migration and size limitations.

**View-watch checkpoint:** `watch_view` returns the bounded view at attachment
and polls for changed committed conversation state and generation progress. It
has no frame queue: slow readers get a replacement snapshot and can miss
intermediate commits. Unlike upstream's [watch](https://github.com/earendil-works/pi/blob/main/packages/durable/README.md#watching-a-conversation), it has no per-commit Chord operations, callback or end reason,
and does not end when its originating handle closes. See the durable README for
ownership, cancellation, memory and persistence limitations.

**Subsequent checkpoint:** Busy reset queues at safe boundaries, provider-overflow compaction and persisted bounded exponential retry were added. A host can attach a background generic task driver to the conversation store, with direct-child all/any/fail-fast waits and local descendant cancellation. A persistent subagent link can resume child admission. Task lifecycle/abort ownership is not yet integrated with conversation execution, reset ordering and tool handoff are incomplete, and subagent links do not yet supply automatic answer reporting or ownership-aware abort.

**Latest checkpoint:** Subagent completion can now be reported automatically to its parent, and reporter-driven conversations continue polling pending tools. Named child status is available as a read-only Rust API, including reservations and queued work; it is not a model-facing management tool. Automatic child tool restriction and background anchor ownership for named links are still missing. Queued submissions can be withdrawn. Conversation extension selections, prompt sections, extension-provided tools, before/after-tool hooks and selected generation hooks are supported; the scheduler can preload an extension registry before automatic recovery. The remaining hooks and hook-created tasks are not yet integrated. Task sleeps can wait for a deadline or any named signal. Subagent cancellation is not yet an ownership-aware cascade. Later checkpoints and the table below supersede earlier statements where they differ.

**Extension safety checkpoint:** Tool results are checkpointed before after-tool hooks. Abort during preparation records skipped tool results; pending and reconciled operations retain the prepared arguments for result hooks. Older pending records without those arguments fall back to the original model arguments. Extension hooks may be replayed after interruption and must make external effects idempotent. See [extension runtime tests](../crates/durable/tests/extension_runtime.rs).

**Abort and reporter checkpoint:** `Scheduler::abort` persists conversation aborts, withdraws queued inputs and fences both ordinary and reporter-driven dispatch; `abort_and_wait` waits for local workers. A dispatched uncertain effect requires reconciliation even if replay-safe. Background reporter children remain independent: parent abort does not propagate through an ownership tree. See [abort tests](../crates/durable/tests/abort.rs) and [reporter tests](../crates/durable/tests/reporter_pending.rs).

**Conversation-owned task abort checkpoint:** A conversation abort atomically marks its live generic and lifecycle task descendants and withdraws queued inputs. Root and lifecycle admission are fenced while the mark is active; an in-flight task cannot publish children after its mark. Reopening resumes task cleanup child-first, and the conversation stays abort-marked until its owned tasks settle. This requires an attached task scheduler or driver to make progress. Handler interruption remains cooperative: active synchronous handlers cannot be signalled and must return before cleanup; cleanup can replay after a crash and must be idempotent. Missing abort handlers fail with an orphan diagnostic, and restart exhaustion can fail without cleanup. Direct TaskStore mutations and noncooperating executors are outside the ownership protocol. Unlike current upstream, pi-rs has no background-task ownership flag: all conversation-owned generic tasks are included; reporter/subagent conversation links remain independent. `abort_and_wait` waits for local conversation workers, which poll task cleanup; blocked external effects still require reconciliation.

**Background task boundary checkpoint:** Conversation-owned generic tasks can be marked background at creation. Ordinary conversation abort and its task-drain check skip that task and its descendants, including after reopening; explicitly aborting the task still marks its subtree. Child tasks cannot be marked background through this API. The preceding checkpoint's statement that all generic tasks are included is superseded. This is only a task-graph prerequisite: subagent links and reporters are not owned by these tasks, there is no conversation abort option to cross background boundaries, and upstream ownership-aware idle, terminal-owner traversal, task-to-conversation cascades and abnormal-completion propagation are not implemented. Existing reporter children therefore remain independent of parent abort, and foreground subagents are not yet supported as owned tool scopes.


**Opt-in task-owned subagent admission:** `Harness::ensure_task_owned_subagent` and its scheduler counterpart atomically create an empty child conversation, permanent task-scoped reservation and ownership edge while advancing the parent task version. Matching retries return the same child, including after abort and reopen; changed owner, configuration or mode is rejected. Admission refuses an already aborting or terminal task. This does not submit input, schedule execution, seed history, or reject longer cycles. Harness abort traversal follows foreground ownership edges as described below. Existing named subagents remain independent. Storage errors require reopening before retry. See `owned_subagent` tests.

**Task-owned initial input:** `Harness::submit_task_owned_subagent` atomically creates the ownership reservation, edge and runnable initial input under the parent task version fence. Matching retries return the original child and submission, including after abort or reopen; changing the input or using the empty-child API with the same key is rejected. `Scheduler::submit_task_owned_subagent` schedules after commit, and reopening recovers a committed child if scheduling was interrupted. Foreground abort traversal and background boundaries follow the ownership rules below. This opt-in API does not seed parent history or configure extensions; storage errors require reopening. See `owned_subagent` tests.

**Foreground ownership abort traversal:** `Harness::request_abort` and `Harness::request_abort_task` atomically persist abort marks across foreground task and conversation ownership edges, withdraw queued inputs, skip background branches, and fence visited records and edges against concurrent admission. Cycles terminate; conflicts retry the complete traversal. Direct store writers outside the ownership protocol are not fenced. The standalone task scheduler and task driver still fail closed on foreground conversation edges; they do not signal or join child conversation workers. Hosts must stop and drive those workers separately, including after reopening, until scheduler propagation is implemented. A storage error can have an uncertain outcome and requires reopening. See `owned_subagent` tests.

**Child-first owned cleanup checkpoint:** Compared with upstream [abort and subagents](https://github.com/earendil-works/pi/blob/06f5671c924cd6eaa1d7501736925db0e5cb2a49/packages/durable/README.md#abort-and-subagents), which waits for the conversation to become idle and supports explicitly crossing background boundaries, this implementation retains the boundaries and limitations below. Task abort cleanup waits for each foreground owned conversation to finish its persisted abort, including that conversation's foreground task descendants. Restart-limit failures also wait for those children. `Scheduler::abort_and_wait` joins the workers for all conversations marked by the atomic traversal. Background edges remain boundaries. Cyclic ownership may deadlock cleanup; blocked uncertain operations require reconciliation and generic tasks require a running driver. The standalone task scheduler and driver still reject aborts involving foreground conversation edges. See `owned_subagent` tests.

**Earlier scheduler propagation checkpoint (superseded by child-first checkpoint above):** `Scheduler::abort` and `abort_task` fence existing conversation polls while committing the foreground graph, cancel affected workers, and schedule each marked conversation for cleanup. Reopening schedules all persisted conversations. Background edges remain independent. Standalone task abort still rejects foreground child conversations, and task cleanup does not join child conversation cleanup; `abort_and_wait` waits only for the requested conversation's local workers. Active nested-conversation race and crash/reopen coverage remains incomplete. Legacy task cancellation fails closed when it would strand a foreground child. See `owned_subagent` tests.

**Ownership edge storage checkpoint:** `ownership_edge::EdgeStore` prepares checked, atomic task-to-existing-conversation links with explicit foreground/background metadata and a unique owner per child. Both endpoint versions and task ownership are fenced at commit, and edge creation advances the task version to invalidate a concurrent traversal's earlier task snapshot. Edges survive reopen. This is only a composable storage primitive: creation of the conversation and task must currently precede the edge; no traversal, cycle detection beyond a direct self-edge, scheduling, abort propagation, lifecycle cleanup, or subagent integration is provided. Edge mode is stored metadata and does not itself implement upstream background boundaries. See [ownership edge tests](../crates/durable/tests/ownership_edge.rs).

**Continue checkpoint:** `Harness::submit_continue` and `Scheduler::submit_continue` persist a distinct, deduplicated run submission without a user message, reject busy conversations, place queued steers and follow-ups according to the configured queue modes, and settle the participating submissions together. Empty or answered contexts settle `nothing_to_answer` without a model request; failed runs retain their unanswered user/tool context. Recovery resumes the committed phase, and truncated tool calls are recorded as skipped without dispatch. See [continuation tests](../crates/durable/tests/continue_submission.rs) and [runtime tests](../crates/durable/tests/runtime.rs). Unlike upstream, this runtime has no public transactional/tool-side admission, `pi.live.runFailure`; it uses Rust status and reason strings and represents continue content as an empty compatibility field in memory (omitted from storage). Historical synthetic failure messages from older versions are not rewritten. Queued reset ordering and generic task ownership remain separate gaps.

**Admission policy checkpoint:** `Harness`, `Scheduler`, and the state-backed
conversation helper now support optional busy and idle rejection for input,
with request-ID deduplication before the policy check and version-checked
admission under contention. Busy means an active run, even when queued input
remains after a failed run. Duplicate input request IDs are resolved before content validation. Arbitrary host transactions / `submit(tx, draft)` are not supported. See the admission concurrency and recovery tests in
[`runtime_cas_tests.rs`](../crates/durable/src/runtime_cas_tests.rs). The
original audit table below remains a historical baseline.
**Write-submission checkpoint:** The experimental runtime accepts display-only application entries through `submit_write`, persists them immediately while busy, and delays placement behind queued resets. Request IDs deduplicate within the conversation and cannot be reused across input and write types. Entries are exposed in `Conversation.application_writes` and observer snapshots with a placement flag and preceding reset ID. This is a narrower API than upstream: model messages, head edits, stale-head handling, generic entry transactions and write withdrawal are not implemented. Current forks and historical snapshots created after this change inherit application entries at the selected point, but not their request IDs. Queued writes are exposed as pending records, not placed transcript entries; observers must filter `placed`. The runtime still stores snapshots rather than an upstream ordered entry stream.

**onYield checkpoint:** Final answers enter a persisted onYield phase with a stable hook memo. A string continuation keeps the current submissions open and starts a fresh turn budget; queued steering, follow-ups, or resets take precedence, and after-run hooks run only once an answer stands. Hook-created tasks and their wait are committed atomically; after all children terminate, the first successful child in creation order with a nonempty string `{"continue": "..."}` is selected. Failed and invalid child outcomes are ignored. A registered task driver is required, and reopening resumes the persisted wait. Hooks may replay after interruption or a concurrent admission and must make effects idempotent. Unlike upstream, this subset accepts only string continuation input, exposes the already-committed answer in the hook snapshot, and treats invalid hook decisions or hook errors as recoverable phase errors rather than reporting and skipping them. Conversation abort marks owned hook children and descendants atomically and waits for cleanup with an attached task driver; synchronous effects still cannot be interrupted or rolled back. See [extension runtime tests](../crates/durable/tests/extension_runtime.rs).

**beforeCompact checkpoint:** Manual, threshold and overflow compactions persist the selected message range and a stable hook memo identity before calling selected hooks. The first decline or summary wins; hook errors are skipped, cancellation replays the phase, and hook summaries bypass model usage. Unlike upstream, the host exposes message indices instead of entry IDs and markers, has no manual instructions parameter or hook report callback, rejects blank summaries, and still requires idle manual compaction. See [compaction tests](../crates/durable/tests/features.rs).

**After-tools termination checkpoint:** A successful after-tools child result of exactly `{ "terminate": true }` settles active inputs with the tool-calling assistant answer, runs after-run hooks, and only then places queued inputs at the final boundary. The persisted child wait resumes after reopening. Other results are ignored without upstream’s invalid-decision report; tool-result terminate controls remain unsupported. See [extension runtime tests](../crates/durable/tests/extension_runtime.rs).

**Queue delivery checkpoint:** Durable conversations persist independent steering and follow-up delivery modes, defaulting to one at a time for new and legacy records. `all` selects every queued input of that kind at the eligible boundary. Final boundaries settle the previous run before starting the selected successor inputs; post-tool boundaries select steers only. See [durable README](../crates/durable/README.md).

Admission can atomically compose checked document operations and task creation; conversation forks copy eligible conversation-scoped documents. ## Verification baseline

For the already implemented subsets, run `cargo test -p durable-store` and `cargo test -p pi-rs-durable`; the standalone example `cargo run -p pi-rs-durable --example resume -- start DB_PATH` followed by `resume DB_PATH CONVERSATION_ID` demonstrates admission across two processes, not full upstream compatibility. Run upstream tests against the pinned upstream revision when implementing a specific compatibility gate. For crash cases use process termination and controlled barriers, not graceful shutdown or timing-dependent sleeps. No general exactly-once guarantee follows from local persistence.

### Opt-in provider request bodies

A host can install a `model::ProviderAdapter`, then select its stable, versioned
ID for a settled conversation with `Harness::select_provider_adapter`. Selection
is persisted (including in fork snapshots); after reopening, install the same
adapter and selected extensions on `open_paused` before resuming. A missing or
mismatched adapter fails closed. Unselected conversations continue to use the
existing `Model` interface. Core and built-in providers are unchanged.

The adapter prepares the provider JSON body without dispatching. The selected
`BeforeProviderRequest` hooks receive `{model, payload}` in selection order and
return `Replace({"payload": ...})` or `Pass`. The model here is the configured
model name, not upstream's full model descriptor. Each replacement feeds the
next hook. The runtime rejects hook errors, malformed replacements, non-object
or over-8-MiB bodies, then calls the host's provider-specific validation before
dispatch. The host must implement both validation and guarded dispatch, and
must send exactly the validated body while enforcing authorization, endpoint
and budget policy. The adapter is trusted code; the runtime cannot enforce its
internal behavior. Hook failures deliberately fail closed, whereas upstream
reports the error and continues the chain (upstream pi commit
`1cfb326bfcc5c221526809fa081c4ff85b459847`,
`packages/durable/src/harness/generation.ts` and `CHANGELOG.md`).

The attempt carries the committed conversation and request IDs, turn, retry
count and restart count. New generation attempts after retry or recovery get a
new request ID. Hook context contains the persisted conversation snapshot and
request-scoped durable memo. Bodies and arbitrary hook side effects are not
checkpointed: hooks and preparation run again for each attempt and should use
memo for stable values. Cancellation stops preparation, hook execution or
stream collection, but cannot prove a remote request did not execute; recovery
settles the abandoned request as unconfirmed. As upstream, compaction bypasses
this generation hook. Unlike upstream pi-ai, provider-internal HTTP retries or
body rebuilds are not intercepted; adapters must avoid hidden rebuilds or guard
them themselves. This interface does not retrofit built-in provider clients,
settlement, exactly-once network execution, or automatic adapter installation.
